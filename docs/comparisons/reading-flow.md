## 긴 문서에서 실제로 달라진 부분

가상의 색인 갱신 서비스를 처음 접하는 백엔드 개발자가 대상입니다. HTTP와 비동기 작업은 알지만 서비스의 접수·상태·검색 전환 관계는 모르는 독자로 설정했습니다. [생성 입력](../../evaluations/runs/2026-11-03-reading-flow/inputs/long-document.md)에는 20개 사실 메모를 제공했습니다.

익명 검토자는 문서 전체를 기준으로 세 결과 모두 20개 사실과 조건을 보존했다고 판단했습니다. 자동 재시도나 완료 시간을 확정하는 등 원자료와 직접 충돌한 정책은 발견하지 못했습니다. 이는 모델의 문서 대조 결과이며, 모든 문장을 따로 읽어도 전제가 완벽히 붙어 있다는 뜻은 아닙니다.

### 상태표 뒤의 설명을 단계의 흐름으로 묶었습니다

미적용 결과는 전체 상태표 뒤에서 검증·완료를 설명하고, 후반의 「접수 응답, 작업 상태, 검색 결과를 함께 읽기」에서 상태별 의미와 다음 행동을 다시 표로 정리합니다. 이 표는 필요한 행동을 찾는 데 쓸 수 있지만, 앞의 내용을 순서대로 읽는 독자에게는 반복 구간이 됩니다.

v0.2.1도 상태표를 먼저 제공한 뒤 검증 범위와 반영 시점을 풀어 설명합니다. v0.3.0 생성본은 정상 경로를 한 줄로 제시하고 「대기부터 검증까지: 후보 색인 준비」, 「반영 대기부터 완료까지: 활성 판 전환」으로 나눕니다. 후보를 만드는 과정과 검색에 사용하는 판이 바뀌는 과정을 구별해 이어 읽게 하는 구성입니다.

**v0.2.1 — 상태표의 검증 항목**

> 검증 중 | 후보의 문서 수와 확인용 문서 조회를 검사한다. | 모든 검사를 통과해야 다음 상태로 간다.

**v0.2.1 — 표 뒤의 보충 문단**

> 검증에서는 후보의 문서 수가 원본과 일치하는지 확인한다. 또한 원본에 지정된 두 확인용 문서가 정확한 키로 조회되는지 검사한다. 이 검사를 모두 통과해야 `반영 대기`로 이동한다. 검증이 확인하는 범위는 문서 누락과 기본 조회이며, 검색 순위의 품질을 평가한 결과는 아니다.

**v0.3.0 생성본 — 후보 준비 절의 검증 문단**

> `검증 중`에는 후보의 문서 수가 원본과 일치하는지, 원본에 지정된 두 확인용 문서가 정확한 키로 조회되는지 검사합니다. 이 조건을 모두 충족해야 다음 상태로 넘어갑니다. 검증 범위는 문서 누락과 기본 조회이며, 검증을 통과했다고 해서 검색 순위의 품질까지 평가한 것은 아닙니다.

새 생성본은 같은 검증을 표와 문단에서 반복하는 부분을 줄였습니다. 다만 상태 하나의 뜻을 빠르게 조회하려는 독자에게는 기존 상태표가 유용할 수 있습니다. 표를 없애는 것이 항상 개선이라는 뜻은 아닙니다.

### 접수 판단에 필요한 응답을 접수 절에 두었습니다

v0.2.1의 접수 절은 진행 중 작업이 있으면 새 작업을 받지 않는다고 설명합니다. 이때 반환하는 `진행 중 작업 있음`과 기존 접수 번호, 새 번호를 만들지 않는 조건은 뒤의 중단 절에서 확인할 수 있습니다.

v0.3.0 생성본은 접수 거절을 설명하는 문단에서 그 응답과 번호 처리까지 함께 제시합니다. 접수 결과를 확인하는 독자가 관련 내용을 다른 절에서 모을 필요가 줄어든 배치입니다. **미적용 문서도 이 정보를 접수 절에 제공합니다.** 새 스킬에서만 나타난 독점적인 개선으로 계산하지 않습니다.

### 필요한 조건의 반복은 남았습니다

세 결과 모두 중단 요청의 수락과 실제 종료를 구별합니다. 새 생성본에는 다음과 같은 문단이 있습니다.

> 새 갱신이나 재시도를 시작하려면 작업 상태가 실제로 `중단`으로 바뀌었는지 확인해야 합니다. 한 자료집에는 진행 중 작업을 하나만 허용하므로, 중단 요청을 수락했어도 아직 `중단` 상태가 아니면 그 작업이 자리를 차지합니다. 이때 새 갱신이나 재시도를 요청하면 `진행 중 작업 있음`과 기존 접수 번호를 반환하고 새 번호는 만들지 않습니다.

앞의 접수 절에서 이미 설명한 제한을 현재 판단인 ‘언제 새 작업을 넣을 수 있는가’에 연결합니다. 이런 반복은 단순한 중복 삭제의 대상에서 제외했습니다. 이 조건은 미적용과 기존 버전도 보존하므로, 새 버전이 바로잡은 사실 오류로 제시하지 않습니다.

### 새 생성본에도 찾아보기의 보완점이 있습니다

새 생성본의 첫 갱신 예외는 「완료 상태와 검색 결과를 함께 읽기」의 마지막 문단에 있습니다. 아직 완료한 적이 없는 자료집의 `색인 준비 안 됨`을 찾는 독자에게는 제목만으로 위치를 알기 어렵습니다. v0.2.1의 「실패하거나 첫 갱신이 끝나지 않았을 때」가 이 예외를 제목에 더 직접 드러냅니다.

새 생성본의 「조정기가 전환하기 전까지 조회 API는 기존 활성 판을 사용합니다」도 기존 활성 판이 있다는 전제를 그 문장 가까이에 두면 더 정확하게 찾아 읽을 수 있습니다. 다음 절에서는 첫 갱신의 예외를 정확히 설명하므로 검토자는 문서 전체의 사실 충돌로 판단하지 않았습니다. 정보의 근접 배치라는 새 지침을 모든 위치에서 완벽히 구현한 출력은 아닙니다.

## 짧은 PR의 분량과 조건 보존

짧은 사례는 **관측 로그만 추가하고 원인이나 해결을 확정하지 않은 PR**입니다. 긴 문서 지침이 짧은 요청에도 목차·개요·결론을 붙이는지, 분량 때문에 미확정 원인과 미실행 검증을 지우는지 확인했습니다. [생성 입력](../../evaluations/runs/2026-11-03-reading-flow/inputs/short-pr.md)은 250~400자 정도를 요청합니다.

v0.3.0 생성본은 관측과 영향의 불확실성을 첫 문단에 모으고, 다음 문단에서 로그 추가와 유지되는 처리 조건을 설명합니다. v0.2.1의 「처리 동작은 유지합니다」는 정리 조건·제한 시간·재시도·응답 형식을 포괄하지만 각 항목을 직접 열거하지는 않습니다. 미적용과 v0.3.0 생성본에는 네 항목이 명시되어 있습니다.

어느 조건도 이 한 사례에서 긴 문서 형식을 과하게 적용하지 않았습니다. 새 지침만이 짧은 글의 과잉 구성을 막았다고 결론낼 수는 없습니다.

# 모래결 색인 갱신기: 요청 접수부터 검색 반영까지

모래결 색인 갱신기는 자료집의 문서를 검색할 색인을 만드는 내부 서비스다. 새로 합류한 개발자가 먼저 구분해야 할 것은 **갱신 요청의 접수, 작업의 진행 상태, 검색에 쓰이는 활성 색인**이다. 접수가 성공하면 작업 기록이 생기지만, 검색 결과가 곧바로 바뀌지는 않는다. 작업이 후보 색인을 만들고 검증한 뒤 활성 판으로 전환되어야 새 내용을 검색할 수 있다.

이 문서는 가상의 자료집 `C17`, 원본 `r18`, 접수 `q203`, 색인 판 `i52`를 예로 들어 그 과정을 설명한다.

## 1. 원본에서 검색 결과까지, 구성 요소가 맡는 일

원본을 올리는 기능은 별도 시스템에 있다. 모래결 색인 갱신기는 이미 보관된 원본을 선택해 색인을 갱신한다. 조회 API가 검색하는 대상은 원본 자체가 아니라 활성 색인이다. 따라서 새 원본의 보관이 끝났다는 사실만으로 검색에 새 내용이 반영되었다고 판단할 수는 없다.

갱신과 검색은 다음 네 구성 요소가 나누어 맡는다.

| 구성 요소 | 역할 |
| --- | --- |
| 접수 API | 갱신 요청을 확인하고 작업 기록을 저장한다. |
| 작업 조정기 | 작업을 구축기에 넘기고, 검증을 통과한 후보를 활성 색인으로 반영한다. |
| 구축기 | 선택된 원본으로 후보 색인을 만들고 검증한다. |
| 조회 API | 자료집의 활성 색인을 사용해 검색한다. |

접수 API가 요청을 기록하면 조정기가 작업을 구축기에 넘긴다. 구축기는 검색에 사용할 새 색인을 후보로 만든다. 이 후보는 기존 활성 색인과 분리되어 보관된다. 구축 도중 일부 문서만 만들어져 있어도 그 내용이 기존 검색 결과에 섞이지 않는 이유다.

후보가 검증을 통과하면 조정기가 활성 판으로 전환한다. 조회 API는 이 전환이 확정되기 전까지 기존 활성 판을 사용한다. 후보를 만드는 과정과 실제 검색에 사용하는 판을 바꾸는 과정은 이렇게 구분된다.

## 2. 네 식별자를 구분하고, 작업이 선택한 원본을 확인한다

하나의 갱신을 살펴볼 때는 다음 식별자를 함께 보게 된다.

| 식별자 | 가리키는 대상 | 예시 |
| --- | --- | --- |
| 자료집 번호 | 색인을 갱신하고 검색할 자료집 | `C17` |
| 원본 번호 | 내용이 고정된 원본 한 묶음 | `r18` |
| 접수 번호 | 접수된 작업 기록 | `q203` |
| 색인 판 번호 | 만들어진 색인의 판 | `i52` |

예를 들어 “자료집 `C17`의 원본 `r18`로 색인을 갱신한다”는 요청이 `q203`으로 접수되고, 그 작업이 색인 `i52`를 만들 수 있다. 이때 `r18`, `q203`, `i52`의 숫자는 각각 별도 순서다. 숫자 크기를 서로 비교해 진행률이나 최신 여부를 판단해서는 안 된다.

**작업 상태를 조회할 때 사용하는 식별자는 접수 번호다.** `q203`의 상태를 알고 싶다면 `q203`으로 조회해야 한다. 자료집 번호 `C17`이나 색인 판 번호 `i52`로 대신 조회할 수 없다.

원본 번호는 작업이 어떤 내용을 사용해야 하는지도 고정한다. `q203`이 `r18`로 접수되었다면 이후 `r19`가 보관되어도 작업은 끝까지 `r18`을 사용한다. 조정기나 구축기가 진행 도중 최신 원본으로 대상을 바꾸는 기능은 없다. 따라서 새 원본이 올라왔는지와 현재 작업이 어느 원본을 처리하는지는 별도로 확인해야 한다.

## 3. 접수 성공은 어디까지 보장하는가

접수 API는 먼저 자료집이 존재하는지, 지정한 원본의 보관이 완료되었는지 확인한다. 둘 중 하나라도 충족하지 않으면 이유를 반환하고 작업 기록을 만들지 않는다.

두 조건을 모두 충족해도 접수가 거절될 수 있다. 한 자료집에는 진행 중인 작업을 하나만 허용하기 때문이다. 같은 자료집에 진행 중 작업이 있으면 새 갱신이나 재시도 요청에 대해 `진행 중 작업 있음`과 그 작업의 접수 번호를 반환하며, 새 접수 번호는 만들지 않는다. 이 제한은 자료집별로 적용되므로 다른 자료집의 접수에는 영향을 주지 않는다.

접수에 성공하면 작업 기록을 저장한 뒤 새 접수 번호와 `대기` 상태를 반환한다. 이 응답으로 확인할 수 있는 것은 요청이 작업 목록에 들어갔다는 사실이다. 다음 사항까지 보장하는 응답은 아니다.

- 구축기가 작업을 시작했다는 것
- 후보 색인이 검증을 통과했다는 것
- 자료집의 활성 색인이 바뀌었다는 것

접수 뒤에는 응답으로 받은 접수 번호로 작업 상태를 확인한다. 검색에 새 내용이 반영되었는지를 판단하려면 이후의 상태 전이, 특히 `완료` 여부를 봐야 한다. 접수 응답은 그 확정까지 걸리는 시간도 약속하지 않는다.

## 4. 정상 경로에서 각 상태가 뜻하는 것

정상적인 갱신은 `대기 → 구축 중 → 검증 중 → 반영 대기 → 완료` 순서로 진행한다. 이 중 `완료`는 종료 상태다. 정상 경로 밖의 종료 상태로는 `실패`와 `중단`이 있으며, 이 세 상태를 제외한 나머지는 모두 진행 중 상태다.

| 상태 | 작업에서 일어나는 일 | 다음에 기다리는 일 |
| --- | --- | --- |
| 대기 | 작업 기록은 있지만 구축기가 아직 시작하지 않았다. | 구축 시작 |
| 구축 중 | 접수할 때 선택한 원본으로 후보 색인을 만든다. | 후보 구축을 마치고 검증 진행 |
| 검증 중 | 후보의 문서 수와 확인용 문서의 조회를 검사한다. | 모든 검증 항목 통과 |
| 반영 대기 | 검증을 통과한 후보가 활성 판으로 전환되기를 기다린다. | 조정기의 활성 판 전환 |
| 완료 | 활성 판 변경과 작업 완료 기록이 함께 확정되었다. | 해당 갱신 작업은 종료됨 |

### 검증 통과가 뜻하는 범위

검증 중에는 두 가지를 확인한다. 후보의 문서 수가 원본과 일치해야 하고, 원본에 지정된 두 확인용 문서가 정확한 키로 조회되어야 한다. 모두 통과해야 `반영 대기`로 넘어간다.

이 검증은 문서 누락과 기본 조회를 확인하는 범위다. 검색 순위의 품질을 평가한 결과는 아니다. 따라서 검증 통과 기록을 근거로 검색 순위가 좋아졌다고 설명할 수는 없다.

검증 통과와 검색 반영도 구분해야 한다. `반영 대기`는 후보가 검증을 마쳤다는 뜻이지만, 아직 활성 판 전환을 기다리는 상태다. 이때 조회 API는 기존 활성 판을 사용한다. 검증 통과 기록이나 `반영 대기` 표시만 보고 새 내용이 이미 검색된다고 안내해서는 안 된다.

### 완료가 뜻하는 확정 시점

반영할 때 조정기는 자료집의 활성 색인 판 변경과 해당 작업의 완료 기록을 하나의 변경으로 함께 확정한다. 따라서 `완료` 상태는 활성 판 전환이 확정되었다는 뜻이다.

`q203`이 만든 `i52`가 반영되는 경우라면, `q203`의 완료는 자료집 `C17`의 활성 판이 `i52`로 전환되었음을 뜻한다. 접수 성공과 달리 실제 검색에 사용할 판의 변경까지 확인할 수 있는 상태다.

## 5. 완료 뒤에도 이전 판의 검색 응답이 올 수 있다

작업 완료와 검색 응답을 함께 읽으려면 검색 요청이 **언제 시작했는지**를 봐야 한다. 조회 API는 요청을 시작할 때 활성 판을 한 번 정하고, 응답을 마칠 때까지 그 판을 유지한다. 한 검색 요청 안에서 두 판의 결과를 섞지는 않는다.

| 검색 요청이 시작된 시점 | 사용하는 색인 판 | 응답을 해석하는 방법 |
| --- | --- | --- |
| 활성 판 전환 전 | 기존 활성 판 | 전환 뒤에 응답이 도착하더라도 이전 판의 결과일 수 있다. |
| 활성 판 전환 확정 후 | 새 활성 판 | 새로 반영된 판으로 검색한다. |

예를 들어 `q203`이 `반영 대기`인 동안 시작한 검색은 기존 활성 판을 선택한다. 그 검색이 끝나기 전에 `q203`이 완료되어 `i52`가 활성화되더라도, 이미 시작한 검색은 끝까지 기존 판을 사용한다. 반대로 전환이 확정된 뒤 시작한 검색은 `i52`를 사용한다.

따라서 완료를 확인한 뒤 이전 내용의 응답을 받았다는 사실만으로 전환 실패라고 판단할 수는 없다. 그 응답이 전환 전에 시작한 검색의 결과인지 함께 살펴야 한다. 새 판의 검색 결과를 확인하려면 전환 확정 뒤 시작한 검색을 기준으로 읽는다.

## 6. 실패했을 때 기존 검색은 어떻게 되는가

구축이나 검증을 더 진행할 수 없는 오류가 나면 작업은 `실패`로 끝난다. 상태 조회에는 오류가 발생한 단계와 이유가 남는다. 실패한 후보는 활성 판으로 반영하지 않는다.

이미 활성 판이 있는 자료집은 그 판을 계속 사용한다. 새 갱신의 실패가 기존 검색의 중단을 뜻하지 않는 이유다. 갱신 상태에 실패가 표시되어도 조회 API는 이전에 반영된 색인으로 검색할 수 있다.

다만 첫 갱신이라면 상황이 다르다. 한 번도 반영을 마치지 않은 자료집에는 기존 활성 판이 없다. 첫 갱신이 진행 중이거나 `실패` 또는 `중단`으로 끝났다면 조회 API는 `색인 준비 안 됨`을 반환한다.

이 응답은 검색 결과가 없는 정상 응답인 빈 목록과 구분해야 한다. 빈 목록은 검색 결과가 없다는 뜻이고, `색인 준비 안 됨`은 검색에 사용할 활성 판이 아직 없다는 뜻이다. 작업 상태만 보지 말고 해당 자료집에 이전에 반영된 활성 판이 있었는지도 함께 보아야 한다.

## 7. 중단 수락과 작업의 중단 완료는 다른 시점이다

중단 요청은 모든 상태에서 받을 수 있는 것이 아니다.

| 조정기가 중단 요청을 확인한 시점의 상태 | 수락 여부 |
| --- | --- |
| 대기·구축 중·검증 중 | 수락 가능 |
| 반영 대기 | 거절 |
| 완료·실패·중단 | 거절 |

판단 기준은 사용자가 중단 버튼을 누른 시각이 아니라 **조정기가 요청을 확인한 시점의 작업 상태**다. 사용자가 검증 중이라고 보고 중단을 요청했더라도, 조정기가 확인할 때 이미 `반영 대기`라면 요청은 거절된다.

중단을 수락하면 먼저 중단 표시를 남긴다. 이후 조정기나 구축기가 그 표시를 확인하고 작업을 멈춘 뒤에야 상태를 `중단`으로 바꾼다. 따라서 중단 수락 뒤에도 잠시 직전의 진행 중 상태가 보일 수 있다. 수락 응답을 곧바로 중단 완료로 읽어서는 안 된다.

그동안에도 중단 표시의 효력은 있다. 표시가 남은 후보는 검증을 마치더라도 `반영 대기`로 넘어가거나 활성화될 수 없다. 중단으로 새 후보가 활성 판을 대체하지 않으므로, 기존 활성 판이 있었다면 기존 검색을 계속 사용한다. 활성 판이 없는 첫 갱신이었다면 앞서 설명한 대로 `색인 준비 안 됨` 상태가 이어진다.

### 새 작업은 중단 상태가 된 뒤 접수한다

중단 요청이 수락되었더라도 아직 상태가 `중단`이 아니라면 그 작업은 자료집의 진행 중 작업 자리를 차지한다. 이때 새 갱신이나 재시도를 요청하면 `진행 중 작업 있음`과 기존 접수 번호가 반환되며 새 번호는 생기지 않는다.

따라서 중단 후 다른 작업을 시작하려면 기존 접수 번호로 상태를 확인하면서 실제로 `중단`에 도달하기를 기다려야 한다. 중단을 요청했다는 사실, 중단이 수락되었다는 사실, 작업이 `중단` 상태로 끝났다는 사실을 구분해야 다음 접수 시점을 판단할 수 있다.

## 8. 재시도는 같은 원본으로 새 작업을 시작한다

재시도는 `실패` 또는 `중단`으로 끝난 작업에만 요청할 수 있다. 수락되면 기존 기록을 그대로 두고 새 접수 번호를 만든다. 새 작업은 `대기`부터 시작하며, 이전 작업과 같은 원본 번호를 사용한다.

이때 이전 후보를 재사용하거나 문서별 진행 위치에서 이어서 처리하지 않는다. 선택된 원본으로 처음부터 다시 구축한다. 재시도 후 상태를 확인할 때도 기존 작업의 접수 번호가 아니라 새로 받은 접수 번호를 사용해야 한다.

원본 선택이 달라지는 것도 아니다. `r18`을 사용한 `q203`이 실패한 뒤 `r19`의 보관이 끝났다고 하자. 이 상황에서 선택할 요청은 반영하려는 원본에 따라 달라진다.

| 원하는 결과 | 요청할 작업 | 사용하는 원본 |
| --- | --- | --- |
| 실패하거나 중단된 작업을 같은 원본으로 다시 수행 | 기존 작업의 재시도 | 기존 작업이 선택한 `r18` |
| 새로 보관된 원본을 검색에 반영 | `r19`를 지정한 일반 갱신 | 새 요청에서 지정한 `r19` |

`q203`을 재시도하면 이후에 보관된 `r19`가 있어도 `r18`을 사용한다. `r19`를 반영하려면 자료집에 진행 중 작업이 없는 때에 `r19`를 지정해 일반 갱신을 요청해야 한다. 재시도는 실패·중단 작업을 다시 수행하는 방법이고, 반영할 원본을 새로 선택하는 요청은 일반 갱신이다.

재시도에도 자료집별 진행 중 작업 제한이 적용된다. 기존 작업이 이미 실패나 중단으로 끝났더라도 같은 자료집에서 다른 작업이 진행 중이면 새 재시도를 접수할 수 없다.

## 9. 접수 응답, 작업 상태, 검색 결과를 함께 읽기

갱신 뒤 무엇을 기다려야 하는지는 현재 확인한 정보에 따라 달라진다. 접수 응답은 작업 기록의 생성 여부를, 상태 조회는 해당 작업의 진행과 종료를, 검색 응답은 요청 시작 시점에 선택된 활성 판의 결과를 보여 준다.

| 현재 확인한 정보 | 알 수 있는 것 | 이어서 확인할 것 |
| --- | --- | --- |
| 새 접수 번호와 `대기` 응답 | 작업 기록이 저장되었다. | 해당 접수 번호로 이후 상태를 확인한다. |
| `구축 중` 또는 `검증 중` | 선택한 원본으로 후보를 준비하고 있다. | 검증과 활성 판 전환이 끝나는지 확인한다. |
| `반영 대기` | 후보가 검증을 통과했다. | 활성 판 전환이 확정되어 `완료`가 되는지 확인한다. |
| `완료` | 활성 판 전환이 확정되었다. | 새 판의 결과는 전환 확정 뒤 시작한 검색으로 확인한다. |
| `실패` | 해당 후보는 반영되지 않는다. | 오류 단계와 이유를 보고, 같은 원본을 재시도할지 다른 원본의 일반 갱신을 요청할지 판단한다. |
| 중단 수락 뒤 진행 중 상태 | 중단 표시는 남았지만 작업의 중단이 아직 끝나지 않았다. | 새 작업을 접수하기 전에 `중단` 상태를 확인한다. |
| `색인 준비 안 됨` | 검색에 사용할 활성 판이 없다. | 첫 갱신이 진행 중인지, 실패·중단으로 끝났는지 작업 상태를 확인한다. |

예를 들어 `C17`에 기존 활성 판이 있고 `r18` 갱신이 `q203`으로 접수되었다면, 대기·구축·검증·반영 대기 동안 검색은 기존 판을 사용한다. `q203`이 완료되면 활성 판이 `i52`로 전환된 것이며, 그 뒤 시작한 검색은 `i52`를 사용한다. 도중에 `r19`가 보관되었더라도 `q203`이 만든 판은 `r18`을 바탕으로 한다.

같은 작업이 구축이나 검증에서 실패했다면 `i52` 후보는 반영되지 않고 기존 판으로 검색을 계속한다. `q203`을 재시도하면 새 접수 번호로 `r18`부터 다시 구축한다. `r19`가 필요하다면 진행 중 작업이 없는 때에 별도의 일반 갱신으로 요청한다. 이 흐름에서 작업의 종료 여부와 원하는 원본 번호를 함께 확인해야 다음 요청을 올바르게 선택할 수 있다.

## 10. 아직 정해지지 않은 운영 정책

현재 자료로 확정할 수 있는 것은 위의 상태 의미와 수동 재시도 조건까지다. 다음 항목은 미확정이다.

- 대기 시간의 상한
- 자동 재시도의 유무와 간격
- 실패·중단 후보의 보관 기간
- 반영 단계에서 오류가 났을 때의 복구 절차

따라서 접수나 중단 수락을 근거로 일정 시간 안에 다음 상태가 된다고 약속할 수 없다. 실패한 작업이 자동으로 재시도된다거나, 반영 단계의 오류가 특정 절차로 자동 복구된다고 가정해서도 안 된다. 후보의 보관·삭제 시점 역시 정해진 정책으로 설명할 수 없다. 이런 운영 판단에는 별도로 확정된 정책이 필요하다.

# 모래결 색인 갱신기: 요청 접수부터 검색 반영까지

모래결 색인 갱신기는 자료집의 문서를 검색할 색인을 만드는 내부 서비스다. 원본 업로드는 별도 시스템이 담당하며, 이 서비스는 보관이 끝난 원본을 선택해 색인을 갱신한다. 조회 API가 검색에 사용하는 대상은 원본이 아니라 활성 색인이다.

갱신을 요청한 뒤에는 접수 응답, 작업 상태, 검색 결과를 함께 읽어야 한다. 접수 성공은 작업 기록이 저장되었다는 뜻이고, 완료는 새 색인으로의 전환이 확정되었다는 뜻이다. 검색 결과를 해석할 때는 해당 검색이 전환 전후 어느 시점에 시작했는지도 살펴야 한다. 이 문서의 서비스명과 사례는 모두 가상이다.

## 구성 요소와 원본이 검색에 반영되는 경로

갱신은 접수 API에서 시작한다. 접수 API가 요청을 확인해 작업 기록을 남기면, 작업 조정기가 그 작업을 구축기에 넘긴다. 구축기는 선택된 원본으로 후보 색인을 만들고 검증한다. 검증을 통과한 후보를 활성 색인으로 반영하는 주체는 조정기다.

조회 API는 이 과정에서 활성 색인으로 검색한다. 구축 중인 후보는 활성 색인과 분리되어 보관되므로, 후보에 일부 문서만 만들어진 상태가 검색 결과에 섞이지 않는다. 기존 활성 색인이 있는 자료집이라면 새 후보를 만드는 동안에도 그 기존 판으로 검색한다. 처음 색인을 만드는 자료집처럼 활성 판이 아직 없는 경우의 응답은 뒤에서 따로 설명한다.

## 자료집, 원본, 요청, 색인을 구분하는 식별자

갱신 과정을 따라가려면 무엇을 가리키는 번호인지 먼저 구분해야 한다. 예를 들어 자료집 `C17`의 원본 `r18`을 갱신해 달라는 요청 `q203`이 색인 `i52`를 만들 수 있다.

| 식별자 | 사례 | 가리키는 대상 |
| --- | --- | --- |
| 자료집 번호 | `C17` | 색인을 갱신할 자료집 |
| 원본 번호 | `r18` | 내용이 고정된 원본 한 묶음 |
| 접수 번호 | `q203` | 접수한 갱신 작업. 작업 상태를 조회할 때 사용한다. |
| 색인 판 번호 | `i52` | 만들어진 색인의 판 |

`r18`, `q203`, `i52`의 숫자는 각각 별도 순서다. 숫자끼리 비교해 진행률이나 최신 여부를 판단할 수 없다. 작업 상태를 조회할 때도 접수 번호인 `q203`을 사용해야 하며, 자료집 번호나 색인 판 번호로 대신 조회할 수 없다.

원본 번호는 작업이 사용할 내용을 고정한다. `q203`이 `r18`로 접수되었다면 작업 도중 `r19`가 올라와도 끝까지 `r18`을 사용한다. 조정기와 구축기는 진행 중에 최신 원본으로 대상을 바꾸지 않는다. 따라서 갱신 완료 여부를 확인할 때는 어떤 원본을 대상으로 접수했는지도 함께 확인해야 한다.

## 접수 성공으로 알 수 있는 것

접수 API는 자료집이 존재하는지, 지정한 원본의 보관이 끝났는지 확인한다. 둘 중 하나라도 충족하지 않으면 이유를 반환하고 작업 기록을 만들지 않는다. 이 확인을 통과하더라도 같은 자료집에 진행 중인 작업이 있으면 새 작업을 받지 않는다. 한 자료집에는 진행 중 작업을 하나만 허용하기 때문이다.

요청을 받으면 작업 기록의 저장을 마친 뒤 새 접수 번호와 `대기` 상태를 반환한다. 이 응답으로 확인할 수 있는 것은 요청이 작업 목록에 들어갔다는 사실이다. 구축기가 이미 작업을 시작했는지, 검증을 통과했는지, 활성 색인이 바뀌었는지는 접수 성공만으로 알 수 없다. 접수 응답은 활성 색인 전환까지 걸리는 시간도 약속하지 않는다.

접수 번호를 받았다면 이후에는 그 번호로 작업 상태를 조회한다. 기존 활성 색인이 있는 자료집에서 접수 직후 예전 내용이 검색되더라도, 그것만으로 갱신이 실패했다고 판단할 수는 없다. 새 후보가 활성 판으로 전환되기 전까지는 기존 판을 사용하기 때문이다.

## 대기에서 완료까지 무엇을 기다리는가

정상적인 갱신은 `대기 → 구축 중 → 검증 중 → 반영 대기 → 완료` 순서로 진행한다.

| 상태 | 작업에서 일어나는 일 | 상태를 읽을 때의 기준 |
| --- | --- | --- |
| 대기 | 작업 기록은 저장되었지만 구축기가 아직 시작하지 않았다. | 접수는 끝났고 구축 시작을 기다리는 상태다. |
| 구축 중 | 선택한 원본으로 후보 색인을 만든다. | 후보는 활성 색인과 분리되어 있어 검색에 섞이지 않는다. |
| 검증 중 | 후보의 문서 수와 확인용 문서 조회를 검사한다. | 모든 검사를 통과해야 다음 상태로 간다. |
| 반영 대기 | 검증을 통과한 후보가 활성 판으로 전환되기를 기다린다. | 아직 전환 전이며, 기존 활성 판이 있다면 조회 API는 그 판을 사용한다. |
| 완료 | 활성 색인 판 변경과 작업 완료 기록이 함께 확정되었다. | 새 판으로의 전환이 확정된 상태다. |

검증에서는 후보의 문서 수가 원본과 일치하는지 확인한다. 또한 원본에 지정된 두 확인용 문서가 정확한 키로 조회되는지 검사한다. 이 검사를 모두 통과해야 `반영 대기`로 이동한다. 검증이 확인하는 범위는 문서 누락과 기본 조회이며, 검색 순위의 품질을 평가한 결과는 아니다.

`반영 대기`는 검증을 마쳤지만 검색에 사용할 판은 아직 바뀌지 않은 상태다. 조정기가 반영할 때 자료집의 활성 색인 판 변경과 해당 작업의 완료 기록을 하나의 변경으로 함께 확정한다. 따라서 검증 통과 기록이나 `반영 대기` 표시만 보고 새 내용이 이미 검색된다고 안내해서는 안 된다. 전환이 확정되었는지는 `완료` 상태로 판단한다.

작업의 종료 상태는 `완료`, `실패`, `중단`이다. `대기`, `구축 중`, `검증 중`, `반영 대기`는 모두 진행 중 상태이므로, 이 중 어느 상태에 있든 같은 자료집의 진행 중 작업 자리를 차지한다.

## 완료 상태와 실제 검색 결과를 함께 읽기

조회 API는 검색 요청을 시작할 때 활성 판을 한 번 정하고, 응답을 마칠 때까지 그 판을 유지한다. 검색 도중 활성 판이 바뀌어도 같은 요청 안에서 두 판의 결과를 섞지 않는다.

예를 들어 기존 활성 판으로 검색 요청을 시작한 뒤 `q203`의 반영이 확정되었다고 하자. 이 검색은 `q203`이 완료된 뒤 응답하더라도 기존 판의 결과를 반환할 수 있다. 반영이 확정된 뒤 시작한 검색은 새 판인 `i52`를 사용한다.

따라서 완료 상태를 확인한 시각과 검색 응답을 받은 시각만 비교해서는 부족하다. 완료 뒤 도착한 응답이 예전 내용이라면 검색이 전환 전에 시작했는지 살펴야 한다. 새 판의 결과를 확인하려면 전환이 확정된 뒤 시작한 검색의 결과를 읽어야 한다.

## 실패하거나 첫 갱신이 끝나지 않았을 때

구축 또는 검증을 더 진행할 수 없는 오류가 나면 작업은 `실패`로 끝난다. 상태 조회에는 오류가 발생한 단계와 이유가 남으며, 해당 후보는 활성 판으로 반영하지 않는다. 기존 활성 판이 있었다면 계속 사용하므로 갱신 실패가 기존 검색의 중단을 뜻하지는 않는다.

한 번도 반영을 마치지 않은 자료집에는 유지할 기존 활성 판이 없다. 첫 갱신이 진행 중이거나 `실패` 또는 `중단`으로 끝났다면 조회 API는 `색인 준비 안 됨`을 반환한다. 이는 검색을 정상적으로 수행했지만 결과가 없어 빈 목록을 반환하는 경우와 구분해야 한다.

## 중단 요청이 수락되어도 기다려야 하는 이유

중단 요청은 `대기`, `구축 중`, `검증 중`에만 받는다. `반영 대기`와 종료 상태인 `완료`, `실패`, `중단`에서는 거절한다. 수락 가능 여부는 사용자가 중단 버튼을 누른 시각이 아니라 조정기가 요청을 확인한 시점의 작업 상태로 판단한다. 버튼을 누를 때 `검증 중`이었더라도 조정기가 확인할 때 `반영 대기`라면 중단 요청은 거절된다.

중단 요청을 수락하면 먼저 중단 표시를 남긴다. 이후 조정기나 구축기가 그 표시를 확인하고 실제로 작업을 멈춘 뒤에야 상태를 `중단`으로 바꾼다. 그동안 상태 조회에는 직전의 진행 중 상태가 보일 수 있다. 중단 요청 수락과 작업의 중단 완료를 구분해야 하는 이유다.

중단 표시가 남은 후보는 검증을 마치더라도 `반영 대기`로 넘어가거나 활성화될 수 없다. 기존 활성 판이 있는 자료집은 계속 그 판으로 검색한다. 기존 활성 판이 없다면 앞서 설명한 `색인 준비 안 됨` 상태가 이어진다.

진행 중 작업 제한도 상태가 실제로 `중단`이 된 뒤에 풀린다. 중단 요청을 수락했더라도 아직 진행 중 상태라면 같은 자료집의 자리를 차지한다. 이때 새 갱신이나 재시도를 요청하면 `진행 중 작업 있음`과 진행 중인 작업의 접수 번호를 반환하며, 새 접수 번호는 만들지 않는다. 이 제한은 다른 자료집의 접수에는 영향을 주지 않는다.

## 재시도와 다른 원본으로 갱신하기

재시도는 `실패` 또는 `중단`으로 끝난 작업에만 요청할 수 있다. 재시도가 수락되면 기존 작업 기록은 그대로 두고 새 접수 번호를 발급해 `대기`부터 시작한다. 이전 후보나 문서별 진행 위치를 이어 쓰지 않고 처음부터 다시 구축하며, 사용하는 원본 번호는 기존 작업과 같다.

예를 들어 `r18`을 사용한 `q203`이 실패한 뒤 `r19`의 보관이 끝났더라도, `q203`을 재시도하면 다시 `r18`로 구축한다. `r19`를 반영하려면 진행 중 작업이 없는 때에 `r19`를 지정한 일반 갱신을 요청해야 한다. 같은 원본의 작업을 다시 수행할지, 다른 원본을 선택해 새로 갱신할지에 따라 요청을 구분한다.

기존 검색에 미치는 영향은 새 요청에서도 같다. 기존 활성 판이 있다면 재구축과 검증을 진행하는 동안 그 판을 사용하고, 새 후보의 반영이 확정되어야 활성 판이 바뀐다. 기존 활성 판이 없다면 재시도를 접수한 것만으로 검색이 준비되지는 않는다.

## 아직 확정되지 않은 운영 정책

현재 자료로 설명할 수 있는 재시도는 앞서 다룬 수동 재시도의 조건까지다. 다음 항목은 미확정이다.

- 대기 시간의 상한
- 자동 재시도 여부와 간격
- 실패하거나 중단한 후보의 보관 기간
- 반영 단계에서 발생한 오류의 복구 절차

이 항목에 대해서는 시간 보장이나 자동 복구를 전제로 판단할 수 없다. 접수 뒤의 진행 상황은 접수 번호로 확인하고, 완료된 갱신의 검색 결과는 활성 판 전환과 검색 요청 시작 시점을 함께 고려해 해석한다.

# 모래결 색인 갱신기: 접수부터 검색 반영까지

모래결 색인 갱신기는 자료집의 문서를 검색할 색인을 만드는 내부 서비스입니다. 원본 업로드는 별도 시스템이 맡고, 이 서비스는 보관된 원본을 골라 색인을 갱신합니다. 검색에는 원본 대신 색인을 사용하며, 현재 검색에 사용하도록 지정된 색인 판을 **활성 판**이라고 합니다. 이 문서에 나오는 서비스와 사례는 모두 가상입니다.

갱신을 이해하려면 접수 성공, 작업 완료, 검색 결과가 각각 무엇을 뜻하는지 구분해야 합니다. 접수 성공은 작업 기록이 저장됐다는 뜻이고, 완료는 활성 판 전환이 확정됐다는 뜻입니다. 개별 검색 결과는 그 검색 요청이 시작될 때의 활성 판을 따릅니다. 먼저 구성 요소와 식별자를 살펴본 뒤, 갱신 과정과 실패·중단·재시도 시의 판단 기준을 이어서 설명합니다.

## 구성 요소와 식별자로 갱신 흐름 이해하기

갱신 요청은 접수 API에서 시작합니다. 접수 API가 요청을 기록하면 작업 조정기가 작업을 구축기에 넘깁니다. 구축기는 선택한 원본으로 아직 검색에 쓰이지 않는 후보 색인을 만들고 검증합니다. 조정기는 검증을 통과한 후보를 활성 판으로 반영하고, 조회 API는 활성 판을 사용해 검색합니다.

이 흐름에서 자료집, 원본, 작업, 색인은 서로 다른 식별자를 사용합니다.

| 식별자 | 예시 | 가리키는 대상 |
| --- | --- | --- |
| 자료집 번호 | `C17` | 갱신할 자료집 |
| 원본 번호 | `r18` | 갱신에 사용할 원본 |
| 접수 번호 | `q203` | 접수한 작업. 작업 상태를 조회할 때 사용합니다. |
| 색인 판 번호 | `i52` | 구축한 색인의 판 |

예를 들어 자료집 `C17`의 원본 `r18`을 갱신해 달라는 요청 `q203`이 색인 `i52`를 만들 수 있습니다. `r18`, `q203`, `i52`의 숫자는 각각 별도 순서이므로 서로 비교해 진행률이나 최신 여부를 판단할 수 없습니다.

## 접수할 원본을 정하고 작업 기록 저장하기

원본 번호는 내용이 고정된 한 묶음을 가리킵니다. `q203`이 `r18`로 접수됐다면 이후 `r19`가 올라와도 작업은 끝까지 `r18`을 사용합니다. 조정기나 구축기가 진행 도중 최신 원본으로 대상을 바꾸는 기능은 없습니다.

접수 API는 자료집이 존재하는지, 지정한 원본의 보관이 완료됐는지 확인합니다. 둘 중 하나라도 충족하지 않으면 이유를 돌려주고 작업 기록을 만들지 않습니다. 두 조건을 모두 충족해도 같은 자료집에 진행 중인 작업이 있으면 새 작업을 받지 않습니다. 이때는 `진행 중 작업 있음`과 진행 중인 작업의 접수 번호를 반환하며, 새 접수 번호는 만들지 않습니다. 이 제한은 같은 자료집에 적용되며 다른 자료집의 접수에는 영향을 주지 않습니다.

접수에 성공하면 작업 기록의 저장이 끝난 뒤 새 접수 번호와 `대기` 상태를 반환합니다. 이 응답으로 확인할 수 있는 것은 요청이 작업 목록에 들어갔다는 사실입니다. 구축 시작, 검증 성공, 활성 판 변경까지 보장하는 응답은 아닙니다.

접수 뒤에는 응답으로 받은 접수 번호로 작업 상태를 확인합니다. 앞의 예에서는 `q203`을 사용하며, 자료집 번호 `C17`이나 색인 판 번호 `i52`로 대신 조회할 수 없습니다.

## 작업 상태를 따라 반영 시점 확인하기

정상적인 갱신은 다음 순서로 진행합니다.

**대기 → 구축 중 → 검증 중 → 반영 대기 → 완료**

`완료`, `실패`, `중단`은 종료 상태입니다. `대기`, `구축 중`, `검증 중`, `반영 대기`는 모두 진행 중 상태이므로, 접수 뒤 이 상태들이 보인다면 아직 작업이 끝나지 않은 것입니다.

### 대기부터 검증까지: 후보 색인 준비

`대기`는 작업 기록은 있지만 구축기가 아직 시작하지 않은 상태입니다. 구축기가 선택한 원본으로 후보 색인을 만들기 시작하면 `구축 중`이 됩니다. 후보는 활성 판과 분리해 보관하므로, 일부 문서만 만들어진 후보가 검색 결과에 섞이지 않습니다.

`검증 중`에는 후보의 문서 수가 원본과 일치하는지, 원본에 지정된 두 확인용 문서가 정확한 키로 조회되는지 검사합니다. 이 조건을 모두 충족해야 다음 상태로 넘어갑니다. 검증 범위는 문서 누락과 기본 조회이며, 검증을 통과했다고 해서 검색 순위의 품질까지 평가한 것은 아닙니다.

### 반영 대기부터 완료까지: 활성 판 전환

`반영 대기`는 검증을 통과한 후보가 활성 판으로 전환되기를 기다리는 상태입니다. 조정기가 전환하기 전까지 조회 API는 기존 활성 판을 사용합니다. 따라서 검증 통과 기록이나 `반영 대기` 표시만으로 새 내용이 이미 검색된다고 안내하면 안 됩니다.

반영할 때 조정기는 자료집의 활성 색인 판 변경과 해당 작업의 완료 기록을 하나의 변경으로 함께 확정합니다. **`완료` 상태는 활성 판 전환이 확정됐음을 뜻합니다.** 접수 성공 응답은 이 확정까지 걸리는 시간을 약속하지 않습니다.

## 완료 상태와 검색 결과를 함께 읽기

작업이 완료됐는지와 개별 검색 응답이 어느 판을 사용했는지는 검색 요청의 시작 시점으로 연결됩니다. 조회 API는 검색 요청을 시작할 때 활성 판을 한 번 정하고, 응답을 마칠 때까지 그 판을 유지합니다. 같은 검색 요청 안에서 두 판의 결과를 섞지 않습니다.

기존 활성 판이 있는 자료집에서 새 판으로 전환한다면, 전환 시점을 기준으로 검색 결과를 다음과 같이 읽습니다.

| 검색 요청을 시작한 시점 | 검색에 사용하는 판 |
| --- | --- |
| 전환이 확정되기 전 | 기존 활성 판. 전환 뒤에 응답하더라도 구버전 결과일 수 있습니다. |
| 전환이 확정된 뒤 | 새 활성 판 |

앞의 예에서 `q203`이 `i52`를 반영했다면, 그 전환이 확정된 뒤 시작한 검색은 `i52`를 사용합니다. 새 판으로 검색되는지 확인하려면 작업의 `완료` 상태를 확인한 뒤 새로운 검색 요청을 시작합니다. 검색 응답이 도착한 시각만으로 사용한 판을 판단하지 않도록 주의해야 합니다.

한 번도 반영을 마치지 않은 자료집에는 기존 활성 판이 없습니다. 첫 갱신이 진행 중이거나 `실패` 또는 `중단`으로 끝났다면 조회 API는 `색인 준비 안 됨`을 반환합니다. 이는 검색 결과가 없는 정상 응답인 빈 목록과 구분해야 합니다.

## 실패와 중단이 검색에 미치는 영향

### 실패하면 오류 단계와 이유 확인하기

구축 또는 검증을 더 진행할 수 없는 오류가 나면 작업은 `실패`로 끝납니다. 상태 조회에는 오류가 발생한 단계와 이유가 남으므로 접수 번호로 이를 확인합니다. 실패한 후보는 활성 판으로 반영하지 않습니다.

기존 활성 판이 있었다면 조회 API는 그 판을 계속 사용합니다. 따라서 갱신 실패가 기존 검색의 중단을 뜻하지는 않습니다. 첫 갱신이었다면 사용할 활성 판이 없으므로 앞서 설명한 `색인 준비 안 됨` 상태가 이어집니다.

### 중단 요청을 수락한 뒤에는 실제 종료 기다리기

중단 요청은 `대기`, `구축 중`, `검증 중`에만 받습니다. `반영 대기` 또는 종료 상태인 `완료`, `실패`, `중단`에서는 거절합니다. 수락 가능 여부를 판단하는 기준은 사용자가 중단 버튼을 누른 시각이 아니라 **조정기가 요청을 확인한 시점의 작업 상태**입니다. 버튼을 누를 때 `검증 중`이었더라도 조정기가 확인할 때 이미 `반영 대기`라면 중단 요청은 거절됩니다.

중단 요청을 수락하면 먼저 중단 표시를 남깁니다. 조정기나 구축기가 그 표시를 확인해 작업을 멈춘 뒤에야 상태가 `중단`으로 바뀝니다. 그동안 상태 조회에는 직전 진행 중 상태가 보일 수 있으므로, 중단 요청의 수락과 실제 중단 완료를 구분해야 합니다.

중단 표시가 남은 후보는 검증이 끝나더라도 `반영 대기`로 넘어가거나 활성화될 수 없습니다. 기존 활성 판이 있는 자료집은 그 판으로 검색을 계속합니다.

새 갱신이나 재시도를 시작하려면 작업 상태가 실제로 `중단`으로 바뀌었는지 확인해야 합니다. 한 자료집에는 진행 중 작업을 하나만 허용하므로, 중단 요청을 수락했어도 아직 `중단` 상태가 아니면 그 작업이 자리를 차지합니다. 이때 새 갱신이나 재시도를 요청하면 `진행 중 작업 있음`과 기존 접수 번호를 반환하고 새 번호는 만들지 않습니다.

## 재시도할 원본과 새로 반영할 원본 구분하기

재시도는 `실패` 또는 `중단`으로 끝난 작업에만 요청할 수 있습니다. 수락되면 기존 작업 기록은 그대로 두고, 새 접수 번호로 `대기`부터 시작합니다. 재시도 역시 새 작업이므로 같은 자료집에 다른 진행 중 작업이 있으면 받을 수 없습니다.

재시도는 기존 작업과 같은 원본 번호를 사용합니다. 이전 후보나 문서별 진행 위치를 이어 쓰지 않고, 선택된 원본으로 처음부터 다시 구축합니다. 새 접수 번호가 생겨도 사용할 원본이 바뀌는 것은 아닙니다.

예를 들어 `r18`을 사용한 `q203`이 실패한 뒤 `r19`의 보관이 완료됐다고 가정해 보겠습니다. `q203`을 재시도하면 새 작업도 `r18`을 사용합니다. `r19`를 반영하려면 진행 중 작업이 없는 때에 `r19`를 지정한 일반 갱신을 요청해야 합니다. 같은 원본을 다시 처리할지, 다른 원본을 반영할지에 따라 요청을 선택합니다.

## 아직 정해지지 않은 동작

위에서 설명한 재시도 조건은 수동으로 재시도를 요청할 때 적용됩니다. 다음 항목은 아직 확정되지 않았습니다.

- 대기 시간의 상한
- 자동 재시도의 유무와 간격

## 검토 방법과 해석 범위

원자료 작성자는 비교할 스킬과 기존 출력을 보지 않고 두 가상 사례를 준비했습니다. 생성기에는 사실 메모만 전달했고, 필수 보존 항목·확인 질문·정답은 전달하지 않았습니다. 여섯 출력은 각각 새 컨텍스트에서 한 번 생성한 뒤 원문과 해시를 고정했습니다.

각 사례는 별도의 새 컨텍스트 검토자가 익명 순서로 읽었습니다. 검토자는 원자료와 확인 질문은 받았지만 스킬·버전·조건 대응표와 정답은 받지 않았습니다. 원자료를 함께 대조했으므로 이 검토를 실제 독해·기억 시험으로 해석하지 않습니다. 작성과 검토에는 같은 세션 계열 모델을 사용했으며, 배포 모델 식별자와 샘플링 설정은 노출되지 않았습니다.

검토 기록과 조건 대응표는 아래에 공개합니다. 같은 문서의 사람 대상 읽기 시간·정확도·지연 회상·피로도는 측정하지 않았고, 모델이나 사례를 바꿨을 때의 효과도 이 여섯 출력만으로 추정하지 않습니다. 기존 v0.2.0의 20점 평가 결과는 수정하거나 이번 결과와 합산하지 않았습니다.
