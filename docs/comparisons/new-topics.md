# 느티나무 자료 가져오기 조사

다음 개발 단계에서는 입력 정보 보존과 판정 경로 연결을 먼저 진행할 것을 권합니다(판단). 운영 shadow 실행에서는 입력 420행을 모두 보류했습니다. 별도 연구·시험 자료의 기준 재현과 모델 비교 결과는 관측 집단과 실행 조건이 다르므로, 운영 처리 결과와 구분해 개발 순서를 판단해야 합니다.

## 운영 입력과 별도 기준 자료의 처리 결과

2026-10-28 운영 작업함 3개에서 관측한 입력은 420행으로, CSV 300행과 NDJSON 120행이었으며 XML 입력은 없었습니다. 당일 운영 shadow 실행에서는 필수 정책이 누락된 45행과 파서 검토가 필요한 375행을 모두 보류했고, 저장 DB에 반영한 건수는 0건이었습니다. 이전에 보고한 수용 12행은 연구 PC의 별도 개발 이미지에서 재생한 결과로, 이 운영 실행의 결과가 아닙니다.

2026-11-01에는 연구 PC와 시험 서버의 자료로 기준 40행을 구성했습니다. 이 가운데 조치가 필요한 행은 15행이었지만, 현행 엔진은 40행 모두 판정 불가로 처리했고 조치 필요 보고는 0행이었습니다. 이 기준 자료는 운영 입력 420행과 다른 집단이므로, 여기서 나온 결과를 현장 결과로 옮겨 해석하지 않습니다.

기준 작성에 사용한 동일 원문과 규칙을 격리 환경의 어댑터에 입력했을 때는 40행 모두 기준과 일치했습니다. 다만 독립 평가셋으로 정확도 기여를 측정한 결과는 없습니다. 따라서 이 결과는 동일 자료와 규칙으로 기준을 재현한 것으로 한정하며, 정확도 개선으로 일반화하지 않습니다.

## 문서 추출·지연·재순위 평가의 범위

문서 추출 비교는 구조화 12문항과 조건부 8문항을 대상으로 수행했습니다. 이 비교에서 LLM이 규칙보다 더 맞힌 답은 없었습니다.

2026-11-02 bench-b에서 측정한 변환기 단독 지연은 CPU 2스레드, 질의 1개씩 1,000회 실행한 조건에서 p50 31.2ms였고, 최대 RSS는 1.40GiB였습니다. GPU fp16 조건의 p50은 3.8ms였으나 GPU 반복 횟수는 자료에 없습니다. 이 값은 변환기 단독 지연 측정값이며, 정확도나 전체 작업 완료 시간을 나타내지 않습니다.

재순위 평가는 같은 후보 풀을 사용한 600질의를 대상으로 수행했습니다. 정답은 공개 사전 대응으로 기계 생성했으며, 사람이 검수하지 않았습니다. 입력 유형별 1순위 정답 건수는 다음과 같습니다.

| 입력 유형 | 질의 수 | 어휘 검색의 1순위 정답 | Pine-Reranker의 1순위 정답 |
| --- | ---: | ---: | ---: |
| 사전 제목 | 240질의 | 180건 | 195건 |
| 패키지명 | 360질의 | 244건 | 249건 |

이 평가에서는 통계적 동등성이나 유의성 검정을 수행하지 않았습니다. 위 건수는 해당 후보 풀과 기계 생성 정답을 사용한 결과이며, 실제 운영 정확도를 확인한 결과는 아닙니다.

## 수집기 점검 결과

2026-11-03 수집기 점검에서는 하루 결과가 12,000건을 넘으면 해당 구간을 건너뛰는 로직을 확인했습니다. 운영 수집기는 이 로직으로 6시간마다 실행 중입니다. 점검 대상 18,240건 중 18,200건은 이전 판이었고, 무작위로 확인한 60건의 본문 구성은 같았습니다.

# 구름 보관 서비스의 키 관리 설계 검토

관리 인력과 비용을 고려해 갈피 키 저장소를 첫 실증 후보로 권합니다(판단). 이는 실제 채택이나 설치가 완료됐다는 뜻이 아닙니다. 실증 범위는 아래 설정 근거와 미확인 항목을 바탕으로 결정해야 하며, 키 교체를 실행하려면 대상 계정의 운영 값 대조와 복구 백업 검증을 모두 마쳐야 합니다.

## 배치 설정과 인증 값의 연결 관계

운영 Compose는 외부 bridge 네트워크 `archive-net`을 요구합니다(`cloud-archive/ops/deploy/production/compose.yaml:148-156`, `cloud-archive/ops/.env.example:24-29`). 이 설정대로 배포하면 포털과 보관 API는 같은 Docker 호스트를 사용한다고 판단합니다. 실제 운영 호스트 배치는 조회하지 않았으므로, 이는 설정을 읽은 추론이며 실제 배치를 확인한 결과는 아닙니다.

인증 값은 포털의 전달 경로와 API의 검증 경로에 나뉘어 있습니다. 포털은 `PORTAL_TOKEN`을 읽어 API를 호출하고(`cloud-archive/apps/portal/src/clients/archive/client.ts:42-58`), API는 받은 토큰을 `SERVICE_TOKENS` 목록과 대조합니다(`cloud-archive/services/api/src/http/auth/token_controller.py:90-113`).

`ARCHIVE_DB_USER`와 `PORTAL_DB_USER`는 설정상 같은 업무용 계정으로 보입니다(`cloud-archive/ops/.env.example:71-79, 144-151`). 다만 운영 값을 대조하지 않았으므로 계정과 비밀값이 각각 동일한지는 미확인입니다. 동일 비밀값을 공유하는 서비스는 한쪽만 바꾸면 인증에 실패할 수 있습니다. 이 경우 저장소의 같은 항목을 참조하는 방안을 제안하며, 실증 전에 대상 값을 대조해야 합니다. 같은 항목을 참조하는 방식이 현재 구현됐다는 뜻은 아닙니다.

## 마운트와 백업에서 확인할 비밀 파일

점검 컨테이너는 `/srv/archive`를 `/host/archive`에 읽기 전용으로 마운트합니다(`cloud-archive/ops/deploy/production/compose.yaml:260-268`). 이 마운트는 호스트 파일을 읽을 수 있는 경로를 만든다고 판단합니다. 해당 경로의 비밀 파일은 컨테이너 읽기 권한에 따라 보일 수 있지만, 실제 열람과 노출 재현은 수행하지 않았습니다. 따라서 이 설정만으로 노출이 확정됐다고 볼 수는 없습니다.

백업 스크립트는 `.env`를 백업 디렉터리에 그대로 복사합니다(`cloud-archive/ops/scripts/archive-backup.sh:31-38`). 로컬에서 `.env-backups`라는 디렉터리 이름도 확인했지만 내용은 열지 않았습니다. 디렉터리 이름만으로 현재 평문 비밀값이 남아 있다고 확정할 수 없으므로, 백업 사본도 확인 대상에 포함해야 합니다.

## 갈피 키 저장소 실증과 키 교체 조건

아래 명령은 실증용으로 제시한 것으로, 변경 계획만 출력하고 키를 변경하지 않습니다. 실제 운영에서는 실행하지 않았습니다.

```bash
cd cloud-archive/ops
archive-keys rotate --dry-run
```

키 교체를 실행하기 전에는 다음 두 조건을 모두 충족해야 합니다. 어느 하나라도 끝나지 않았다면 키 교체를 중단하고 기존 키를 유지합니다.

- 대상 계정의 운영 값을 대조했습니다.
- 복구 백업을 검증했습니다.

교체 요청의 `accepted`는 접수 상태입니다. 이후 `rotation_state=committed`를 확인하고 연결 점검까지 성공해야 이전 키 폐기를 검토할 수 있습니다. 요청이 접수됐다는 이유만으로 이전 키를 폐기하지 않습니다.

## 업로드 재시도와 복구 검증의 한계

업로드 작업자는 실패 결과를 `pending_uploads/results`에 저장하고 90초마다 재시도하며, 최대 간격을 10,800초로 늘립니다(`cloud-archive/agents/uploader/src/jobs/result_retry_worker.py:120-134, 310-329`). 영구 실패는 재시도에서 제외합니다.

이 재시도 동작은 장기 장애 후 복구가 완료된다는 보장을 뜻하지 않습니다. 장기 장애 후 복구율과 재부팅 후 보존은 검증하지 않았습니다. 자동 교체 구현, 운영 적용 일정, 장기 장애의 복구 완료 보장은 아직 정해지지 않았습니다.
