# 한국어 개발 문서 작성

독자가 프로젝트를 이해하고 판단하거나 다음 행동을 할 수 있도록 씁니다. 사용자 요청과 프로젝트의 문서 관례를 먼저 따르고, 필요한 만큼만 설명합니다.

## 판단 순서

**사실·의미 보존 → 독자와 목적에 맞는 구조 → 문단의 흐름 → 자연스러운 문장 → 형식** 순서로 검토합니다. 더 짧거나 매끄러운 표현이 앞선 기준을 해치면 사용하지 않습니다.

## 향상 스킬과 함께 사용한다

- `humanize-korean`과 `stack-diagram`은 선택 사항입니다. 현재 환경에서 사용 가능한 스킬만 읽어 적용하고, 없으면 이 스킬의 기본 절차로 문서 작업을 마칩니다. 설치되어 있거나 실행했다고 추정하지 않습니다.
- 문장 교정·윤문이 필요하면 `humanize-korean`의 해당 모드만 적용합니다. 먼저 사실과 문서 구조를 정리한 뒤 문장을 다듬고, 수치·조건·부정·확실성·코드 식별자와 필요한 소제목·표·근거를 원자료와 다시 대조합니다. 구조 재배치와 문장별 작업표의 제약이 충돌하면 구조를 먼저 확정하고 그 결과를 교정 입력으로 삼습니다.
- 구성 요소·데이터 흐름·책임 관계를 그림으로 설명할 필요가 있으면 `stack-diagram`을 적용합니다. 원자료에 있는 요소와 연결만 사용하고, 도식과 본문의 이름·방향·조건이 일치하는지 확인합니다. 명령이나 표만으로 충분한 문서에는 도식을 추가하지 않습니다.
- 도식 스킬의 실행 환경이나 렌더링 도구가 없으면 사용 가능한 형식으로 설명을 완성하고, 생성하지 않은 이미지나 수행하지 않은 시각 검수를 완료했다고 쓰지 않습니다.
- 설치된 스킬을 매번 모두 실행하거나 교정을 반복하지 않습니다. 요청 범위와 필요한 작업에 맞춰 선택하고, 추가 스킬의 진단표·수정 이력은 사용자가 요구하거나 결과 판단에 필요할 때만 반환합니다.
- 문서 작성 요청을 외부 스킬 설치나 갤러리 게시 요청으로 확대하지 않습니다. 설치·공개 공유는 사용자가 요청한 범위에서만 수행합니다.

## 1. 요청과 자료를 파악한다

- 문서의 독자, 용도, 읽은 뒤 해야 할 행동을 요청과 자료에서 파악합니다. 내용을 처음 이해하려는지, 절차를 실행하려는지, 특정 항목을 찾아보려는지 구분합니다. 맥락으로 알 수 있는 내용을 매번 질문하지 않습니다.
- **표현 교정:** 제공된 사실과 범위를 유지하며 문장·문단을 다듬습니다. 요청하지 않은 기능이나 내용을 채우기 위해 조사 범위를 넓히지 않습니다.
- **구조 정리:** 기존 정보의 순서와 묶음을 바꿉니다. 중복을 줄이되 조건·예외·제약을 함께 옮깁니다.
- **새 문서 작성:** 제공된 자료와 필요한 코드·설정에서 근거를 확인하고 독자에게 필요한 내용을 구성합니다.
- 짧은 원문은 추가 압축을 목표로 삼지 않고 관계와 명료성을 다듬습니다. 길이를 제한하면 인사말·중복 설명·불필요한 형식부터 줄이고, 대상·판단 근거·검증 범위와 검토에 필요한 식별자·필드는 남깁니다.
- 작업을 막는 핵심 정보만 질문합니다. 그 밖의 미확인 내용은 빼거나 문서에 필요한 경우 확인 항목으로 남깁니다. 빈 항목 때문에 문서 전체 작성을 중단하지 않습니다.
- 문장 교정 기준이 필요하면 [교정과 유지 예시](references/before-after-guide.md)를 읽습니다. 새 문서를 쓰거나 구조를 바꾸면 [문서별 구성](references/document-types.md)에서 해당 종류만 읽습니다.
- 문서 세트 교정에서는 먼저 대상 Markdown 전체와 연결된 안내 문서를 목록으로 만듭니다. 각 파일을 현행 안내·명세, 검증 이력, 원본 보존용 사본으로 구분하고 모든 대상 파일을 끝까지 읽습니다. 일부 파일의 검색 결과를 전체 검토 결과로 보고하지 않습니다. 원본 보존용 사본은 수정하지 않고 제외 이유와 내용의 동일 여부를 기록합니다.
- 긴 설명을 구성하거나 읽기 피로·내용 연결·기억 부담을 다루면 [긴 글의 흐름과 이해](references/reading-flow.md)를 읽습니다. 짧은 문서에 긴 글용 안내와 요약을 억지로 추가하지 않습니다.

## 2. 사실과 의미를 고정한다

- 주체, 대상, 조건, 범위, 기본값, 예외, 부정, 의무의 강도, 확실성 수준을 유지합니다.
- 구체적으로 보이게 하려고 수치·버전·원인·기한·기능·경로·포트·측정 결과를 만들어 넣지 않습니다. 구체적인 정보가 없다는 이유만으로 표현을 단정하지 않습니다.
- 관찰한 사실, 원인에 대한 가설, 앞으로의 계획, 확인할 항목을 구분합니다. `권장한다`, `설정상 …로 보인다`, `확인했다`처럼 자료에 맞는 서술어로 상태를 드러냅니다. 문장마다 `(판단)`·`(추측)`을 붙이는 대신 근거와 확인 범위를 자연스럽게 연결합니다.
- 미확정이라는 결론과 그 이유를 함께 보존합니다. 원자료에 있는 관측 수단·환경의 한계를 지워 막연한 미확정으로 바꾸지 않고, 어떤 시스템·작업의 판단인지 구분하는 이름도 남깁니다. 자료에 없는 한계나 이름을 만들지는 않습니다.
- 현재 구현과 제안·목표 설계를 구분합니다. 예정된 배포를 완료로, 증상 완화를 원인 해결로, 미실행 테스트를 통과로 쓰지 않습니다.
- 한 버전에서 실행을 확인한 사실을 그 이상 버전 전체의 지원으로 확장하지 않습니다. 지원 범위와 실제 검증 환경은 각각 근거가 있을 때 적습니다.
- 코드 식별자, CLI 옵션, 경로, API 필드, 상태 코드, 로그 원문은 정확히 보존합니다. 설명을 한국어로 바꾸더라도 이 값은 임의로 번역하거나 교정하지 않습니다.
- 코드 블록의 명령과 출력, 환경변수, 포트, 수치, 날짜, SHA-256 해시, UUID도 원형을 유지합니다. 문장 속 기술 용어를 풀어 쓰는 규칙을 코드 식별자나 원시 기록에 적용하지 않습니다.
- 자료가 충돌하면 한쪽을 조용히 확정하지 않습니다. 확인 가능한 근거로 해결하거나 독자의 판단에 영향을 주는 차이를 표시합니다.
- 정확성 지침을 본문에서 되풀이하지 않습니다. 측정 대상·환경·표본·평가 방법을 필요한 위치에 명시하고, 이미 드러난 범위를 반복 해명하는 면책 문구는 줄입니다. 공통 제약은 한곳에 모으되, 결론의 신뢰도나 실행 여부를 바꾸는 미대조·미검증·중단 조건은 해당 판단 옆에도 남깁니다.
- 교정 중 사실 오류를 발견하면 근거가 있는 수정과 표현 수정을 구분해 짧게 알립니다. 출처를 확인하지 못한 의심만으로 내용을 바꾸지 않습니다.

## 3. 독자의 질문 순서로 구성한다

- 첫 문단에서 문서의 대상과 핵심 내용을 밝힙니다. README는 무엇을 하는 프로젝트인지, PR은 왜 무엇을 바꿨는지, 운영 절차는 언제 사용하는지부터 설명합니다.
- 긴 문서는 독자가 전체 관계를 먼저 잡도록 핵심 구분과 읽는 경로를 짧게 안내합니다. 제목과 소제목은 내용을 예측하게 쓰고, 이해에 필요한 결론을 호기심을 위해 숨기지 않습니다.
- 하나의 문단은 하나의 질문에 답하도록 묶습니다. 서로 다른 질문에 답하는 실험·환경·시점·설계 쟁점이 한 문단에 섞이면 나누고, 주장·이유·예시나 조건·동작·결과는 연결합니다. 긴 문단을 짧은 문장으로만 바꾸거나 빈 줄 없이 계속 이어 쓰지 않습니다.
- 새 개념을 설명할 때 필요한 전제와 역할을 가까이 둡니다. 원인·대조·조건의 관계와 지시 대상을 독자가 추측해야 한다면 드러내되, 이미 아는 기초 설명을 반복하지 않습니다.
- 개념과 예시, 판단과 근거, 명령과 실행 조건·확인 결과를 가까이 둡니다. 핵심 제약을 먼 절이나 접힌 상세 설명으로 보내지 않습니다.
- 제목은 내용을 찾는 데 쓰고, 매 문장마다 새 제목을 만들지 않습니다. 짧은 문서는 불필요한 개요·요약·결론을 반복하지 않습니다.
- 조사 요약이나 검토 절에서 독립된 발견이 3개 이상 이어지면 결론을 담은 번호형 소제목으로 나눕니다. 한 줄씩으로 충분한 항목은 번호 목록으로 묶고, 짧은 PR에 소제목을 억지로 늘리지 않습니다. 제목의 단정 강도도 본문과 맞춥니다.
- 통독 순서와 별개로 초기 상태의 예외, 오류·거절·중단 기준을 찾을 수 있게 합니다. 주제가 드러나는 제목·항목명에서 위치를 찾고, 관련 본문이나 표에서 조건·응답·예외를 함께 확인할 수 있게 합니다. 다른 절에서는 그 위치를 짧게 가리키되, 그 절의 판단·실행에 필요한 조건은 함께 남깁니다.
- 설명과 인과관계는 문단으로, 독립된 항목은 목록으로, 실행 순서는 번호로, 같은 기준의 비교는 표로 정리합니다.
- 표 뒤에는 표를 다시 나열하지 않고 필요한 해석·선택 이유만 잇습니다. 독립적으로 찾아 읽는 항목에는 `두 설정`, `위 조건` 대신 그 판단에 필요한 이름·조건을 짧게 명시합니다.
- 목차와 항목 수를 고정하지 않습니다. 독자에게 필요 없는 기능 목록, 디렉터리 나열, 이미지, 요약 표는 추가하지 않습니다.
- 문서 종류에 맞는 구조를 선택합니다. 원인을 모르는 버그에 확정 원인을 채우거나, 조사 중인 작업을 해결된 회고로 구성하지 않습니다.
- 사용자가 요청한 결과물을 먼저 제시합니다. 별도 요청이 없으면 편집 과정과 점검표 전체를 결과물에 붙이지 않습니다.
- 문체 교정·도식 스킬을 함께 적용해도 필요한 소제목, 비교 표, 근거 목록, 실행 조건의 배치를 유지합니다. 문장을 자연스럽게 잇는 작업 때문에 서로 다른 논점을 한 문단으로 합치지 않습니다.

### 현행 명세와 검증 이력의 경계를 유지합니다

- 아키텍처·API·운영 명세에는 현재 동작, 계약, 실행 조건과 제약을 씁니다. 특정 실행의 임시 경로, 일회성 PID·포트·컨테이너 ID, 단계별 수정 일지와 회귀 시험 로그는 별도 이력 문서에 보존하고 필요한 위치에 링크합니다. 현재 운영에 필요한 고정 경로·포트나 실패 조건까지 이력으로 옮기지 않습니다.
- 이력을 분리할 때 날짜·값·명령·검증 상태를 함께 보존합니다. 확인된 실행, 미실행, 차단, 미확인을 구별하며, 본문의 결론을 바꾸는 한계는 본문에도 남깁니다. 로그를 옮긴 사실을 새 검증이나 통과로 보고하지 않습니다.
- 제품 문서에는 에이전트 대화방 이름, 모델·추론 설정, 내부 승인 처리 표현을 남기지 않습니다. 검증 기록의 설명도 검토 범위·서버 검증 단계·실행 정책 제한 등 객관적인 조건으로 씁니다. 실제 오류 문자열이나 원시 로그를 보존해야 하면 원문 사본에 그대로 두고 설명에서 뜻을 풉니다.
- 구체적인 구분과 예시는 [현행 명세와 검증 이력](references/document-types.md#현행-명세와-검증-이력)을 따릅니다.

## 4. 한국어 문장과 흐름을 다듬는다

- 한 문장에 하나의 중심 내용을 담습니다. 조건과 결과, 순서가 한 흐름으로 쉽게 읽히면 함께 써도 됩니다. 서술어 개수만으로 나누지 않습니다.
- 긴 문장을 나눌 때는 각 동작에 적용되는 조건과 지시 대상을 확인합니다. 짧은 문장만 이어져 흐름이 끊기면 관련 문장을 연결합니다.
- 여러 중단·거절 조건을 `거나`로 길게 이으면 공통 조치를 먼저 밝히고 조건을 목록이나 대응 표로 나눕니다. 모두 충족해야 하는 조건과 하나만 해당해도 되는 조건을 구별합니다.
- `의`, `것`, `수 있다`, `기본적으로`를 금지어로 다루지 않습니다. 실제 관계·가능성·기능·권한·기본값을 나타내면 유지하거나 뜻이 같은 표현으로 바꿉니다.
- 불필요한 명사화와 대동사는 직접적인 동사로 바꿉니다. 조사를 줄인 결과 명사만 길게 이어지거나 의미가 모호해지면 동사형으로 풀어 씁니다.
- 목적이나 원인을 둘러 말하는 분열문, 명사 뒤에 붙은 기능동사, 겹조사와 추상적인 매개 표현을 찾아 주체와 동작을 직접 연결합니다. 원인을 필요조건으로 바꾸거나, 일회성 관찰을 실행 지시로 바꾸지 않습니다. [문장 구조 예시](references/before-after-guide.md#문장-구조를-직접-연결하기)에서 뜻이 유지되는 경우와 예외를 확인합니다.
- 능동형으로 주체가 더 분명해지면 바꿉니다. 상태나 결과가 중심인 자연스러운 피동은 유지하고, 알려지지 않은 주체를 새로 만들지 않습니다.
- 한 문서 안에서 같은 개념은 같은 용어로 부릅니다. 익숙한 기술 용어를 억지로 번역하지 말고, 독자에게 필요한 약어만 처음에 짧게 설명합니다.
- 개발 문서에서는 [직역 조어 치환 사전](references/before-after-guide.md#개발-용어의-직역-조어를-문맥에-맞게-풀기)의 모든 항목을 확인합니다. 표의 표현은 탐지 후보이며 무조건 바꾸는 금지어가 아닙니다. 저장 방식, 대상, 측정 단위, 정상 동작의 확인 여부가 달라지는 치환은 원자료로 조건을 확인한 뒤 적용합니다.
- 과장된 수식어와 내용 없는 도입을 줄입니다. 효과를 뒷받침하는 자료가 있으면 그 조건과 결과를 쓰고, 없으면 실제 동작이나 변경 내용까지만 설명합니다.
- 종결어미는 문서의 기능에 맞춰 일관되게 씁니다. 반복을 피하려고 설명·명령·권고의 강도를 임의로 바꾸지 않습니다.
- 같은 저장소의 독자 안내·명세 문서 세트는 본문과 완결된 문장형 표 셀을 경어체로 통일합니다. 현재 동작은 `~합니다`, 과거 검증은 `~했습니다`처럼 시제와 상태를 유지합니다. 짧은 명사구 표 셀, 코드 주석·출력 원문, 명시적으로 보존한 인용은 구분합니다. 자연스러운 변화를 주려고 평서형을 섞지 않습니다.
- 숫자 앞뒤의 공백이나 조사를 생략한 압축 표기는 [띄어쓰기 탐지 예시](references/before-after-guide.md#압축-표기의-공백과-단위를-확인하기)로 점검합니다. 고유 식별자와 버전 토큰은 그대로 두며, 빠진 단위는 원자료에서 대상이 확인될 때만 보충합니다.
- 연결어를 늘리기보다 문장 순서를 먼저 고칩니다. 같은 배경·이유·결론의 목적 없는 반복을 줄입니다. 전환점이나 실행 직전에는 다음 판단에 필요한 구분·조건을 짧게 다시 짚습니다. 그것으로 충분하면 이미 설명한 원리와 배경을 다시 풀지 않습니다. 여러 조건이나 예외가 필요하면 문장 수에 맞춰 지우지 않습니다. 모든 절에 요약을 붙이지 않습니다.

## 5. 실행 안내와 근거를 확인한다

- 설치·실행·빌드·테스트를 구분합니다. 관련 자료에서 작업 디렉터리, 패키지 관리자, 실제 스크립트, 필요한 설정을 확인합니다.
- 확인된 절차만 실행 순서로 설명합니다. 명령의 목적과 입력 위치가 불명확하면 짧게 덧붙입니다. 한 줄짜리 자명한 명령에 장황한 해설을 붙이지 않습니다.
- 독자가 바로 찾아 실행할 명령·예시에는 필요한 선행조건, 시간 한계의 시작 기준, 실패·중단 대응을 같은 실행 단위에 둡니다. 앞 절의 설명은 줄일 수 있지만 실행 여부를 바꾸는 조건을 링크나 기억에만 맡기지 않습니다.
- 독자가 성공 여부를 판단할 수 있도록 자료에 있는 출력·상태·확인 방법을 안내합니다. 알 수 없는 성공 메시지를 새로 만들지 않습니다.
- 시스템의 동작·판정 조건을 먼저 밝히고, 사람이 이를 조회·확인하는 절차를 구분해 씁니다. 확인하는 행동이 상태 변화의 원인이나 필수조건인 것처럼 인과를 추가하지 않습니다. 조회 자체가 상태를 바꾸는 동작이라면 자료에 있는 그 동작을 따릅니다.
- 예시와 실제 값을 구분합니다. 자리표시자는 의미를 표시하고, 실제 배포 문서에 예시 주소·없는 파일·빈 코드 블록이 남지 않게 합니다.
- API의 오류·거절 응답에는 자료에 있는 재요청 가능 시점·해제 조건을 함께 둡니다. 재시도·권한·중단·복구 동작이 자료에 없으면 일반적인 관례로 채우지 않습니다.
- 문서를 쓰기 위해 명령을 임의로 실행하지 않습니다. 실행 검증이 작업에 포함된 경우 그 범위에서 확인하고, 실제 실행 여부를 정확히 기록합니다.
- 외부 자료나 코드에서 보완한 중요한 사실은 출처로 추적할 수 있게 합니다. 긴 경로·여러 행 범위·저장소 목록은 문장 중간에서 빼고 해당 주장 바로 아래 근거 줄이나 표에 둡니다. 표시 이름을 줄여도 실제 경로·행 범위·주장과의 대응은 보존합니다. 실행할 명령의 경로·옵션은 명령 안에 남깁니다.

## 6. 검토한 뒤 교정을 마친다

1. **의미:** 대상·조건·예외·기본값·부정·가능성·계획·검증 상태와 판단 한계의 이유가 달라지거나 빠지지 않았는지 원자료와 대조합니다.
2. **구조:** 처음 읽는 사람이 대상과 목적을 알 수 있는지 확인합니다. 초기 상태·장애·예외·거절 조건을 급히 찾는 사람도 소제목과 표에서 해당 위치를 찾을 수 있는지 살핍니다. 짧은 본문에는 이를 위해 제목이나 표를 억지로 만들지 않습니다.
3. **흐름:** 숨이 차는 문장, 여러 논점이 뭉친 문단, 지나치게 끊긴 문장을 함께 고칩니다. 반복 면책과 긴 괄호·근거 경로를 정리하고, 필요한 조건이나 근거를 찾으려 앞 절로 돌아가야 하는 부분을 확인합니다.
4. **실용성:** 명령·오류 응답이 있는 절부터 읽어도 실행·재요청 여부를 판단할 수 있는지 확인합니다. 시간의 시작 기준, 중단 조건, 확인 결과를 점검하고 시스템 판정과 사람의 확인 절차를 구분합니다.
5. **형식:** 제목 단계, 목록 들여쓰기, 링크, 표, 코드 펜스를 확인합니다. 코드 블록을 포함한 Markdown 예시는 바깥 펜스를 더 길게 씁니다.
6. **전체 범위:** 문서 목록의 모든 파일에 검토 결과나 원본 보존 사유를 기록합니다. 번역 문체·직역 조어·세션 표현·압축 표기를 검색하고, 코드 밖 본문과 완결된 표 셀의 종결어미를 다시 확인합니다. 교정 전 예시나 정확한 원문 인용은 실제 본문 위반과 따로 집계합니다.
7. **참조와 보존:** 로컬 링크와 문서 간 앵커를 전수 검사합니다. 제목을 바꿀 때는 기존 앵커를 명시적인 HTML `id`로 남깁니다. 명령·식별자·값과 원본 사본을 수정 전 내용과 대조하고, 요청된 Python 검사·테스트와 공백 검사를 실제 실행한 결과만 보고합니다.

작성·교정 작업에서는 발견한 누락·분산·중복을 본문에서 고친 뒤, 수정의 영향을 받은 사실과 실행 단위를 다시 확인합니다. 고칠 수 있는 편집 문제를 아쉬운 점 목록으로 대신하지 않습니다. 원문을 보존해야 하면 이력을 유지하고 별도 교정본을 완성합니다.

요청한 길이와 수정 범위를 확인합니다. 자수 제한이 있으면 완성 본문을 실제로 세고 의미를 보존하며 조정합니다. 확인 자료의 부재나 미실시 검증은 근거에 맞게 남기되, 이를 이미 고칠 수 있는 문장·배치 문제와 구분합니다. 길이 감소를 이해 향상으로 간주하지 않습니다. 필요한 수정이 끝나면 불필요한 재작성이나 장식을 멈춥니다.
