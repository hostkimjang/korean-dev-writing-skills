# Harbor Intake 이벤트 수집 서비스 아키텍처

Harbor Intake는 HTTP로 제출된 이벤트를 Kafka에 수락한 뒤 PostgreSQL에 비동기로 저장하는 서비스다. API 요청을 처리하는 `collector-api`와 데이터베이스에 기록하는 `event-writer`가 분리되어 있다.

연동할 때 가장 먼저 구분해야 할 것은 **이벤트 수락과 저장 완료**다. `POST /v1/events`의 `202` 응답은 Kafka 발행이 확인되었다는 뜻이다. 이 시점에 `event_store` 저장까지 완료되었다고 판단해서는 안 된다. 현재는 `event_id`로 최종 저장 상태를 조회하는 API도 없다.

## 구성요소

| 구성요소 | 역할 | 처리 경계 |
| --- | --- | --- |
| `collector-api` | `POST /v1/events` 요청의 토큰과 스키마를 검증하고 이벤트를 Kafka에 발행한다. | Kafka 발행 확인 후 `202`와 `event_id`를 반환한다. 자체적으로 중복 요청을 제거하지 않는다. |
| Kafka 토픽 `telemetry.raw.v1` | API가 수락한 이벤트를 `event-writer`에 전달한다. | 이벤트가 토픽에 발행되었다는 사실과 데이터베이스에 저장되었다는 사실은 구분된다. |
| `event-writer` | Kafka에서 이벤트를 읽어 데이터베이스에 기록한다. | 데이터베이스 트랜잭션이 성공한 뒤 Kafka offset을 커밋한다. |
| PostgreSQL 데이터베이스 `event_store` | 이벤트를 저장하고 `event_id`의 유일성 제약을 적용한다. | 같은 `event_id`의 이벤트가 다시 처리되더라도 추가 행을 만들지 않는다. |

## 이벤트가 저장되는 흐름

### 1. 요청 검증

클라이언트는 `POST /v1/events`에 이벤트를 제출한다. `collector-api`는 토큰과 스키마를 확인한다.

- 토큰이 유효하지 않으면 `401`을 반환한다.
- 스키마에 오류가 있으면 `400`을 반환한다.
- 검증을 통과하면 `telemetry.raw.v1`에 이벤트를 발행한다.

### 2. Kafka 발행과 수락 응답

`collector-api`는 Kafka 발행이 확인된 뒤 `202`와 `event_id`를 반환한다. Kafka 발행에 실패하면 `503`을 반환한다.

`202`는 API의 수락 단계가 끝났음을 알리는 응답이다. 이후 저장은 `event-writer`가 처리한다. 따라서 클라이언트가 `202`를 받았어도 데이터베이스 장애 등으로 저장이 지연될 수 있다. 반대로 응답을 받은 시점에 이미 저장되었을 수도 있지만, 응답만으로 그 여부를 구분할 수는 없다.

### 3. 데이터베이스 기록

`event-writer`는 `telemetry.raw.v1`에서 이벤트를 읽고 `event_store`에 기록한다. 이때 `event_id`의 유일성 제약으로 중복을 확인한다. 이미 기록된 이벤트라면 추가 행을 만들지 않는다.

### 4. Kafka offset 커밋

`event-writer`는 데이터베이스 트랜잭션이 성공한 뒤 Kafka offset을 커밋한다. 이 순서는 데이터베이스에 기록하지 못한 이벤트를 다시 처리할 수 있게 한다.

다만 데이터베이스 기록과 offset 커밋 사이에는 중단될 수 있는 구간이 있다. 기록은 성공했지만 offset을 커밋하기 전에 worker가 종료되면 같은 이벤트를 다시 읽을 수 있다. 이 재처리에서 추가 행이 생기지 않도록 하는 장치가 `event_id` 유일성 제약이다.

## API 응답 해석

| 응답 | 의미 | 연동 시 처리 |
| --- | --- | --- |
| `400` | 이벤트 스키마에 오류가 있다. | 요청 내용을 수정해야 한다. 동일한 잘못된 요청을 반복해도 스키마 오류는 해소되지 않는다. |
| `401` | 토큰이 유효하지 않다. | 인증 정보를 확인하고 수정해야 한다. |
| `503` | Kafka 발행에 실패했다. | 같은 논리적 이벤트를 재시도할 때 같은 `event_id`를 사용해야 한다. |
| `202` + `event_id` | Kafka 발행이 확인되어 이벤트가 큐에 수락되었다. | 수락된 것으로 처리하되, 최종 저장 완료로 해석하지 않는다. |

`event_id`를 반환받았다는 사실만으로 저장 완료를 확인할 수는 없다. 현재 구현에는 해당 ID로 저장 상태를 조회하는 API가 없으므로, 연동 코드에서 조회 API를 통한 완료 확인을 전제로 삼아서는 안 된다.

## 중복 전달과 `event_id`

Harbor Intake의 전송 및 소비 과정에서는 같은 이벤트가 여러 번 전달될 수 있다. `collector-api`가 중복 요청을 제거하지 않기 때문에 클라이언트의 재시도 요청이 Kafka에 다시 발행될 수 있고, `event-writer`도 미커밋 이벤트를 다시 읽을 수 있다.

중복 처리는 저장 단계에서 이루어진다. `event_store`의 `event_id` 유일성 제약으로 중복임이 확인되면, `event-writer`는 이를 이미 기록된 이벤트로 취급하고 추가 행을 만들지 않는다. 따라서 **같은 논리적 이벤트를 재시도할 때 같은 `event_id`를 유지해야 한다.**

재시도마다 새 ID를 사용하면 기존 이벤트와 같은 ID라는 조건이 성립하지 않아 이 중복 방지 장치가 적용되지 않는다. 또한 유일성 제약은 ID를 기준으로 하므로, 서로 다른 논리적 이벤트에 같은 ID를 재사용해서도 안 된다.

이 동작이 보장하는 범위는 중복으로 인한 추가 저장 행의 방지다. 이벤트가 Kafka에 한 번만 발행되거나 `event-writer`에서 한 번만 처리된다는 뜻은 아니다.

## 장애 시 재처리 위치

재처리 주체는 장애가 발생한 단계에 따라 달라진다.

| 장애 상황 | 처리 상태 | 재처리 동작 |
| --- | --- | --- |
| Kafka 발행 실패 | `collector-api`가 `503`을 반환한다. | 클라이언트가 같은 논리적 이벤트를 다시 제출할 때 같은 `event_id`를 사용한다. |
| 데이터베이스 쓰기 실패 | 해당 이벤트의 offset을 커밋하지 않는다. | 데이터베이스가 회복되면 `event-writer`가 미커밋 이벤트를 다시 처리한다. |
| 데이터베이스 기록 후 offset 커밋 전에 worker 종료 | 데이터베이스에는 기록되었지만 Kafka offset은 커밋되지 않았을 수 있다. | 같은 이벤트를 다시 읽을 수 있다. `event_id` 유일성 제약으로 확인된 중복은 이미 기록된 이벤트로 처리해 추가 행을 만들지 않는다. |

이미 `202`를 받은 이벤트의 데이터베이스 쓰기에 실패하면, 서비스 내부의 재처리 지점은 `event-writer`다. 운영자는 API 수락 여부와 writer의 저장 처리 상태를 구분해서 확인해야 한다.

## 연동·운영 시 확인할 경계

### 수락 성공과 저장 성공을 따로 판단한다

`202` 응답이 정상적으로 반환되어도 저장이 지연되거나 실패할 수 있다. 이벤트가 보이지 않는다는 문의를 받으면 Kafka 발행 확인 여부, `event-writer`의 데이터베이스 기록 여부, offset 커밋 여부를 나누어 살펴봐야 한다. API 응답만으로 전체 저장 경로가 정상이라고 결론 내릴 수는 없다.

### 재처리가 발생했다는 사실만으로 중복 저장을 판단하지 않는다

데이터베이스 기록 후 offset 커밋 전에 중단된 경우에는 이미 저장된 이벤트도 다시 처리된다. 같은 이벤트를 다시 읽는 동작은 이 구조에서 가능한 복구 동작이다. 중복 전달 여부와 데이터베이스에 추가 행이 생겼는지를 구분해야 한다.

# Harbor Intake 아키텍처

Harbor Intake는 HTTP로 제출된 이벤트를 Kafka에 수락한 뒤 PostgreSQL에 저장하는 이벤트 수집 서비스입니다. 요청을 받는 `collector-api`와 데이터를 저장하는 `event-writer`가 분리되어 있어, API의 수락 응답과 데이터베이스 저장 완료 시점을 구분해야 합니다.

## 구성요소와 책임

| 구성요소 | 역할 |
| --- | --- |
| `collector-api` | 클라이언트가 제출한 이벤트의 토큰과 스키마를 확인하고 Kafka에 발행합니다. |
| Kafka 토픽 `telemetry.raw.v1` | `collector-api`가 발행한 이벤트를 `event-writer`가 읽는 토픽입니다. |
| `event-writer` | 토픽에서 이벤트를 읽어 데이터베이스에 기록하고, 트랜잭션이 성공한 뒤 Kafka offset을 커밋합니다. |
| PostgreSQL 데이터베이스 `event_store` | 이벤트를 저장합니다. `event_id`에 유일성 제약이 있으며, `event-writer`는 이 제약으로 중복 이벤트를 확인합니다. |

## 이벤트가 저장되는 흐름

1. 클라이언트가 `POST /v1/events`에 이벤트를 제출합니다.
2. `collector-api`가 토큰과 스키마를 확인합니다. 유효하지 않은 토큰에는 `401`, 스키마 오류에는 `400`을 반환합니다.
3. 검증을 통과한 이벤트를 `telemetry.raw.v1`에 발행합니다. Kafka 발행이 확인되면 `202`와 `event_id`를 반환하고, 발행에 실패하면 `503`을 반환합니다.
4. `event-writer`가 토픽에서 이벤트를 읽어 `event_store`에 기록합니다.
5. 데이터베이스 트랜잭션이 성공하면 `event-writer`가 Kafka offset을 커밋합니다.

**`202`는 이벤트가 Kafka 큐에 수락되었다는 뜻이며, `event_store`에 저장되었다는 뜻은 아닙니다.** 클라이언트가 응답을 받은 시점에는 데이터베이스 저장이 아직 완료되지 않았을 수 있습니다.

현재 구현에는 클라이언트가 `event_id`로 최종 저장 상태를 조회하는 API가 없습니다. 따라서 반환된 `event_id`를 사용해 저장 완료 여부를 API로 확인하는 흐름은 구성할 수 없습니다.

## 재시도와 중복 처리

클라이언트는 **같은 논리적 이벤트를 재시도할 때 같은 `event_id`를 사용해야 합니다.** `collector-api` 자체에서는 중복 요청을 제거하지 않으므로, 같은 이벤트가 Kafka에 여러 번 전달될 수 있습니다.

중복 처리는 저장 단계에서 이루어집니다. `event-writer`는 `event_store`의 `event_id` 유일성 제약으로 확인된 중복 이벤트를 이미 기록된 이벤트로 취급하며, 추가 행을 만들지 않습니다. 이 동작은 전송이나 소비 과정에서 중복 전달이 발생하지 않는다는 뜻은 아닙니다.

# Harbor Intake 이벤트 수집 아키텍처

Harbor Intake는 클라이언트가 제출한 이벤트를 Kafka로 수락한 뒤 PostgreSQL에 저장하는 내부 서비스입니다. 연동과 운영에서 먼저 구분해야 할 것은 **큐에 수락된 시점과 데이터베이스에 저장된 시점**입니다. API의 `202` 응답은 Kafka 발행이 확인되었다는 뜻이며, 최종 저장 완료를 뜻하지 않습니다.

이 문서는 현재 구현을 기준으로 구성요소의 역할, 이벤트 저장 흐름, 중복 처리와 장애 복구 동작을 설명합니다.[^implementation]

## 구성요소와 역할

| 구성요소 | 역할 |
| --- | --- |
| `collector-api` | `POST /v1/events` 요청의 토큰과 스키마를 확인하고, 이벤트를 Kafka에 발행합니다. 발행 결과에 따라 클라이언트에 응답합니다. |
| Kafka 토픽 `telemetry.raw.v1` | `collector-api`가 발행한 이벤트를 담고, `event-writer`가 읽는 대상입니다. |
| `event-writer` | 토픽에서 이벤트를 읽어 데이터베이스에 기록합니다. 데이터베이스 트랜잭션이 성공한 뒤 Kafka offset을 커밋합니다. |
| PostgreSQL 데이터베이스 `event_store` | 이벤트를 저장합니다. `event_id`에 유일성 제약을 두어 저장 중복을 판별합니다. |

요청 수락은 `collector-api`가, 데이터베이스 기록은 `event-writer`가 담당합니다. 두 구성요소 사이에서 이벤트를 전달하는 경계가 `telemetry.raw.v1`입니다.

## 이벤트가 저장될 때까지의 흐름

1. **클라이언트가 이벤트를 제출합니다.** `POST /v1/events` 요청을 받은 `collector-api`는 토큰과 스키마를 확인합니다. 유효하지 않은 토큰에는 `401`, 스키마 오류에는 `400`을 반환합니다.
2. **`collector-api`가 이벤트를 Kafka에 발행합니다.** `telemetry.raw.v1` 발행이 확인되면 `202`와 `event_id`를 반환합니다. 이 시점에 확인된 것은 큐의 수락입니다. Kafka 발행에 실패하면 `503`을 반환합니다.
3. **`event-writer`가 이벤트를 저장합니다.** 토픽에서 이벤트를 읽어 `event_store`에 기록하고, 데이터베이스 트랜잭션이 성공한 뒤 Kafka offset을 커밋합니다. 저장과 offset 커밋은 이 순서로 진행됩니다.

API 응답과 데이터베이스 저장은 서로 다른 단계이므로, 클라이언트는 `202`만으로 저장 완료 여부를 판단할 수 없습니다. **현재 구현에는 `event_id`로 최종 저장 상태를 조회하는 API도 없습니다.** 응답에 포함된 `event_id`를 받았다는 사실과 저장 상태를 확인할 수 있다는 사실을 구분해야 합니다.

## API 응답과 클라이언트 재시도

연동 시 응답은 다음 기준으로 해석합니다.

| HTTP 상태 코드 | 반환 조건 | 의미 |
| --- | --- | --- |
| `202` | Kafka 발행 확인 | 이벤트가 큐에 수락되었습니다. 응답에 `event_id`가 포함되며, 데이터베이스 저장 완료를 나타내지는 않습니다. |
| `400` | 스키마 오류 | 제출한 이벤트가 스키마 검사를 통과하지 못했습니다. |
| `401` | 유효하지 않은 토큰 | 제출한 토큰이 유효하지 않습니다. |
| `503` | Kafka 발행 실패 | `collector-api`가 이벤트 발행에 실패했습니다. |

클라이언트는 **같은 논리적 이벤트를 재시도할 때 같은 `event_id`를 사용해야 합니다.** 이 규칙은 `503`을 받은 뒤 재시도하는 경우에도 적용됩니다.

`collector-api` 자체는 중복 요청을 제거하지 않습니다. 따라서 같은 `event_id`로 재시도하더라도 API 단계에서 중복이 걸러진다고 가정해서는 안 됩니다. 저장 중복은 뒤에서 설명하는 `event_store`의 유일성 제약과 `event-writer`의 처리로 막습니다.

## 장애가 발생했을 때의 재처리

재처리 주체는 실패한 단계에 따라 달라집니다. Kafka 발행에 실패한 요청을 다시 제출하는 주체는 클라이언트입니다. Kafka에서 읽은 이벤트의 데이터베이스 기록에 실패했다면, `event-writer`가 offset을 커밋하지 않고 이후에 다시 처리합니다.

| 상황 | 처리 결과와 복구 동작 |
| --- | --- |
| Kafka 발행 실패 | `collector-api`가 `503`을 반환합니다. 클라이언트가 같은 논리적 이벤트를 재시도할 때는 같은 `event_id`를 사용해야 합니다. |
| 데이터베이스 쓰기 실패 | `event-writer`가 해당 이벤트의 offset을 커밋하지 않습니다. 데이터베이스가 회복되면 미커밋 이벤트를 다시 처리합니다. |
| 데이터베이스 기록 후, offset 커밋 전에 `event-writer` 종료 | 데이터베이스에는 이벤트가 기록되어 있어도 같은 이벤트를 다시 읽을 수 있습니다. 재처리 중 확인된 중복은 이미 기록된 이벤트로 취급합니다. |

마지막 경우처럼 저장에 성공한 이벤트도 다시 소비될 수 있습니다. 따라서 offset이 커밋되지 않았다는 사실만으로 데이터베이스에도 이벤트가 없다고 판단할 수는 없습니다.

## 중복 전달과 저장 중복 처리

Harbor Intake의 전송·소비 과정에는 중복 전달 가능성이 있습니다. 클라이언트 재시도뿐 아니라, 데이터베이스 기록과 offset 커밋 사이의 worker 종료도 재처리로 이어질 수 있기 때문입니다.

`event_store`에는 `event_id`의 유일성 제약이 있습니다. `event-writer`는 이 제약으로 확인된 중복 이벤트를 이미 기록된 이벤트로 취급하며, 추가 행을 만들지 않습니다. 같은 논리적 이벤트의 재시도에 같은 `event_id`를 유지해야 하는 이유도 이 저장 중복 처리와 연결됩니다.

운영 중 이벤트가 다시 전달되거나 소비되었다는 사실과 데이터베이스에 중복 행이 생겼다는 사실은 각각 구분해 확인해야 합니다. 중복 전달 가능성은 현재 처리 흐름에 포함되어 있고, 추가 행 생성을 막는 지점은 데이터베이스 기록 단계입니다.

# ADR-007: 이벤트 중복 판정 저장소

| 항목 | 내용 |
| --- | --- |
| 작성일 | 2026-10-15 |
| 상태 | 제안 |
| 검토 현황 | 데이터 및 운영 담당자 검토 미완료 |

## 배경과 요구사항

기존 이벤트 API는 PostgreSQL에 업무 이벤트를 저장한다. 같은 `tenant_id`에서 같은 `event_id`가 다시 제출되어도 업무 이벤트가 중복 생성되지 않아야 한다. 서로 다른 `tenant_id`에서는 같은 `event_id`를 사용할 수 있으므로, 중복 판정의 기준은 `(tenant_id, event_id)` 쌍이다.

중복 판정은 일반적인 요청 재시도뿐 아니라 과거 이벤트를 다시 가져오는 작업에도 적용된다. 따라서 중복 판정 기록의 보존 범위가 과거 이벤트에 대한 중복 방지 범위를 결정한다. 기록을 얼마나 오래 보관할지는 아직 정하지 않았다.

## 제안

PostgreSQL에 `event_receipts` 테이블을 만들고 `(tenant_id, event_id)`에 유일성 제약을 설정한다. 중복 판정 기록의 생성과 업무 이벤트의 생성은 같은 데이터베이스 트랜잭션에서 처리한다.

요청 처리 방식은 다음과 같다.

1. 요청의 `(tenant_id, event_id)`를 기준으로 중복 판정 기록을 생성한다.
2. 새 키라면 같은 트랜잭션에서 업무 이벤트를 생성하고 커밋한다.
3. 이미 존재하는 키라면 업무 이벤트를 새로 만들지 않는다.
4. 데이터베이스 작업이 실패하면 요청에 `503`을 반환한다. 클라이언트는 같은 `tenant_id`와 `event_id`로 재시도한다.

유일성 제약은 같은 키로 들어온 요청이 중복 판정 기록을 각각 생성하지 못하도록 한다. 같은 트랜잭션을 사용하면 중복 판정 기록과 업무 이벤트가 함께 커밋되거나 함께 롤백되므로, 두 기록의 정합성을 기존 데이터베이스 안에서 관리할 수 있다.

이 방식은 리뷰를 위한 제안이며, 아직 승인된 결정이 아니다.

## 이 선택을 제안하는 이유

핵심 요구사항은 중복 여부를 빠르게 조회하는 데 그치지 않고, 중복 판정 결과에 따라 업무 이벤트가 한 번만 생성되도록 하는 것이다. 업무 이벤트를 이미 PostgreSQL에 저장하고 있으므로, 중복 판정 기록도 같은 데이터베이스에 두면 기존 트랜잭션으로 두 작업을 묶을 수 있다.

또한 별도 Redis 운영을 추가하지 않아도 된다. 다만 운영 부담이 없어지는 것은 아니다. 중복 판정 기록을 저장하고 유지하는 부담이 기존 PostgreSQL에 추가된다.

과거 이벤트의 재반입도 중복 판정 대상이고 보존 기간이 미정인 상황에서는, TTL 만료에 따라 판정 기록이 사라지는 방식을 채택하기 전에 보장 범위를 먼저 정해야 한다. PostgreSQL 제안 역시 보존 정책이 필요하지만, 저장소 간 원자성을 위한 추가 설계 없이 현재의 업무 이벤트 저장 경로와 통합할 수 있다는 점을 우선한다.

| 업무 이벤트 생성과의 원자성 | 같은 PostgreSQL 트랜잭션으로 처리 | PostgreSQL의 업무 이벤트 생성과 원자적으로 처리하려면 추가 설계 필요 |
| 과거 이벤트 재반입 | 해당 중복 판정 기록이 보존되어 있어야 판정 가능 | TTL 만료 또는 키 유실 후에는 중복을 놓칠 수 있음 |

## 보장 범위와 감수할 점

### 중복 방지 범위는 기록 보존에 의존한다

제안한 방식은 중복 판정 기록이 남아 있는 `(tenant_id, event_id)`에 대해 업무 이벤트의 재생성을 막는다. 서로 다른 테넌트의 동일한 `event_id`는 별개의 키로 취급한다.

### PostgreSQL의 부하와 관리 비용이 늘어난다

중복 판정 기록을 위한 쓰기와 유일성 인덱스 관리가 추가된다. 기록을 계속 보관하면 관리해야 할 데이터도 늘어나므로, 보존 정책과 함께 정리 방법을 마련해야 한다. 정리 작업 자체가 데이터베이스에 미치는 영향도 성능 검증 계획에서 다룰 필요가 있다.

### 데이터베이스 실패 시 재시도가 필요하다

데이터베이스 작업이 실패하면 API는 `503`을 반환한다. 클라이언트가 재시도할 때 같은 `tenant_id`와 `event_id`를 유지해야 기존 요청과 동일한 키로 중복을 판정할 수 있다.

# ADR-007: 이벤트 중복 판정 저장소

- 작성일: 2026-10-15
- 상태: 제안
- 검토 상태: 데이터 및 운영 담당자의 검토가 아직 끝나지 않았다.

이벤트 API의 중복 판정 기록을 PostgreSQL의 `event_receipts` 테이블에 저장할 것을 제안한다. `(tenant_id, event_id)`에 유일성 제약을 두고, 중복 판정 기록과 업무 이벤트 생성을 같은 데이터베이스 트랜잭션에서 처리한다. 기존 PostgreSQL의 트랜잭션을 활용하고 별도 Redis 운영을 추가하지 않는 것이 제안의 주요 근거다.

## 배경과 요구사항

기존 이벤트 API는 PostgreSQL에 업무 이벤트를 저장한다. 같은 `tenant_id`에서 같은 `event_id`가 다시 제출되면 업무 이벤트가 중복 생성되지 않아야 한다. 서로 다른 `tenant_id`에서는 같은 `event_id`를 사용할 수 있으므로, 중복 판정 기준은 두 값의 조합이다.

과거 이벤트를 다시 가져오는 작업도 중복 판정 대상이다. 다만 중복 판정 기록을 얼마나 오래 보관할지는 아직 정하지 않았다. 보존 정책을 정할 때는 과거 이벤트의 재수집을 포함해 중복 방지가 필요한 범위를 함께 검토해야 한다.

## 제안하는 처리 방식

PostgreSQL에 `event_receipts` 테이블을 만들고 `(tenant_id, event_id)`에 유일성 제약을 설정한다. 요청은 다음 원칙에 따라 처리한다.

- 새 키에 대한 중복 판정 기록과 업무 이벤트 생성은 같은 데이터베이스 트랜잭션에서 처리한다.
- 중복 키가 이미 있으면 업무 이벤트를 새로 만들지 않는다.
- 데이터베이스 작업이 실패하면 요청에 `503`을 반환한다. 클라이언트는 같은 `tenant_id`와 `event_id`로 재시도한다.

## 검토한 대안과 제안 이유

비교한 대안은 Redis에 중복 판정 키를 저장하고 TTL을 두는 방식이다.

| 비교 기준 | PostgreSQL의 `event_receipts` 사용 | Redis에 키와 TTL 저장 |
| --- | --- | --- |
| 업무 이벤트 생성과의 원자적 처리 | 중복 판정 기록과 업무 이벤트 생성을 같은 데이터베이스 트랜잭션에서 처리한다. | PostgreSQL의 업무 이벤트 생성과 원자적으로 처리하려면 추가 설계가 필요하다. |
| 과거 이벤트의 중복 판정 | 중복 판정 기록의 보존 기간과 정리 정책을 정해야 한다. | TTL 만료 또는 키 유실 뒤 과거 이벤트가 다시 들어오면 중복을 놓칠 수 있다. |
| 저장소 운영 | 기존 PostgreSQL을 사용하므로 별도 Redis 운영을 추가하지 않는다. | Redis 운영이 추가된다. |

이 요구사항에서는 과거 이벤트를 다시 가져올 때도 중복을 판정해야 한다. Redis의 TTL 방식은 키가 사라진 뒤의 재수집을 다루어야 하고, PostgreSQL에 저장하는 업무 이벤트와의 원자적 처리도 별도로 설계해야 한다. PostgreSQL 제안은 기존 데이터베이스의 트랜잭션으로 두 기록을 함께 처리할 수 있다는 점에서 적합하다고 판단한다. 다만 이 방식도 보존 정책이 정해져야 중복 판정의 시간적 범위를 확정할 수 있다.

## 도입 시 감수할 점과 검증의 한계

`event_receipts`를 도입하면 기존 PostgreSQL의 쓰기와 인덱스 부하가 늘어난다. 중복 판정 기록을 정리하는 정책도 마련해야 한다. 기록 정리는 과거 이벤트의 중복 판정에 영향을 주므로, 보존 기간과 함께 결정해야 한다.

현재 부하에서 `event_receipts`의 추가 비용을 측정한 결과는 없다. 공식 지연 목표나 처리량 보장도 이번 ADR에서는 정하지 않았다. 따라서 성능 적합성은 검증이 필요한 사항으로 남는다.

# river-worker 적체 장애 대응 절차

`WorkerQueueAgeHigh` 알람이 발생하면 이 절차를 시작한다. 대상 worker는 `river-worker`, 작업 큐는 `river-events`다. 알람만으로 배포가 원인이라고 확정하지 말고, 적체 시작 시점과 배포 정보를 확인한 뒤 롤백 여부를 판단한다.

## 1. 현재 상태와 배포 정보를 확인한다

다음 명령을 실행하고 결과를 기록한다.

```bash
opsctl queue inspect river-events
opsctl worker status river-worker
opsctl deploy show river-worker
```

| 조회 대상 | 기록할 항목 | 확인 목적 |
| --- | --- | --- |
| `river-events` | `pending`, `oldest_age_seconds`, `consumer_state` | 현재 적체와 소비 상태를 파악하고, 복구 확인에 사용할 기준값을 남긴다. |
| `river-worker` | `state`, `inflight` | worker 상태와 처리 중인 작업을 확인한다. |
| 배포 | `current`, `stable`, `changed_at` | 현재 배포와 복구 대상 배포, 배포 변경 시각을 확인한다. |

`stable`은 온콜이 복구 대상으로 사용할 수 있도록 미리 지정된 배포다.

알람 발생 시각과 적체 시작 시각도 기록한다. 적체 시작 시각을 `changed_at`과 비교해 **현재 배포 직후부터 적체가 시작됐는지** 확인한다. 적체 시작 시각을 확인할 수 없다면 알람 발생 시각만으로 이를 대신 판단하지 않는다.

## 2. 롤백 조건을 판단한다

이 절차에서는 다음 두 조건을 **모두 확인한 경우에만** 롤백을 진행한다.

1. 현재 배포 직후부터 적체가 시작됐다.
2. `current`와 `stable`이 다르다.

두 조건을 모두 확인했으면 3단계로 진행한다. 배포와 적체 시작 시점의 관계를 확인할 수 없거나, 롤백 조건이 충족되지 않으면 롤백하지 않고 플랫폼 온콜에 이관한다. 이관할 내용은 6단계를 따른다.

## 3. worker를 일시정지하고 처리 중인 작업이 끝났는지 확인한다

롤백 전에 다음 명령을 실행하고, 일시정지 요청 시각을 기록한다.

```bash
opsctl worker pause river-worker
```

명령이 반환됐다는 것은 **일시정지 요청을 접수했다는 뜻**이다. 이미 처리 중인 작업은 계속 진행될 수 있으므로, 명령 반환만으로 롤백을 시작하지 않는다.

다음 명령으로 상태를 반복 확인한다.

```bash
opsctl worker status river-worker
```

| 관찰 결과 | 다음 행동 |
| --- | --- |
| `state=paused`이고 `inflight=0`이다. | 4단계에서 롤백한다. |
| 두 조건 중 하나라도 충족하지 않았고, 일시정지 요청 후 5분이 지나지 않았다. | 상태를 계속 확인한다. |
| 일시정지 요청 후 5분이 지나도 두 조건을 모두 충족하지 못했다. | 롤백하지 않고 플랫폼 온콜에 이관한다. |

## 4. stable로 롤백하고, 성공한 경우에만 소비를 재개한다

2단계의 롤백 조건을 충족했고, 3단계에서 `state=paused`와 `inflight=0`을 모두 확인한 다음 실행한다.

```bash
opsctl deploy rollback river-worker --to stable
```

명령 결과를 기록하고 성공 여부를 확인한다.

- **롤백 성공:** 아래 명령으로 소비를 재개하고, 재개 시각과 명령 결과를 기록한다.
- **롤백 실패:** 소비를 재개하지 않는다. worker를 일시정지한 상태로 두고 플랫폼 온콜에 이관한다.

```bash
opsctl worker resume river-worker
```

재개 명령을 실행했더라도 아직 복구로 판단하지 않는다. 5단계에서 실제 소비 상태와 적체 변화를 확인한다.

## 5. 소비 상태와 적체 변화를 확인해 복구를 판단한다

재개 후 다음 명령을 반복 실행하고, 각 조회 시각과 결과를 기록한다.

```bash
opsctl queue inspect river-events
```

복구로 판단하려면 다음 두 조건을 **모두 확인해야 한다.**

1. `consumer_state=running`이다.
2. 반복 조회 결과에서 `oldest_age_seconds`가 감소한다.

`consumer_state=running`만 확인되거나 `oldest_age_seconds`의 감소만 확인된 상태에서는 복구로 판단하지 않는다. 한 번의 조회만으로 감소 여부를 판단하지 말고, 앞선 조회값과 비교한다.

**재개 후 10분 동안 개선되지 않으면 반복 롤백하지 않고 플랫폼 온콜에 이관한다.** 이때 소비 상태와 `oldest_age_seconds`의 변화도 함께 전달한다.

다음 상황에서는 이 절차의 추가 조치를 중단하고 플랫폼 온콜에 이관한다.

| 이관 사유 | 중단 시 행동 |

# river-worker 적체 알람 대응 절차

`WorkerQueueAgeHigh` 알람이 발생하면 이 절차에 따라 `river-worker`와 작업 큐 `river-events`의 상태를 확인하고 롤백 여부를 판단합니다. 알람만으로 배포가 원인이라고 확정할 수는 없습니다.

이 절차에서는 **큐 삭제, offset 초기화, 처리 중인 작업 강제 종료를 하지 않습니다.** 작업 손실이나 중복을 일으킬 수 있어 별도 판단이 필요합니다.

## 1. 큐와 worker 상태 확인

다음 명령으로 현재 상태를 확인합니다.

```sh
opsctl queue inspect river-events
opsctl worker status river-worker
```

| 명령 | 확인할 항목 |
| --- | --- |
| `queue inspect` | `pending`, `oldest_age_seconds`, `consumer_state` |
| `worker status` | `state`, `inflight` |

명령 실행 결과와 알람 발생 시각을 기록하고, 적체가 시작된 시각을 확인합니다. `oldest_age_seconds`는 소비 재개 후 적체가 개선되는지 판단할 때도 확인합니다.

## 2. 롤백 조건 확인

배포 정보를 조회합니다.

```sh
opsctl deploy show river-worker
```

출력의 `current`, `stable`, `changed_at`을 확인합니다. `stable`은 온콜이 복구 대상으로 사용할 수 있도록 미리 지정된 배포입니다.

`changed_at`과 적체 시작 시각을 비교하고, **다음 두 조건을 모두 확인한 경우에만** 3단계로 진행합니다.

- 적체가 현재 배포 직후부터 시작됐습니다.
- `current`와 `stable`이 다릅니다.

조건을 확인할 수 없거나 `current`와 `stable`이 같으면 이 절차에서 롤백하지 않습니다. 관찰 결과를 정리해 플랫폼 온콜에 이관합니다.

## 3. 일시정지 요청 후 처리 중인 작업 확인

```sh

```

명령이 반환됐다는 것은 **일시정지 요청을 접수했다는 뜻**입니다. 이미 처리 중인 작업은 계속 진행될 수 있으므로, 반환만으로 롤백을 시작하지 않습니다.

다음 명령으로 상태를 다시 확인합니다.

```sh
opsctl worker status river-worker
```

**`state=paused`와 `inflight=0`을 모두 확인한 다음에만** 4단계로 진행합니다. 일시정지 요청 후 5분이 지나도 두 조건을 만족하지 못하면 롤백하지 않고 플랫폼 온콜에 이관합니다.

## 4. 롤백 성공 후 소비 재개

일시정지 상태와 처리 중인 작업이 없음을 모두 확인했다면 `stable`로 롤백합니다.

```sh
opsctl deploy rollback river-worker --to stable
```

롤백 명령의 결과를 확인합니다. **롤백에 실패하면 worker를 일시정지한 상태로 두고 플랫폼 온콜에 이관합니다.**

롤백 명령이 성공한 경우에만 소비를 재개하고 재개 시각을 기록합니다.

```sh
opsctl worker resume river-worker
```

## 5. 소비 재개 후 복구 여부 확인

소비를 재개한 뒤 큐 상태를 다시 조회합니다.

```sh
opsctl queue inspect river-events
```

큐 상태를 관찰하며 다음 두 조건을 모두 확인해야 복구로 판단합니다.

- `consumer_state=running`입니다.
- `oldest_age_seconds`가 감소합니다.

소비가 재개됐다는 사실만으로 복구로 판단하지 않습니다. **재개 후 10분 동안 개선되지 않으면 반복 롤백하지 말고 플랫폼 온콜에 이관합니다.**
