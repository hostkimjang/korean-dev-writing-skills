## 요약

중복 발송 이슈 #184의 원인을 조사하기 위해 발송 worker에 조건부 진단 로그를 추가합니다. 이번 PR에는 중복 발송을 해결하는 수정은 포함하지 않습니다.

## 문제와 원인 가설

운영 로그에서 같은 `job_id`가 두 번 발송된 사례를 확인했습니다. 로컬에서는 아직 안정적인 재현 방법을 찾지 못했습니다.

발송 작업이 길어져 작업 완료 전에 lock TTL이 만료되는 상황을 원인 후보로 보고 있습니다. 실제 중복 발송 원인인지는 확인하지 못했으며, 진단 로그로 추가 조사할 예정입니다.

## 변경 내용

`src/workers/deliver.ts`에 `delivery_retry_probe` 진단 로그를 추가합니다.

| 항목 | 내용 |
| --- | --- |
| 활성화 조건 | `DELIVERY_DIAG_ENABLED=true`일 때만 출력 |
| 설정 기본값 | `false` |
| 기록 필드 | `job_id`, `attempt`, `lock_owner` |
| 기록하지 않는 정보 | 수신자 주소, 메시지 본문 |

발송 순서, 재시도 횟수, lock TTL 값, 중복 방지 동작은 변경하지 않습니다.

## 검증 결과

`tests/workers/deliver-log.test.ts`에서 진단 로그의 조건부 출력과 기록 필드를 검증했습니다. 로컬에서 아래 명령을 실행했고 테스트가 통과했습니다.

```bash
pnpm exec vitest run tests/workers/deliver-log.test.ts
```

스테이징에서 실제 발송 경로는 검증하지 않았습니다. 진단 로그를 활성화했을 때 처리량과 지연이 얼마나 달라지는지도 측정하지 않았습니다.

## 배포 후 확인 계획

1. `DELIVERY_DIAG_ENABLED=true`로 진단 로그를 활성화합니다.
2. 중복 발송 사례의 `job_id`, `attempt`, `lock_owner`를 대조합니다.
3. 조사 결과를 #184에 정리한 뒤 수정 방향을 결정합니다.

## 리뷰 요청

- `job_id`, `attempt`, `lock_owner`가 중복 발송 사례를 구분하기에 충분한지 확인해 주세요.
- 수신자 주소나 메시지 본문이 진단 로그에 섞일 여지가 없는지 확인해 주세요.
