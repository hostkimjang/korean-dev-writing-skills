## 실제로 달라진 부분

### 1. 아키텍처: 핵심 설명을 찾을 위치가 줄었다

미적용과 기존 스킬 출력은 수락과 저장의 경계, 중복 전달과 중복 저장의 차이를 도입·구성요소 표·흐름·응답 표·장애 표·마지막 운영 절에서 거듭 설명한다. 두 평가자 모두 내용은 정확하다고 보면서, 이미 설명한 관계를 여러 절에서 다시 풀어 쓰는 부분을 지적했다.

예를 들어 미적용 문서는 마지막에 다음 제목과 설명을 다시 둔다.

> ### 재처리가 발생했다는 사실만으로 중복 저장을 판단하지 않는다
>
> 데이터베이스 기록 후 offset 커밋 전에 중단된 경우에는 이미 저장된 이벤트도 다시 처리된다. 같은 이벤트를 다시 읽는 동작은 이 구조에서 가능한 복구 동작이다. 중복 전달 여부와 데이터베이스에 추가 행이 생겼는지를 구분해야 한다.

개선본은 흐름 뒤에서 `202`의 의미를 설명하고, 재시도·중복 처리와 장애 표를 중심으로 구성한다. 중복 처리 절의 핵심 문장은 다음과 같다.

> `event-writer`는 `event_store`의 `event_id` 유일성 제약으로 확인된 중복 이벤트를 이미 기록된 이벤트로 취급하며, 추가 행을 만들지 않습니다. 이 동작은 전송이나 소비 과정에서 중복 전달이 발생하지 않는다는 뜻은 아닙니다.

점수 차이는 잘못된 문장을 고쳐서 생긴 것이 아니다. 정확한 내용을 여러 위치에서 반복하는 정도가 줄어든 데서 생겼다. 이 판단은 원자료 A3·A6·A7과 대조했다.

### 2. ADR: 비교와 비용 설명의 역할이 더 분명해졌다

기존 스킬 출력은 제안 이유, 대안 비교표, 도입 시 감수할 점에서 쓰기·인덱스 부하와 미측정 성능을 반복한다. 미적용 출력도 보존 정책이 중복 판정 범위를 정한다는 설명을 여러 절에서 상세히 되풀이한다.

개선본은 대안 비교표에서 원자성·과거 이벤트·운영 영향을 비교하고, 비용과 검증 상태는 다음 문단에 모은다.

> `event_receipts`를 추가하면 기존 데이터베이스의 쓰기와 인덱스 부하가 늘어난다. 중복 판정 기록을 정리하는 정책도 마련해야 한다. 현재 부하에서 이 테이블의 추가 비용을 측정한 결과는 없으며, 이번 ADR에서는 공식 지연 목표나 처리량 보장을 정하지 않았다.

제안 상태, 테넌트별 중복 범위, 같은 트랜잭션, 보존 기간 미정이라는 핵심은 세 조건 모두 지켰다. 개선본의 이점은 검토자가 같은 근거를 반복해서 읽는 부담을 줄였다는 데 있다. 원자료 D3·D7·D8을 기준으로 확인했다.

### 3. README: 간결해졌지만 미적용보다 높은 점수는 아니었다

기존 스킬 출력은 덮어쓰기 주의를 옵션 표, 저장 명령 앞, 마지막 주의사항에 세 번 둔다. 평가자 B는 마지막 반복을 군더더기로 봤지만, 평가자 A는 감점하지 않았다. 기존 스킬의 평균 19.5점에는 이 의견 차이가 그대로 반영되어 있다.

개선본은 덮어쓰기 조건을 옵션 표에 남기고, 로그 수준의 결과는 전체 조합 표 대신 짧은 설명과 예로 정리했다. 미적용과 개선본은 모두 20점이었다. 첫 사용자를 위한 여러 실행 예시가 필요한 상황에서는 더 긴 미적용 문서가 편할 수도 있으며, 이 실험은 그런 독자 선호까지 확인하지 않았다.

### 4. PR·운영 절차·문단 교정: 추가 효과를 확인하지 못했다

PR은 세 조건 모두 원인 가설과 확인된 사실, 진단 로그 추가와 문제 해결, 로컬 테스트와 미실시 스테이징 검증을 구분했다. 운영 절차도 일시정지 요청 접수와 실제 정지, 롤백 성공과 소비 재개, 재개와 복구 확인의 조건을 보존했다.

짧은 문단 교정의 대표 문장은 다음과 같다.

| 조건 | 실제 출력 일부 |
| --- | --- |
| 미적용 | `scan_limit=0`은 무제한 조회를 뜻하지 않으며, 이 값을 사용하면 `400 Bad Request`가 반환됩니다. |
| 기존 스킬 | `scan_limit=0`은 무제한 조회를 뜻하지 않습니다. 이 값을 지정하면 `400 Bad Request`를 반환합니다. |
| 개선 스킬 | `scan_limit=0`은 무제한 조회를 뜻하지 않으며, 이 값으로 요청하면 `400 Bad Request`가 반환됩니다. |

세 문장 모두 뜻이 정확하고 자연스럽다. 두 평가자 모두 이 사례의 세 출력에 같은 점수를 줬다. 스킬 적용 자체만으로 체감할 만큼 다른 문장이 나오는 것은 아니었다.

## 평가자 의견 차이

아키텍처와 ADR의 미적용·기존 출력에 대해 두 평가자는 총점 19점으로 같았지만 감점한 차원이 달랐다. A는 반복을 구조의 문제로, B는 문단의 자연스러움 문제로 보았다. 따라서 구조 점수와 자연스러움 점수의 작은 차이를 서로 독립된 효과로 해석하면 안 된다.

기존 스킬 README는 A가 20점, B가 19점을 줬다. 나머지 출력의 총점은 일치했다. 평가자를 합의시키거나 결과를 본 뒤 점수를 바꾸지 않았다. 모든 36개 채점 기록에는 다섯 차원의 근거가 있으며, 치명적 사실왜곡 표시는 모두 false다.

## 실행 방식과 한계

- **생성:** 여섯 사례 × 세 조건 = 18개 문서. 각 작업을 새 컨텍스트에서 한 번씩 생성했다. 같은 사례의 요청·독자·목적·원자료는 같고, 비교 대상 스킬만 달랐다. 결과를 보고 재생성하거나 문장을 고치지 않았다.
- **모델:** 세션에서 상속한 GPT-6 Astra Pro. 정확한 API 배포 ID와 temperature·샘플링 시드 등은 노출되지 않았다. Claude·Gemini에서 실행한 비교가 아니다.
- **미적용의 뜻:** 비교 대상 스킬을 추가하지 않은 조건이다. 플랫폼의 공통 글쓰기 지침은 여전히 적용되어 있어 기본 출력이 이미 좋았다.
- **자료:** 정리된 사실·조건을 충분히 제공한 합성 사례다. 실제 저장소에서 흩어진 근거를 찾아 문서를 작성하는 능력이나, 모호하고 충돌하는 메모를 해석하는 능력은 검증하지 않았다.
- **평가:** 같은 계열 모델의 평가자 두 개가 별도 컨텍스트에서 익명 문서를 평가했다. 서로 다른 모델이나 사람의 독립 평가가 아니므로 공통 취향과 편향이 남는다. 문체로 조건을 짐작할 가능성도 없앨 수 없다.
- **동결:** 사례 작성자는 스킬과 생성 결과를 보지 않고 기준을 만들었다. 기준 파일의 해시는 일부 초기 생성 작업이 시작된 뒤, 블라인드 평가 전 기록했다. 결과에 맞춰 기준을 바꾸지는 않았지만 외부에 시점을 증명한 사전 등록 실험은 아니다.
- **눈가림:** 각 출력에 무작위 ID를 붙이고 사례마다 표시 순서를 섞었다. 평가자에게는 원자료·평가 기준·익명 출력만 제공했다. 두 점수 파일을 저장하고 해시를 기록한 뒤 대응표를 공개했다.
- **적용 방식:** 스킬과 두 참고 파일을 명시적으로 읽도록 했다. 클라이언트가 설명만 보고 스킬을 자동 선택하는지, 설치 경로에서 자동으로 찾는지는 시험하지 않았다.
- **표본:** 각 조건·사례에서 한 번만 생성했다. 생성 편차·신뢰구간·통계적 유의성·장기 효과는 평가하지 않았다. 만점에 가까운 점수 분포도 미세한 차이의 해석을 제한한다.

현 단계에서 배포본에 적절한 설명은 “의미와 조건을 보존하며 한국어 개발 문서의 구조와 흐름을 정리하는 스킬”이다. “모든 모델에서 자연스러움이 크게 개선된다”거나 “사실 오류를 줄였음이 검증됐다”는 주장은 이 결과로 뒷받침되지 않는다.
