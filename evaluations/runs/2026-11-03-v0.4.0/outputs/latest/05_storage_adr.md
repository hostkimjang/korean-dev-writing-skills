# ADR-007: 이벤트 중복 판정 저장소

- 작성일: 2026-10-15
- 상태: 제안
- 검토 현황: 데이터·운영 담당자 검토 미완료

이벤트 API의 중복 판정 저장소로 PostgreSQL을 사용하는 방안을 제안한다. `event_receipts` 테이블의 `(tenant_id, event_id)`에 유일성 제약을 설정하고, 중복 판정 기록과 업무 이벤트 생성을 같은 데이터베이스 트랜잭션에서 처리한다.

## 배경과 요구 사항

기존 이벤트 API는 PostgreSQL에 업무 이벤트를 저장한다. 같은 `tenant_id`에서 같은 `event_id`를 다시 제출하더라도 업무 이벤트가 중복 생성되지 않아야 한다. 서로 다른 `tenant_id`에서는 같은 `event_id`를 사용할 수 있으므로, 중복 여부는 두 값을 함께 기준으로 삼아야 한다.

과거 이벤트를 다시 가져오는 작업도 중복 판정 대상이다. 다만 중복 판정 기록의 보관 기간은 아직 정하지 않았다. 보존 정책을 정하기 전에는 과거 이벤트의 중복 판정을 보장할 기간도 확정할 수 없다.

## 제안하는 처리 방식

`event_receipts`의 유일성 제약으로 중복 키를 판정한다. 새 중복 판정 기록과 업무 이벤트는 같은 트랜잭션에서 저장한다.

| 조건 | 제안하는 동작 |
| --- | --- |
| `(tenant_id, event_id)`가 아직 없음 | 중복 판정 기록과 업무 이벤트를 같은 데이터베이스 트랜잭션에서 생성한다. |
| 같은 `(tenant_id, event_id)`가 이미 있음 | 업무 이벤트를 새로 만들지 않는다. |
| 데이터베이스 작업 실패 | 요청에 `503`을 반환하고, 클라이언트는 같은 `tenant_id`와 `event_id`로 재시도한다. |

이 방식의 중복 판정은 보관 중인 기록을 기준으로 한다. 과거 이벤트 재반입까지 포함한 보장 범위는 아래 보존 정책 검토에서 정해야 한다.

## 검토한 대안과 선택 이유

비교한 대안은 Redis에 중복 판정 키를 저장하고 TTL을 두는 방식이다.

| 비교 기준 | PostgreSQL의 `event_receipts` | Redis 키와 TTL |
| --- | --- | --- |
| 과거 이벤트 재반입 | 보관 중인 기록으로 중복을 판정한다. 기록의 보관 기간과 정리 정책을 정해야 한다. | TTL이 만료되거나 키가 유실된 뒤 과거 이벤트가 다시 들어오면 중복을 놓칠 수 있다. |
| 업무 이벤트 생성과의 원자적 처리 | 중복 판정 기록과 업무 이벤트를 같은 데이터베이스 트랜잭션에서 처리한다. | PostgreSQL의 업무 이벤트 생성과 원자적으로 처리하려면 추가 설계가 필요하다. |
| 운영 구성 | 기존 데이터베이스를 사용하며 별도 Redis 운영을 추가하지 않는다. | 중복 판정 키를 저장할 Redis 운영이 필요하다. |

PostgreSQL을 제안하는 이유는 기존 데이터베이스의 트랜잭션을 활용해 중복 판정 기록과 업무 이벤트 생성을 함께 처리할 수 있기 때문이다. 별도 Redis 운영을 추가하지 않는다는 이점도 있다. 과거 이벤트 재반입이 중복 판정 대상이라는 요구를 고려하면, TTL 만료나 키 유실 이후의 중복 누락 가능성과 저장소 간 원자적 처리 설계는 Redis 대안을 선택할 때 해결해야 할 과제다.

## 도입 시 감수할 비용과 검증 한계

`event_receipts`를 추가하면 기존 PostgreSQL의 쓰기와 인덱스 부하가 늘어난다. 중복 판정 기록을 정리하는 정책도 마련해야 하며, 이 정책은 과거 이벤트를 어느 기간까지 중복 판정할 수 있는지와 함께 검토해야 한다.

현재 부하에서 `event_receipts`를 추가했을 때의 비용을 측정한 결과는 없다. 따라서 성능에 미치는 영향은 검증이 필요하다. 공식 지연 목표나 처리량 보장은 이번 ADR에서 정하지 않았다.

## 미결 사항과 승인 조건

| 미결 사항 | 리뷰에서 정할 내용 |
| --- | --- |
| 보존 정책 | 중복 판정 기록의 보관 기간과 정리 정책을 정한다. 과거 이벤트 재반입 요구를 고려해 중복 판정의 보장 범위를 명시한다. |
| 성능 검증 계획 | 현재 부하에서 `event_receipts`로 인해 늘어나는 쓰기·인덱스 부하와 추가 비용을 어떻게 측정할지 정한다. |
| 운영 책임 | 중복 판정 저장소 운영과 보존·정리 정책 실행의 책임 주체를 정한다. |

데이터와 운영 담당자의 검토를 마치고 보존 정책, 성능 검증 계획, 운영 시 책임 주체를 정한 뒤 제안의 승인 여부를 결정한다.
