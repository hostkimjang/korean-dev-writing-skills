# 단풍 로그 보관기 보관 정책

단풍 로그 보관기는 로그를 빠른 검색용 `hot`과 장기 보관용 `archive`에 나누어 보관합니다. 기본 검색은 `hot`만 조회하며, `archive`의 로그는 복원 요청 후 읽을 수 있습니다. 보관 기한을 판단할 때는 로그가 이동·삭제 **대상이 되는 시점**과 정리 작업이 실제 처리를 마친 시점을 구분해야 합니다.

## 보관 기간은 수신 시각부터 계산합니다

보관 기간의 기준은 서버가 UTC로 기록한 `received_at`입니다. 로그 본문의 `event_time`은 이벤트가 발생했다고 주장하는 시각이며, 보관 기간 계산에는 쓰지 않습니다. 로그를 조회해도 `received_at`이나 보관 기한은 바뀌지 않습니다.

현재 정책의 이동·삭제 조건은 다음과 같습니다. 두 기간 모두 같은 `received_at`에서 시작하며, 경계에 도달한 순간을 포함합니다.

| `received_at`부터 지난 기간 | 처리 대상 |
| --- | --- |
| 14일 이상 | `archive` 이동 대상 |
| 60일 이상 | 삭제 대상. 단, `legal_hold=true`이면 제외 |

따라서 삭제 기준은 수신 후 60일입니다. `archive`로 이동한 뒤 60일을 더 보관하는 방식으로 계산하면 안 됩니다.

각 로그에는 수신 시점에 적용된 `policy_revision`과 보관 기준이 저장됩니다. 정책을 바꾸면 변경 후 수신한 로그에만 새 정책이 적용됩니다. 기존 로그의 기한은 다시 계산하지 않으므로, 과거 로그를 확인할 때는 해당 로그에 저장된 정책과 기준을 함께 봐야 합니다.

## 경계 시각과 실제 처리 시각은 다릅니다

정리 작업은 매일 UTC 02:00에 시작합니다. 로그가 14일 또는 60일 경계에 도달해도 그 순간 이동이나 삭제가 끝나는 것은 아닙니다. 작업이 지연되면 처리도 뒤로 밀릴 수 있으며, 시작 일정만으로 완료 시각을 보장할 수 없습니다.

다음 로그를 예로 들면 보관 기간은 `event_time`보다 늦은 `received_at`에서 계산합니다.

| 항목 | UTC 시각 |
| --- | --- |
| `received_at` | `2026-10-01T10:00:00Z` |
| `event_time` | `2026-09-26T07:00:00Z` |
| 14일 경계 | `2026-10-15T10:00:00Z` |
| 60일 경계 | `2026-11-30T10:00:00Z` |

위의 두 경계는 각각 이동·삭제 대상이 되는 시각입니다. 실제 처리 완료 시각으로 안내해서는 안 되며, 삭제 여부를 판단할 때는 아래 보류 조건도 확인해야 합니다.

## `legal_hold=true`이면 삭제만 보류합니다

`legal_hold=true`인 로그는 삭제 대상에서 제외됩니다. 이 설정은 `archive` 이동을 막지 않으며, 보관 기간의 경과도 멈추지 않습니다.

보류를 해제했을 때 이미 수신 후 60일이 지났다면 다음 정리 작업의 삭제 대상이 됩니다. 해제 시각부터 보관 기간을 새로 세거나, 해제 직후 삭제가 완료된 것으로 판단하면 안 됩니다.

## 기본 검색에 없으면 보관 위치를 구분합니다

기본 검색에서 로그를 찾지 못했다는 사실만으로 삭제되었다고 판단할 수 없습니다. 기본 검색의 범위는 `hot`이므로, 검색 결과에 없어도 `archive`에 있는지는 별도로 확인해야 합니다. `archive`의 로그를 읽으려면 **보관 조회 화면**에서 복원을 요청합니다.

복원은 `archive` 원본의 임시 조회 복사본을 만드는 작업입니다. 복사본은 생성이 완료된 때부터 24시간 동안 사용할 수 있으며, 만료 시각은 화면의 `restore_expires_at`에서 확인합니다. 복원 요청 시각을 24시간의 시작점으로 삼으면 안 됩니다.

임시 복사본의 만료와 원본 로그의 삭제는 별개의 기준입니다. 복원해도 원본의 삭제 기한은 늘어나지 않으므로, 원본 기한은 수신 시각과 해당 로그의 보관 기준으로 판단합니다.

정리 작업 장애의 복구 절차, 복원 완료까지 걸리는 시간, 삭제된 로그의 복구 방법은 제공된 정보로 확인할 수 없습니다. 이 안내만으로 처리 완료 시간이나 삭제 후 복구를 약속하지 않습니다.

현재 정책의 처리 기준은 다음과 같습니다.

- **보관 이동:** `received_at`부터 14일 이상 지난 로그는 `archive` 이동 대상이 됩니다.
- **삭제:** 같은 `received_at`부터 60일 이상 지난 로그는 삭제 대상이 됩니다. 삭제 기한은 `archive`로 이동한 날을 기준으로 다시 계산하지 않습니다.

두 기준 모두 경계 시각을 포함합니다. 수신 후 정확히 14일이 되는 시각부터 이동 기준을, 정확히 60일이 되는 시각부터 삭제 기준을 충족합니다.

### 현재 정책을 적용한 시각 예시

다음 로그는 사건 발생 시각보다 서버 수신 시각이 늦습니다. 이동·삭제 기준은 서버 수신 시각에 맞춰 계산합니다.

| 항목 | UTC 시각 |
| --- | --- |
| 사건 발생 시각 `event_time` | `2026-09-26T07:00:00Z` |
| 서버 수신 시각 `received_at` | `2026-10-01T10:00:00Z` |
| 14일 경과: 이동 기준 충족 | `2026-10-15T10:00:00Z` |
| 60일 경과: 삭제 기준 충족 | `2026-11-30T10:00:00Z` |

표의 14일·60일 경과 시각은 처리 대상이 되는 기준입니다. 실제 이동이나 삭제가 완료되는 시각을 뜻하지는 않습니다.

## 정책 변경은 변경 이후 수신 로그에 적용

각 로그에는 수신 당시의 `policy_revision`과 보관 기준이 함께 저장됩니다. 정책이 바뀌면 변경 이후에 수신한 로그부터 새 정책을 적용하며, 기존 로그의 기한은 다시 계산하지 않습니다. 따라서 기존 로그의 보관 기한을 확인할 때는 그 로그에 저장된 보관 기준을 사용합니다.

## 이동·삭제는 매일 UTC 02:00 정리 작업에서 처리

정리 작업은 매일 UTC 02:00에 실행되어 보관 이동과 삭제를 처리합니다. 로그가 14일 또는 60일 기준을 충족하는 순간에 처리가 완료되는 것은 아닙니다. 작업이 지연되면 처리도 뒤로 미뤄질 수 있으며, 완료 시각은 보장되지 않습니다.

### `legal_hold=true`이면 삭제 제외

`legal_hold=true`인 로그는 삭제 대상에서 제외됩니다. 다만 `archive` 이동과 보관 기간의 경과는 계속됩니다. 보류 상태에서도 수신 후 60일 기준 시각은 그대로 유지됩니다.

보류를 해제했을 때 이미 `received_at`부터 60일 이상 지났다면 해당 로그는 다음 정리 작업의 삭제 대상이 됩니다. 보류 해제로 보관 기간이 새로 시작되지는 않습니다.

## 기본 검색에서 보이지 않는 로그 조회

기본 검색은 `hot`만 조회하므로 검색 결과에 로그가 없다는 사실만으로 `archive`에도 없거나 이미 삭제됐다고 판단할 수 없습니다. `archive`의 로그를 확인하려면 **보관 조회 화면**에서 대상 로그의 복원을 요청합니다.

복원은 `archive` 원본을 바탕으로 조회용 임시 사본을 만드는 작업입니다. 임시 사본은 **생성 완료 시점부터 24시간** 동안 유지되며, 만료 시각은 화면의 `restore_expires_at`에서 확인합니다.

임시 사본의 만료는 원본 삭제를 뜻하지 않습니다. 복원을 요청해도 원본의 보관 기간은 연장되지 않으므로, 원본의 삭제 대상 여부는 해당 로그의 보관 기준과 `legal_hold` 상태로 판단합니다.

## 설정 이름과 허용값

| 설정 | CLI | 환경 변수 | YAML | 기본값·허용값 |
| --- | --- | --- | --- | --- |

`WORKER_LOG_LEVEL`은 설정하지 않았고, CLI에도 `--log-level`을 지정하지 않은 상태에서 다음 명령을 실행합니다. `WORKER_TIMEOUT_MS=9000`은 이 명령에만 적용됩니다.

```bash
WORKER_TIMEOUT_MS=9000 breeze-worker --timeout-ms 12000 config inspect --show-origin
```

| 설정 | 적용값 | 출처 |
| --- | --- | --- |
| `timeout_ms` | `12000` ms | `cli` |
| `log_level` | `warn` | `file` |

## 선택값 검증 오류와 빈 환경 변수

값을 선택한 뒤에는 **선택된 값만 검증**합니다. 선택값이 유효하지 않으면 시작 오류가 발생하며, 우선순위가 낮은 값으로 대체하지 않습니다. 반대로 유효한 상위 값이 선택됐다면 하위 값이 유효하지 않아도 해당 설정의 시작 오류를 일으키지 않습니다.

환경 변수를 설정하지 않은 상태와 빈 문자열로 설정한 상태는 다릅니다. 빈 환경 변수도 존재하는 값이므로 상위 CLI 값이 없으면 선택되며, 검증에서 오류가 납니다.

예를 들어 CLI에 `--timeout-ms`가 없고 `WORKER_TIMEOUT_MS`가 빈 문자열이면, YAML의 `timeout_ms`가 유효해도 오류가 발생합니다. 검증 오류가 나면 선택된 출처의 값과 허용값을 확인합니다.
