# 한국어 개발 문서 작성

독자가 프로젝트를 이해하고 판단하거나 다음 행동을 할 수 있도록 쓴다. 사용자 요청과 프로젝트의 문서 관례를 먼저 따르고, 필요한 만큼만 설명한다.

## 판단 순서

**사실·의미 보존 → 독자와 목적에 맞는 구조 → 문단의 흐름 → 자연스러운 문장 → 형식** 순서로 검토한다. 더 짧거나 매끄러운 표현이 앞선 기준을 해치면 사용하지 않는다.

## 1. 요청과 자료를 파악한다

- 문서의 독자, 용도, 읽은 뒤 해야 할 행동을 요청과 자료에서 파악한다. 내용을 처음 이해하려는지, 절차를 실행하려는지, 특정 항목을 찾아보려는지 구분한다. 맥락으로 알 수 있는 내용을 매번 질문하지 않는다.
- **표현 교정:** 제공된 사실과 범위를 유지하며 문장·문단을 다듬는다. 요청하지 않은 기능이나 내용을 채우기 위해 조사 범위를 넓히지 않는다.
- **구조 정리:** 기존 정보의 순서와 묶음을 바꾼다. 중복을 줄이되 조건·예외·제약을 함께 옮긴다.
- **새 문서 작성:** 제공된 자료와 필요한 코드·설정에서 근거를 확인하고 독자에게 필요한 내용을 구성한다.
- 짧은 원문은 추가 압축을 목표로 삼지 않고 관계와 명료성을 다듬는다. 사용자가 길이를 제한하면 인사말·중복 설명부터 줄이고, 대상과 판단에 필요한 조건·근거는 남긴다.
- 작업을 막는 핵심 정보만 질문한다. 그 밖의 미확인 내용은 빼거나 문서에 필요한 경우 확인 항목으로 남긴다. 빈 항목 때문에 문서 전체 작성을 중단하지 않는다.
- 문장 교정 기준이 필요하면 [교정과 유지 예시](references/before-after-guide.md)를 읽는다. 새 문서를 쓰거나 구조를 바꾸면 [문서별 구성](references/document-types.md)에서 해당 종류만 읽는다.
- 긴 설명을 구성하거나 읽기 피로·내용 연결·기억 부담을 다루면 [긴 글의 흐름과 이해](references/reading-flow.md)를 읽는다. 짧은 문서에 긴 글용 안내와 요약을 억지로 추가하지 않는다.

## 2. 사실과 의미를 고정한다

- 주체, 대상, 조건, 범위, 기본값, 예외, 부정, 의무의 강도, 확실성 수준을 유지한다.
- 구체적으로 보이게 하려고 수치·버전·원인·기한·기능·경로·포트·측정 결과를 만들어 넣지 않는다. 구체적인 정보가 없다는 이유만으로 표현을 단정하지 않는다.
- 관찰한 사실, 원인에 대한 가설, 앞으로의 계획, 확인할 항목을 구분한다. 가설에는 자료에 있는 근거와 한계를 붙인다.
- 미확정이라는 결론과 그 이유를 함께 보존한다. 원자료에 있는 관측 수단·환경의 한계를 지워 막연한 미확정으로 바꾸지 않고, 어떤 시스템·작업의 판단인지 구분하는 이름도 남긴다. 자료에 없는 한계나 이름을 만들지는 않는다.
- 현재 구현과 제안·목표 설계를 구분한다. 예정된 배포를 완료로, 증상 완화를 원인 해결로, 미실행 테스트를 통과로 쓰지 않는다.
- 한 버전에서의 실행 확인을 그 이상 버전 전체의 지원으로 확장하지 않는다. 지원 범위와 실제 검증 환경은 각각 근거가 있을 때 적는다.
- 코드 식별자, CLI 옵션, 경로, API 필드, 상태 코드, 로그 원문은 정확히 보존한다. 설명을 한국어로 바꾸더라도 이 값은 임의로 번역하거나 교정하지 않는다.
- 자료가 충돌하면 한쪽을 조용히 확정하지 않는다. 확인 가능한 근거로 해결하거나 독자의 판단에 영향을 주는 차이를 표시한다.
- 교정 중 사실 오류를 발견하면 근거가 있는 수정과 표현 수정을 구분해 짧게 알린다. 출처를 확인하지 못한 의심만으로 내용을 바꾸지 않는다.

## 3. 독자의 질문 순서로 구성한다

- 첫 문단에서 문서의 대상과 핵심 내용을 밝힌다. README는 무엇을 하는 프로젝트인지, PR은 왜 무엇을 바꿨는지, 운영 절차는 언제 사용하는지부터 설명한다.
- 긴 문서는 독자가 전체 관계를 먼저 잡도록 핵심 구분과 읽는 경로를 짧게 안내한다. 제목과 소제목은 내용을 예측하게 쓰고, 이해에 필요한 결론을 호기심을 위해 숨기지 않는다.
- 하나의 문단은 하나의 질문에 답하도록 묶는다. 주장·이유·예시나 조건·동작·결과를 독자가 따라갈 순서로 연결한다.
- 새 개념을 설명할 때 필요한 전제와 역할을 가까이 둔다. 원인·대조·조건의 관계와 지시 대상을 독자가 추측해야 한다면 드러내되, 이미 아는 기초 설명을 반복하지 않는다.
- 개념과 예시, 판단과 근거, 명령과 실행 조건·확인 결과를 가까이 둔다. 핵심 제약을 먼 절이나 접힌 상세 설명으로 보내지 않는다.
- 제목은 내용을 찾는 데 쓰고, 매 문장마다 새 제목을 만들지 않는다. 짧은 문서는 불필요한 개요·요약·결론을 반복하지 않는다.
- 통독 순서와 별개로 초기 상태의 예외, 오류·거절·중단 기준을 찾을 수 있게 한다. 주제가 드러나는 제목·항목명에서 위치를 찾고, 관련 본문이나 표에서 조건·응답·예외를 함께 확인할 수 있게 한다. 다른 절에서는 그 위치를 짧게 가리키되, 그 절의 판단·실행에 필요한 조건은 함께 남긴다.
- 설명과 인과관계는 문단으로, 독립된 항목은 목록으로, 실행 순서는 번호로, 같은 기준의 비교는 표로 정리한다.
- 목차와 항목 수를 고정하지 않는다. 독자에게 필요 없는 기능 목록, 디렉터리 나열, 이미지, 요약 표는 추가하지 않는다.
- 문서 종류에 맞는 구조를 선택한다. 원인을 모르는 버그에 확정 원인을 채우거나, 조사 중인 작업을 해결된 회고로 구성하지 않는다.
- 사용자가 요청한 결과물을 먼저 제시한다. 별도 요청이 없으면 편집 과정과 점검표 전체를 결과물에 붙이지 않는다.

## 4. 한국어 문장과 흐름을 다듬는다

- 한 문장에 하나의 중심 내용을 담는다. 조건과 결과, 순서가 한 흐름으로 쉽게 읽히면 함께 써도 된다. 서술어 개수만으로 나누지 않는다.
- 긴 문장을 나눌 때는 각 동작에 적용되는 조건과 지시 대상을 확인한다. 짧은 문장만 이어져 흐름이 끊기면 관련 문장을 연결한다.
- `의`, `것`, `수 있다`, `기본적으로`를 금지어로 다루지 않는다. 실제 관계·가능성·기능·권한·기본값을 나타내면 유지하거나 뜻이 같은 표현으로 바꾼다.
- 불필요한 명사화와 대동사는 직접적인 동사로 바꾼다. 조사를 줄인 결과 명사만 길게 이어지거나 의미가 모호해지면 동사형으로 풀어 쓴다.
- 능동형으로 주체가 더 분명해지면 바꾼다. 상태나 결과가 중심인 자연스러운 피동은 유지하고, 알려지지 않은 주체를 새로 만들지 않는다.
- 한 문서 안에서 같은 개념은 같은 용어로 부른다. 익숙한 기술 용어를 억지로 번역하지 말고, 독자에게 필요한 약어만 처음에 짧게 설명한다.
- 과장된 수식어와 내용 없는 도입을 줄인다. 효과를 뒷받침하는 자료가 있으면 그 조건과 결과를 쓰고, 없으면 실제 동작이나 변경 내용까지만 설명한다.
- 종결어미는 문서의 기능에 맞춰 일관되게 쓴다. 반복을 피하려고 설명·명령·권고의 강도를 임의로 바꾸지 않는다.
- 연결어를 늘리기보다 문장 순서를 먼저 고친다. 같은 배경·이유·결론의 목적 없는 반복을 줄인다. 전환점이나 실행 직전에는 다음 판단에 필요한 구분·조건을 짧게 다시 짚는다. 그것으로 충분하면 이미 설명한 원리와 배경을 다시 풀지 않는다. 여러 조건이나 예외가 필요하면 문장 수에 맞춰 지우지 않는다. 모든 절에 요약을 붙이지 않는다.

## 5. 실행 안내와 근거를 확인한다

- 설치·실행·빌드·테스트를 구분한다. 관련 자료에서 작업 디렉터리, 패키지 관리자, 실제 스크립트, 필요한 설정을 확인한다.
- 확인된 절차만 실행 순서로 설명한다. 명령의 목적과 입력 위치가 불명확하면 짧게 덧붙인다. 한 줄짜리 자명한 명령에 장황한 해설을 붙이지 않는다.
- 독자가 성공 여부를 판단할 수 있도록 자료에 있는 출력·상태·확인 방법을 안내한다. 알 수 없는 성공 메시지를 새로 만들지 않는다.
- 시스템의 동작·판정 조건을 먼저 밝히고, 사람이 이를 조회·확인하는 절차를 구분해 쓴다. 확인하는 행동이 상태 변화의 원인이나 필수조건인 것처럼 인과를 추가하지 않는다. 조회 자체가 상태를 바꾸는 동작이라면 자료에 있는 그 동작을 따른다.
- 예시와 실제 값을 구분한다. 자리표시자는 의미를 표시하고, 실제 배포 문서에 예시 주소·없는 파일·빈 코드 블록이 남지 않게 한다.
- API의 오류, 재시도, 권한, 운영 절차의 중단·복구 조건은 확인된 동작만 적는다. 없는 동작을 일반적인 관례로 채우지 않는다.
- 문서를 쓰기 위해 명령을 임의로 실행하지 않는다. 실행 검증이 작업에 포함된 경우 그 범위에서 확인하고, 실제 실행 여부를 정확히 기록한다.
- 외부 자료나 코드에서 보완한 중요한 사실은 적절한 출처나 파일 경로로 추적할 수 있게 한다. 평범한 문장마다 인용을 반복하지 않는다.

## 6. 결과물을 다시 읽는다

1. **의미:** 대상·조건·예외·기본값·부정·가능성·계획·검증 상태와 판단 한계의 이유가 달라지거나 빠지지 않았는지 원자료와 대조한다.
2. **구조:** 처음 읽는 사람이 대상과 목적을 알 수 있는지 확인한다. 초기 상태·장애·예외·거절 조건을 급히 찾는 사람도 소제목과 표에서 해당 위치를 찾을 수 있는지 살핀다. 짧은 본문에는 이를 위해 제목이나 표를 억지로 만들지 않는다.
3. **흐름:** 소리 내어 읽는 속도로 문단을 읽고, 숨이 차는 문장과 지나치게 끊긴 문장을 함께 고친다. 앞 절과 현재 절의 관계, 새 용어의 뜻, 조건의 적용 대상을 다시 찾아야만 이해할 수 있는 부분을 확인한다.
4. **실용성:** 실행에 필요한 정보가 자료와 맞는지, 시스템 판정과 사람의 확인 절차를 섞거나 모르는 항목을 아는 것처럼 쓰지 않았는지 확인한다.
5. **형식:** 제목 단계, 목록 들여쓰기, 링크, 표, 코드 펜스를 확인한다. 코드 블록을 포함한 Markdown 예시는 바깥 펜스를 더 길게 쓴다.

요청한 문서 길이와 수정 범위를 지킨다. 길이 감소를 이해 향상으로 간주하지 않으며, 필요한 연결 설명과 예시를 분량 때문에 지우지 않는다. 결과가 이미 목적에 맞으면 불필요한 재작성이나 장식을 멈춘다.
