# 모래결 색인 갱신기: 요청 접수부터 검색 반영까지

모래결 색인 갱신기는 자료집의 문서를 검색할 색인을 만드는 내부 서비스다. 새로 합류한 개발자가 먼저 구분해야 할 것은 **갱신 요청의 접수, 작업의 진행 상태, 검색에 쓰이는 활성 색인**이다. 접수가 성공하면 작업 기록이 생기지만, 검색 결과가 곧바로 바뀌지는 않는다. 작업이 후보 색인을 만들고 검증한 뒤 활성 판으로 전환되어야 새 내용을 검색할 수 있다.

이 문서는 가상의 자료집 `C17`, 원본 `r18`, 접수 `q203`, 색인 판 `i52`를 예로 들어 그 과정을 설명한다.

## 1. 원본에서 검색 결과까지, 구성 요소가 맡는 일

원본을 올리는 기능은 별도 시스템에 있다. 모래결 색인 갱신기는 이미 보관된 원본을 선택해 색인을 갱신한다. 조회 API가 검색하는 대상은 원본 자체가 아니라 활성 색인이다. 따라서 새 원본의 보관이 끝났다는 사실만으로 검색에 새 내용이 반영되었다고 판단할 수는 없다.

갱신과 검색은 다음 네 구성 요소가 나누어 맡는다.

| 구성 요소 | 역할 |
| --- | --- |
| 접수 API | 갱신 요청을 확인하고 작업 기록을 저장한다. |
| 작업 조정기 | 작업을 구축기에 넘기고, 검증을 통과한 후보를 활성 색인으로 반영한다. |
| 구축기 | 선택된 원본으로 후보 색인을 만들고 검증한다. |
| 조회 API | 자료집의 활성 색인을 사용해 검색한다. |

접수 API가 요청을 기록하면 조정기가 작업을 구축기에 넘긴다. 구축기는 검색에 사용할 새 색인을 후보로 만든다. 이 후보는 기존 활성 색인과 분리되어 보관된다. 구축 도중 일부 문서만 만들어져 있어도 그 내용이 기존 검색 결과에 섞이지 않는 이유다.

후보가 검증을 통과하면 조정기가 활성 판으로 전환한다. 조회 API는 이 전환이 확정되기 전까지 기존 활성 판을 사용한다. 후보를 만드는 과정과 실제 검색에 사용하는 판을 바꾸는 과정은 이렇게 구분된다.

## 2. 네 식별자를 구분하고, 작업이 선택한 원본을 확인한다

하나의 갱신을 살펴볼 때는 다음 식별자를 함께 보게 된다.

| 식별자 | 가리키는 대상 | 예시 |
| --- | --- | --- |
| 자료집 번호 | 색인을 갱신하고 검색할 자료집 | `C17` |
| 원본 번호 | 내용이 고정된 원본 한 묶음 | `r18` |
| 접수 번호 | 접수된 작업 기록 | `q203` |
| 색인 판 번호 | 만들어진 색인의 판 | `i52` |

예를 들어 “자료집 `C17`의 원본 `r18`로 색인을 갱신한다”는 요청이 `q203`으로 접수되고, 그 작업이 색인 `i52`를 만들 수 있다. 이때 `r18`, `q203`, `i52`의 숫자는 각각 별도 순서다. 숫자 크기를 서로 비교해 진행률이나 최신 여부를 판단해서는 안 된다.

**작업 상태를 조회할 때 사용하는 식별자는 접수 번호다.** `q203`의 상태를 알고 싶다면 `q203`으로 조회해야 한다. 자료집 번호 `C17`이나 색인 판 번호 `i52`로 대신 조회할 수 없다.

원본 번호는 작업이 어떤 내용을 사용해야 하는지도 고정한다. `q203`이 `r18`로 접수되었다면 이후 `r19`가 보관되어도 작업은 끝까지 `r18`을 사용한다. 조정기나 구축기가 진행 도중 최신 원본으로 대상을 바꾸는 기능은 없다. 따라서 새 원본이 올라왔는지와 현재 작업이 어느 원본을 처리하는지는 별도로 확인해야 한다.

## 3. 접수 성공은 어디까지 보장하는가

접수 API는 먼저 자료집이 존재하는지, 지정한 원본의 보관이 완료되었는지 확인한다. 둘 중 하나라도 충족하지 않으면 이유를 반환하고 작업 기록을 만들지 않는다.

두 조건을 모두 충족해도 접수가 거절될 수 있다. 한 자료집에는 진행 중인 작업을 하나만 허용하기 때문이다. 같은 자료집에 진행 중 작업이 있으면 새 갱신이나 재시도 요청에 대해 `진행 중 작업 있음`과 그 작업의 접수 번호를 반환하며, 새 접수 번호는 만들지 않는다. 이 제한은 자료집별로 적용되므로 다른 자료집의 접수에는 영향을 주지 않는다.

접수에 성공하면 작업 기록을 저장한 뒤 새 접수 번호와 `대기` 상태를 반환한다. 이 응답으로 확인할 수 있는 것은 요청이 작업 목록에 들어갔다는 사실이다. 다음 사항까지 보장하는 응답은 아니다.

- 구축기가 작업을 시작했다는 것
- 후보 색인이 검증을 통과했다는 것
- 자료집의 활성 색인이 바뀌었다는 것

접수 뒤에는 응답으로 받은 접수 번호로 작업 상태를 확인한다. 검색에 새 내용이 반영되었는지를 판단하려면 이후의 상태 전이, 특히 `완료` 여부를 봐야 한다. 접수 응답은 그 확정까지 걸리는 시간도 약속하지 않는다.

## 4. 정상 경로에서 각 상태가 뜻하는 것

정상적인 갱신은 `대기 → 구축 중 → 검증 중 → 반영 대기 → 완료` 순서로 진행한다. 이 중 `완료`는 종료 상태다. 정상 경로 밖의 종료 상태로는 `실패`와 `중단`이 있으며, 이 세 상태를 제외한 나머지는 모두 진행 중 상태다.

| 상태 | 작업에서 일어나는 일 | 다음에 기다리는 일 |
| --- | --- | --- |
| 대기 | 작업 기록은 있지만 구축기가 아직 시작하지 않았다. | 구축 시작 |
| 구축 중 | 접수할 때 선택한 원본으로 후보 색인을 만든다. | 후보 구축을 마치고 검증 진행 |
| 검증 중 | 후보의 문서 수와 확인용 문서의 조회를 검사한다. | 모든 검증 항목 통과 |
| 반영 대기 | 검증을 통과한 후보가 활성 판으로 전환되기를 기다린다. | 조정기의 활성 판 전환 |
| 완료 | 활성 판 변경과 작업 완료 기록이 함께 확정되었다. | 해당 갱신 작업은 종료됨 |

### 검증 통과가 뜻하는 범위

검증 중에는 두 가지를 확인한다. 후보의 문서 수가 원본과 일치해야 하고, 원본에 지정된 두 확인용 문서가 정확한 키로 조회되어야 한다. 모두 통과해야 `반영 대기`로 넘어간다.

이 검증은 문서 누락과 기본 조회를 확인하는 범위다. 검색 순위의 품질을 평가한 결과는 아니다. 따라서 검증 통과 기록을 근거로 검색 순위가 좋아졌다고 설명할 수는 없다.

검증 통과와 검색 반영도 구분해야 한다. `반영 대기`는 후보가 검증을 마쳤다는 뜻이지만, 아직 활성 판 전환을 기다리는 상태다. 이때 조회 API는 기존 활성 판을 사용한다. 검증 통과 기록이나 `반영 대기` 표시만 보고 새 내용이 이미 검색된다고 안내해서는 안 된다.

### 완료가 뜻하는 확정 시점

반영할 때 조정기는 자료집의 활성 색인 판 변경과 해당 작업의 완료 기록을 하나의 변경으로 함께 확정한다. 따라서 `완료` 상태는 활성 판 전환이 확정되었다는 뜻이다.

`q203`이 만든 `i52`가 반영되는 경우라면, `q203`의 완료는 자료집 `C17`의 활성 판이 `i52`로 전환되었음을 뜻한다. 접수 성공과 달리 실제 검색에 사용할 판의 변경까지 확인할 수 있는 상태다.

## 5. 완료 뒤에도 이전 판의 검색 응답이 올 수 있다

작업 완료와 검색 응답을 함께 읽으려면 검색 요청이 **언제 시작했는지**를 봐야 한다. 조회 API는 요청을 시작할 때 활성 판을 한 번 정하고, 응답을 마칠 때까지 그 판을 유지한다. 한 검색 요청 안에서 두 판의 결과를 섞지는 않는다.

| 검색 요청이 시작된 시점 | 사용하는 색인 판 | 응답을 해석하는 방법 |
| --- | --- | --- |
| 활성 판 전환 전 | 기존 활성 판 | 전환 뒤에 응답이 도착하더라도 이전 판의 결과일 수 있다. |
| 활성 판 전환 확정 후 | 새 활성 판 | 새로 반영된 판으로 검색한다. |

예를 들어 `q203`이 `반영 대기`인 동안 시작한 검색은 기존 활성 판을 선택한다. 그 검색이 끝나기 전에 `q203`이 완료되어 `i52`가 활성화되더라도, 이미 시작한 검색은 끝까지 기존 판을 사용한다. 반대로 전환이 확정된 뒤 시작한 검색은 `i52`를 사용한다.

따라서 완료를 확인한 뒤 이전 내용의 응답을 받았다는 사실만으로 전환 실패라고 판단할 수는 없다. 그 응답이 전환 전에 시작한 검색의 결과인지 함께 살펴야 한다. 새 판의 검색 결과를 확인하려면 전환 확정 뒤 시작한 검색을 기준으로 읽는다.

## 6. 실패했을 때 기존 검색은 어떻게 되는가

구축이나 검증을 더 진행할 수 없는 오류가 나면 작업은 `실패`로 끝난다. 상태 조회에는 오류가 발생한 단계와 이유가 남는다. 실패한 후보는 활성 판으로 반영하지 않는다.

이미 활성 판이 있는 자료집은 그 판을 계속 사용한다. 새 갱신의 실패가 기존 검색의 중단을 뜻하지 않는 이유다. 갱신 상태에 실패가 표시되어도 조회 API는 이전에 반영된 색인으로 검색할 수 있다.

다만 첫 갱신이라면 상황이 다르다. 한 번도 반영을 마치지 않은 자료집에는 기존 활성 판이 없다. 첫 갱신이 진행 중이거나 `실패` 또는 `중단`으로 끝났다면 조회 API는 `색인 준비 안 됨`을 반환한다.

이 응답은 검색 결과가 없는 정상 응답인 빈 목록과 구분해야 한다. 빈 목록은 검색 결과가 없다는 뜻이고, `색인 준비 안 됨`은 검색에 사용할 활성 판이 아직 없다는 뜻이다. 작업 상태만 보지 말고 해당 자료집에 이전에 반영된 활성 판이 있었는지도 함께 보아야 한다.

## 7. 중단 수락과 작업의 중단 완료는 다른 시점이다

중단 요청은 모든 상태에서 받을 수 있는 것이 아니다.

| 조정기가 중단 요청을 확인한 시점의 상태 | 수락 여부 |
| --- | --- |
| 대기·구축 중·검증 중 | 수락 가능 |
| 반영 대기 | 거절 |
| 완료·실패·중단 | 거절 |

판단 기준은 사용자가 중단 버튼을 누른 시각이 아니라 **조정기가 요청을 확인한 시점의 작업 상태**다. 사용자가 검증 중이라고 보고 중단을 요청했더라도, 조정기가 확인할 때 이미 `반영 대기`라면 요청은 거절된다.

중단을 수락하면 먼저 중단 표시를 남긴다. 이후 조정기나 구축기가 그 표시를 확인하고 작업을 멈춘 뒤에야 상태를 `중단`으로 바꾼다. 따라서 중단 수락 뒤에도 잠시 직전의 진행 중 상태가 보일 수 있다. 수락 응답을 곧바로 중단 완료로 읽어서는 안 된다.

그동안에도 중단 표시의 효력은 있다. 표시가 남은 후보는 검증을 마치더라도 `반영 대기`로 넘어가거나 활성화될 수 없다. 중단으로 새 후보가 활성 판을 대체하지 않으므로, 기존 활성 판이 있었다면 기존 검색을 계속 사용한다. 활성 판이 없는 첫 갱신이었다면 앞서 설명한 대로 `색인 준비 안 됨` 상태가 이어진다.

### 새 작업은 중단 상태가 된 뒤 접수한다

중단 요청이 수락되었더라도 아직 상태가 `중단`이 아니라면 그 작업은 자료집의 진행 중 작업 자리를 차지한다. 이때 새 갱신이나 재시도를 요청하면 `진행 중 작업 있음`과 기존 접수 번호가 반환되며 새 번호는 생기지 않는다.

따라서 중단 후 다른 작업을 시작하려면 기존 접수 번호로 상태를 확인하면서 실제로 `중단`에 도달하기를 기다려야 한다. 중단을 요청했다는 사실, 중단이 수락되었다는 사실, 작업이 `중단` 상태로 끝났다는 사실을 구분해야 다음 접수 시점을 판단할 수 있다.

## 8. 재시도는 같은 원본으로 새 작업을 시작한다

재시도는 `실패` 또는 `중단`으로 끝난 작업에만 요청할 수 있다. 수락되면 기존 기록을 그대로 두고 새 접수 번호를 만든다. 새 작업은 `대기`부터 시작하며, 이전 작업과 같은 원본 번호를 사용한다.

이때 이전 후보를 재사용하거나 문서별 진행 위치에서 이어서 처리하지 않는다. 선택된 원본으로 처음부터 다시 구축한다. 재시도 후 상태를 확인할 때도 기존 작업의 접수 번호가 아니라 새로 받은 접수 번호를 사용해야 한다.

원본 선택이 달라지는 것도 아니다. `r18`을 사용한 `q203`이 실패한 뒤 `r19`의 보관이 끝났다고 하자. 이 상황에서 선택할 요청은 반영하려는 원본에 따라 달라진다.

| 원하는 결과 | 요청할 작업 | 사용하는 원본 |
| --- | --- | --- |
| 실패하거나 중단된 작업을 같은 원본으로 다시 수행 | 기존 작업의 재시도 | 기존 작업이 선택한 `r18` |
| 새로 보관된 원본을 검색에 반영 | `r19`를 지정한 일반 갱신 | 새 요청에서 지정한 `r19` |

`q203`을 재시도하면 이후에 보관된 `r19`가 있어도 `r18`을 사용한다. `r19`를 반영하려면 자료집에 진행 중 작업이 없는 때에 `r19`를 지정해 일반 갱신을 요청해야 한다. 재시도는 실패·중단 작업을 다시 수행하는 방법이고, 반영할 원본을 새로 선택하는 요청은 일반 갱신이다.

재시도에도 자료집별 진행 중 작업 제한이 적용된다. 기존 작업이 이미 실패나 중단으로 끝났더라도 같은 자료집에서 다른 작업이 진행 중이면 새 재시도를 접수할 수 없다.

## 9. 접수 응답, 작업 상태, 검색 결과를 함께 읽기

갱신 뒤 무엇을 기다려야 하는지는 현재 확인한 정보에 따라 달라진다. 접수 응답은 작업 기록의 생성 여부를, 상태 조회는 해당 작업의 진행과 종료를, 검색 응답은 요청 시작 시점에 선택된 활성 판의 결과를 보여 준다.

| 현재 확인한 정보 | 알 수 있는 것 | 이어서 확인할 것 |
| --- | --- | --- |
| 새 접수 번호와 `대기` 응답 | 작업 기록이 저장되었다. | 해당 접수 번호로 이후 상태를 확인한다. |
| `구축 중` 또는 `검증 중` | 선택한 원본으로 후보를 준비하고 있다. | 검증과 활성 판 전환이 끝나는지 확인한다. |
| `반영 대기` | 후보가 검증을 통과했다. | 활성 판 전환이 확정되어 `완료`가 되는지 확인한다. |
| `완료` | 활성 판 전환이 확정되었다. | 새 판의 결과는 전환 확정 뒤 시작한 검색으로 확인한다. |
| `실패` | 해당 후보는 반영되지 않는다. | 오류 단계와 이유를 보고, 같은 원본을 재시도할지 다른 원본의 일반 갱신을 요청할지 판단한다. |
| 중단 수락 뒤 진행 중 상태 | 중단 표시는 남았지만 작업의 중단이 아직 끝나지 않았다. | 새 작업을 접수하기 전에 `중단` 상태를 확인한다. |
| `색인 준비 안 됨` | 검색에 사용할 활성 판이 없다. | 첫 갱신이 진행 중인지, 실패·중단으로 끝났는지 작업 상태를 확인한다. |

예를 들어 `C17`에 기존 활성 판이 있고 `r18` 갱신이 `q203`으로 접수되었다면, 대기·구축·검증·반영 대기 동안 검색은 기존 판을 사용한다. `q203`이 완료되면 활성 판이 `i52`로 전환된 것이며, 그 뒤 시작한 검색은 `i52`를 사용한다. 도중에 `r19`가 보관되었더라도 `q203`이 만든 판은 `r18`을 바탕으로 한다.

같은 작업이 구축이나 검증에서 실패했다면 `i52` 후보는 반영되지 않고 기존 판으로 검색을 계속한다. `q203`을 재시도하면 새 접수 번호로 `r18`부터 다시 구축한다. `r19`가 필요하다면 진행 중 작업이 없는 때에 별도의 일반 갱신으로 요청한다. 이 흐름에서 작업의 종료 여부와 원하는 원본 번호를 함께 확인해야 다음 요청을 올바르게 선택할 수 있다.

## 10. 아직 정해지지 않은 운영 정책

현재 자료로 확정할 수 있는 것은 위의 상태 의미와 수동 재시도 조건까지다. 다음 항목은 미확정이다.

- 대기 시간의 상한
- 자동 재시도의 유무와 간격
- 실패·중단 후보의 보관 기간
- 반영 단계에서 오류가 났을 때의 복구 절차

따라서 접수나 중단 수락을 근거로 일정 시간 안에 다음 상태가 된다고 약속할 수 없다. 실패한 작업이 자동으로 재시도된다거나, 반영 단계의 오류가 특정 절차로 자동 복구된다고 가정해서도 안 된다. 후보의 보관·삭제 시점 역시 정해진 정책으로 설명할 수 없다. 이런 운영 판단에는 별도로 확정된 정책이 필요하다.

# 모래결 색인 갱신기: 접수부터 검색 반영까지

모래결 색인 갱신기는 자료집에 보관된 원본으로 검색용 색인을 만드는 내부 서비스입니다. 원본을 올리는 기능은 별도 시스템에 있으며, 이 서비스는 보관이 끝난 원본을 선택해 색인을 갱신합니다. 검색에는 원본이 아니라 색인을 사용합니다. 이 문서의 서비스 이름과 사례는 모두 가상입니다.

갱신을 따라갈 때는 **요청 접수, 후보 색인 검증, 활성 색인 전환**을 구분해야 합니다. 접수 성공은 작업 기록이 저장됐다는 뜻이고, 완료는 검색에 사용할 색인 판의 전환이 확정됐다는 뜻입니다. 아래에서는 구성 요소와 식별자를 먼저 살펴본 뒤, 상태 변화와 검색 결과를 연결하고 중단·재시도 조건을 설명합니다.

## 1. 구성 요소와 식별자 이해하기

갱신은 접수 API에서 시작합니다. 접수 API가 요청을 기록하면 작업 조정기가 작업을 구축기에 넘깁니다. 구축기는 후보 색인을 만들고 검증하며, 검증을 통과한 후보를 실제 검색에 반영하는 일은 조정기가 맡습니다. 조회 API는 이렇게 선택된 **활성 색인 판**으로 검색합니다. 따라서 후보가 만들어지는 과정과 조회 API가 사용하는 색인 판의 변경은 별개입니다.

이 흐름에는 서로 다른 대상을 가리키는 네 식별자가 등장합니다.

| 식별자 | 예시 | 가리키는 대상 |
| --- | --- | --- |
| 자료집 번호 | `C17` | 갱신할 자료집 |
| 원본 번호 | `r18` | 내용이 고정된 원본 한 묶음 |
| 접수 번호 | `q203` | 접수된 갱신 작업 |
| 색인 판 번호 | `i52` | 만들어진 색인의 한 판 |

예를 들어 자료집 `C17`의 원본 `r18`을 갱신하는 작업 `q203`이 색인 `i52`를 만들 수 있습니다. `r18`, `q203`, `i52`의 숫자는 각각 별도 순서이므로, 서로 비교해 진행률이나 최신 여부를 판단할 수 없습니다.

작업의 상태를 확인할 때는 **접수 번호**를 사용합니다. `q203`의 진행 상황을 자료집 번호 `C17`이나 색인 판 번호 `i52`로 대신 조회할 수는 없습니다.

## 2. 접수 성공 뒤에 무엇을 기다리는가

접수 API는 먼저 자료집이 존재하는지, 지정한 원본의 보관이 완료됐는지 확인합니다. 둘 중 하나라도 충족하지 않으면 이유를 반환하고 작업 기록을 만들지 않습니다. 두 조건을 충족하더라도 같은 자료집에 진행 중인 작업이 있으면 새 작업을 받지 않습니다. 한 자료집에는 진행 중인 작업을 하나만 허용하기 때문입니다.

접수에 성공하면 작업 기록의 저장을 마친 뒤 새 접수 번호와 `대기` 상태를 반환합니다. 이 응답은 요청이 작업 목록에 들어갔음을 나타냅니다. 구축 시작, 검증 성공, 활성 색인 변경까지 보장하지는 않으므로, 받은 접수 번호로 이후 상태를 확인해야 합니다.

작업에 사용할 원본도 접수 시점에 정해집니다. `q203`이 `r18`로 접수됐다면 이후 `r19`가 올라와도 끝까지 `r18`을 사용합니다. 조정기나 구축기가 진행 도중 대상을 최신 원본으로 바꾸는 기능은 없습니다.

## 3. 대기부터 완료까지의 상태 변화

정상적인 갱신은 다음 순서로 진행됩니다.

**대기 → 구축 중 → 검증 중 → 반영 대기 → 완료**

`완료`, `실패`, `중단`은 종료 상태이고, 나머지는 모두 진행 중 상태입니다. 검증이 끝난 `반영 대기`도 작업이 아직 끝나지 않은 상태에 해당합니다.

### 대기와 구축 중: 후보 색인을 만드는 단계

`대기`는 작업 기록은 있지만 구축기가 아직 작업을 시작하지 않은 상태입니다. 조정기가 작업을 넘겨 구축기가 선택한 원본으로 후보 색인을 만들기 시작하면 `구축 중`이 됩니다.

후보 색인은 활성 색인과 분리해 보관합니다. 따라서 일부 문서만 만들어진 후보가 검색 결과에 섞이지 않습니다. 기존 활성 판이 있는 자료집은 새 후보를 구축하는 동안에도 그 판으로 검색합니다.

### 검증 중: 문서 누락과 기본 조회를 확인하는 단계

구축을 마친 후보는 `검증 중` 상태에서 다음 두 검사를 받습니다.

- 후보의 문서 수가 원본의 문서 수와 일치하는지 확인합니다.
- 원본에 지정된 확인용 문서 두 개가 정확한 키로 조회되는지 확인합니다.

검사를 모두 통과해야 다음 상태로 넘어갑니다. 이 검증이 확인하는 범위는 문서 누락과 기본 조회입니다. 검증 통과를 검색 순위의 품질까지 평가한 결과로 해석해서는 안 됩니다.

### 반영 대기와 완료: 검색에 사용할 판을 바꾸는 단계

`반영 대기`는 검증을 통과한 후보가 활성 판으로 전환되기를 기다리는 상태입니다. 조정기가 전환하기 전까지 조회 API는 기존 활성 판을 사용합니다. 검증 통과 기록이나 `반영 대기` 표시만으로 새 내용이 이미 검색된다고 안내할 수는 없습니다.

조정기는 반영할 때 자료집의 활성 색인 판 변경과 해당 작업의 완료 기록을 하나의 변경으로 함께 확정합니다. **`완료`는 이 전환이 확정됐다는 뜻입니다.** 접수 성공 응답은 여기까지 걸리는 시간을 약속하지 않습니다.

## 4. 완료 상태와 실제 검색 결과를 함께 읽기

조회 API는 검색 요청을 시작할 때 활성 판을 한 번 정하고, 응답을 마칠 때까지 그 판을 유지합니다. 한 검색 요청 안에서 구판과 새 판의 결과를 섞지 않습니다.

이 때문에 작업이 `완료`된 뒤 도착한 검색 응답에도 구판의 결과가 담길 수 있습니다. 그 검색이 전환 전에 시작됐다면, 전환 후에 응답을 마치더라도 처음 선택한 판을 계속 사용하기 때문입니다. 전환이 확정된 뒤 시작한 검색은 새 판을 사용합니다. 새 내용의 반영 여부를 확인하려면 작업의 `완료`를 확인한 뒤 검색 요청을 시작해야 합니다.

지금까지의 설명에서 “기존 판으로 검색한다”는 말은 이미 활성 판이 있는 자료집에 적용됩니다. 한 번도 반영을 마치지 않은 자료집에는 기존 활성 판이 없습니다. 첫 갱신이 진행 중이거나 `실패`·`중단`으로 끝났다면 조회 API는 `색인 준비 안 됨`을 반환합니다. 이는 검색은 정상적으로 수행됐지만 결과가 없는 빈 목록 응답과 구분해야 합니다.

## 5. 실패와 중단이 검색과 다음 접수에 미치는 영향

### 구축·검증 실패 시 후보는 반영하지 않는다

구축 또는 검증을 더 진행할 수 없는 오류가 발생하면 작업은 `실패`로 끝납니다. 상태 조회에는 오류가 발생한 단계와 이유를 남기며, 실패한 후보는 활성 판으로 반영하지 않습니다.

기존 활성 판이 있었다면 조회 API는 그 판을 계속 사용합니다. 따라서 갱신 실패가 기존 검색의 중단을 뜻하지는 않습니다. 첫 갱신이 실패한 자료집은 활성 판이 없으므로 앞서 설명한 `색인 준비 안 됨` 상태에 머뭅니다.

### 중단 요청의 수락과 작업 종료는 시점이 다르다

중단 요청은 `대기`, `구축 중`, `검증 중`에만 받습니다. `반영 대기` 또는 종료 상태인 `완료`, `실패`, `중단`에서는 거절합니다. 수락 가능 여부는 사용자가 중단 버튼을 누른 시각이 아니라 **조정기가 요청을 확인한 시점의 상태**로 판단합니다. 버튼을 눌렀을 때는 `검증 중`이었더라도 조정기가 확인할 때 `반영 대기`라면 중단 요청은 거절됩니다.

중단 요청을 수락하면 먼저 중단 표시를 남깁니다. 조정기나 구축기가 이 표시를 확인해 실제 작업을 멈춘 뒤에야 상태가 `중단`으로 바뀝니다. 그동안 상태 조회에는 직전의 진행 중 상태가 보일 수 있습니다. 다만 중단 표시가 남은 후보는 검증을 마치더라도 `반영 대기`로 넘어가거나 활성화될 수 없습니다.

중단된 후보가 반영되지 않으므로, 기존 활성 판이 있었다면 그 판으로 검색을 계속합니다. 첫 갱신을 중단한 자료집에는 활성 판이 생기지 않으며 조회 API는 `색인 준비 안 됨`을 반환합니다.

### 다음 작업은 종료 상태를 확인한 뒤 요청한다

중단 요청이 수락됐더라도 아직 상태가 `중단`으로 바뀌지 않았다면 진행 중 작업의 자리를 계속 차지합니다. 이때 같은 자료집에 새 갱신이나 재시도를 요청하면 `진행 중 작업 있음`과 현재 작업의 접수 번호를 반환하며, 새 접수 번호는 만들지 않습니다. 다른 자료집의 접수에는 영향을 주지 않습니다.

따라서 중단한 작업을 다시 시도하려면 중단 요청의 수락만 확인해서는 부족합니다. 해당 접수 번호로 상태를 조회해 `중단`으로 끝났는지 확인해야 합니다.

## 6. 재시도와 새 원본 갱신 중에서 선택하기

재시도는 `실패` 또는 `중단`으로 끝난 작업에만 요청할 수 있습니다. 수락되면 기존 작업 기록은 그대로 두고, 새 접수 번호로 `대기`부터 시작합니다. 이전 후보나 문서별 진행 위치를 이어 쓰지 않고 처음부터 다시 구축합니다.

재시도에서 유지되는 것은 기존 작업의 **원본 번호**입니다. `r18`을 사용한 작업이 실패한 뒤 `r19`의 보관이 끝났더라도, 그 작업을 재시도하면 다시 `r18`을 사용합니다. 다음 요청은 반영하려는 원본에 따라 선택합니다.

| 반영하려는 원본 | 요청 방법 |
| --- | --- |
| 실패·중단한 작업과 같은 원본 `r18` | 해당 작업의 재시도를 요청합니다. |
| 새로 보관된 원본 `r19` | 진행 중인 작업이 없을 때 `r19`를 지정한 일반 갱신을 요청합니다. |

재시도 역시 같은 자료집에 진행 중인 작업이 있으면 수락되지 않습니다. 종료된 작업을 재시도하는 것과 최신 원본을 선택하는 것은 별개의 판단입니다.

## 7. 아직 확정되지 않은 운영 정책

현재 자료로 설명할 수 있는 재시도 범위는 위의 수동 재시도 조건까지입니다. 다음 항목은 미확정입니다.

- 대기 시간의 상한
- 자동 재시도의 유무와 간격
- 실패·중단한 후보의 보관 기간
- 반영 단계에서 발생한 오류의 복구 절차

따라서 접수 후 일정 시간 안에 완료된다거나, 실패하면 자동으로 재시도·복구된다고 전제해서는 안 됩니다.

# 모래결 색인 갱신기 온보딩

모래결 색인 갱신기는 자료집의 문서를 검색할 색인을 만드는 내부 서비스입니다. 원본을 올리는 일은 별도 시스템이 맡고, 이 서비스는 보관된 원본을 선택해 색인을 갱신합니다. 검색에는 원본이 아니라 색인을 사용합니다. 아래 서비스 이름과 사례는 모두 가상입니다.

갱신을 이해할 때는 **요청이 접수된 시점, 새 색인이 활성화된 시점, 검색 요청이 시작된 시점**을 구분해야 합니다. 먼저 구성 요소와 식별자를 살펴보고, 접수부터 완료까지의 흐름을 따라가며 각 시점에 무엇을 확인할 수 있는지 알아보겠습니다.

## 구성 요소와 식별자

갱신은 접수 API에서 시작합니다. 접수 API가 요청을 기록하면 작업 조정기가 작업을 구축기에 넘깁니다. 구축기는 새로 사용할 후보 색인을 만들고 검증하며, 조정기는 검증을 통과한 후보를 반영합니다. 조회 API는 이렇게 반영된 활성 색인으로 검색합니다.

후보 색인과 활성 색인은 분리되어 보관됩니다. 후보를 구축하는 동안 일부 문서만 만들어졌더라도 그 내용이 기존 검색 결과에 섞이지 않습니다. 새 후보를 만드는 일과 검색에 사용하는 판을 바꾸는 일은 서로 다른 단계입니다.

각 대상을 구별하는 번호도 따로 있습니다.

| 식별자 | 예시 | 가리키는 대상 |
| --- | --- | --- |
| 자료집 번호 | `C17` | 색인을 갱신할 자료집 |
| 원본 번호 | `r18` | 내용이 고정된 원본 한 묶음 |
| 접수 번호 | `q203` | 접수된 갱신 작업 |
| 색인 판 번호 | `i52` | 색인 한 판 |

예를 들어 자료집 `C17`의 원본 `r18`을 갱신해 달라는 요청 `q203`이 색인 `i52`를 만들 수 있습니다. `r18`·`q203`·`i52`의 숫자는 각각 별도 순서이므로, 서로 비교해 진행률이나 최신 여부를 판단할 수 없습니다.

작업에 사용할 원본은 접수할 때 정해집니다. `q203`이 `r18`로 접수되었다면 이후 `r19`가 올라와도 끝까지 `r18`을 사용합니다. 조정기나 구축기가 진행 도중 최신 원본으로 대상을 바꾸는 기능은 없습니다.[^1]

## 접수 조건과 거절 응답

접수 API는 자료집이 존재하는지, 지정한 원본의 보관이 완료되었는지 확인합니다. 둘 중 하나라도 충족하지 않으면 이유를 반환하고 작업 기록을 만들지 않습니다.

이 두 조건을 통과하더라도 같은 자료집에 진행 중인 작업이 있으면 새 작업을 받지 않습니다. 한 자료집에는 진행 중인 작업을 하나만 허용하기 때문입니다. 이 경우 `진행 중 작업 있음`과 기존 작업의 접수 번호를 반환하며 새 접수 번호는 만들지 않습니다. 다른 자료집의 접수에는 영향을 주지 않습니다.

접수에 성공하면 작업 기록을 저장한 뒤 새 접수 번호와 `대기` 상태를 반환합니다. 이는 요청이 작업 목록에 들어갔다는 뜻입니다. 구축 시작, 검증 성공, 활성 색인 변경까지 보장하는 응답은 아닙니다.

접수 뒤에는 반환받은 **접수 번호**로 작업 상태를 조회합니다. 예시에서는 `q203`을 사용하며, 자료집 번호 `C17`이나 색인 판 번호 `i52`로 대신 조회할 수 없습니다.[^2]

## 대기에서 완료까지

정상 경로는 **대기 → 구축 중 → 검증 중 → 반영 대기 → 완료**입니다. 각 상태가 나타내는 작업 범위는 다음과 같습니다.

| 상태 | 시스템에서 일어나는 일 |
| --- | --- |
| 대기 | 작업 기록은 있지만 구축기가 아직 시작하지 않았습니다. |
| 구축 중 | 접수할 때 선택한 원본으로 후보 색인을 만듭니다. |
| 검증 중 | 후보의 문서 수와 확인용 문서의 조회 결과를 검사합니다. |
| 반영 대기 | 검증을 통과한 후보가 활성 판으로 전환되기를 기다립니다. |
| 완료 | 활성 색인 판의 전환과 해당 작업의 완료 기록이 함께 확정되었습니다. |

검증에서는 후보의 문서 수가 원본과 일치하는지, 원본에 지정된 두 확인용 문서가 정확한 키로 조회되는지 확인합니다. 모든 검사를 통과해야 반영 대기로 넘어갑니다. 이 검증의 범위는 문서 누락과 기본 조회이며, 검색 순위의 품질을 평가한 결과는 아닙니다.

반영 대기까지 왔어도 조회 API는 기존 활성 판을 사용합니다. 조정기가 실제로 전환하기 전에는 새 후보가 검색에 사용되지 않으므로, 검증 통과 기록이나 반영 대기 표시만 보고 새 내용이 이미 검색된다고 안내하면 안 됩니다.

반영할 때 조정기는 자료집의 활성 색인 판 변경과 해당 작업의 완료 기록을 하나의 변경으로 함께 확정합니다. 따라서 `완료` 상태는 활성 판의 전환이 확정되었다는 뜻입니다. 접수 성공 응답은 이 확정까지 걸리는 시간을 약속하지 않습니다.

`완료`·`실패`·`중단`은 종료 상태입니다. 그 밖의 상태인 `대기`·`구축 중`·`검증 중`·`반영 대기`는 모두 진행 중으로 취급합니다.[^3]

## 완료 상태와 검색 결과를 함께 읽기

조회 API는 검색 요청을 시작할 때 활성 판을 한 번 정하고, 응답을 마칠 때까지 그 판을 유지합니다. 같은 검색 요청 안에서 두 판의 결과를 섞지 않습니다.

예를 들어 `q203`이 만든 `i52`로 활성 판을 전환한다고 하겠습니다. 전환 전에 시작한 검색은 전환 뒤에 응답하더라도 이전 판의 결과일 수 있습니다. 전환이 확정된 뒤 시작한 검색은 새 판인 `i52`를 사용합니다. 검색 응답이 도착한 시각만으로는 어느 판을 사용했는지 판단할 수 없습니다.

갱신 결과를 확인할 때는 접수 번호로 `완료` 상태를 확인한 뒤 새 검색 요청을 시작하면 됩니다. 시스템이 판을 고르는 기준은 검색 요청의 시작 시점입니다. 완료 상태를 조회하는 절차는 전환이 확정되었음을 확인하고 그 뒤에 검색을 시작하기 위한 것입니다.[^4]

## 실패와 첫 갱신의 검색 동작

구축 또는 검증을 더 진행할 수 없는 오류가 발생하면 작업은 `실패`로 끝납니다. 상태 조회에는 오류가 발생한 단계와 이유를 남기며, 실패한 후보는 활성 판으로 반영하지 않습니다.

기존 활성 판이 있었다면 조회 API는 그 판을 계속 사용합니다. 따라서 갱신 실패가 기존 검색의 중단을 뜻하지는 않습니다. 중단된 작업의 후보도 반영하지 않으므로 기존 활성 판이 있는 자료집은 계속 그 판으로 검색합니다.

**첫 갱신에서는 기존 활성 판이 없다는 점을 따로 확인해야 합니다.** 한 번도 반영을 마치지 않은 자료집에서 첫 갱신이 진행 중이거나 `실패`·`중단`으로 끝났다면 조회 API는 `색인 준비 안 됨`을 반환합니다. 이는 검색 결과가 없는 정상 응답인 빈 목록과 구분됩니다.[^5]

## 중단 요청의 수락 조건과 실제 중단 시점

중단 요청은 `대기`·`구축 중`·`검증 중`에서만 받습니다. `반영 대기` 또는 종료 상태인 `완료`·`실패`·`중단`에서는 거절합니다. 수락 여부는 사용자가 중단 버튼을 누른 시각이 아니라 **조정기가 요청을 확인한 시점의 작업 상태**로 판단합니다. 예를 들어 구축 중에 중단 버튼을 눌렀더라도, 조정기가 확인할 때 이미 반영 대기라면 요청은 거절됩니다.

중단 요청을 수락하면 먼저 중단 표시를 남깁니다. 이후 조정기나 구축기가 표시를 확인하고 작업을 멈춘 뒤에야 상태를 `중단`으로 바꿉니다. 그 사이에는 상태 조회에 직전의 진행 중 상태가 보일 수 있습니다. 다만 중단 표시가 남은 후보는 검증을 끝내더라도 반영 대기로 넘어가거나 활성화될 수 없습니다.

새 갱신이나 재시도를 요청하려면 실제로 작업이 종료되었는지 확인해야 합니다. 중단 요청이 수락되었어도 아직 `중단` 상태가 아니라면 같은 자료집의 진행 중 작업 자리를 차지합니다. 이때 새 갱신이나 재시도를 요청하면 `진행 중 작업 있음`과 그 접수 번호를 반환하며, 새 번호는 만들지 않습니다.[^6]

## 재시도와 다른 원본으로의 갱신

재시도는 `실패`·`중단` 작업에만 요청할 수 있으며, 같은 자료집에 진행 중인 작업이 없어야 수락됩니다. 수락되면 기존 작업 기록을 그대로 두고 새 접수 번호로 `대기`부터 시작합니다.

새 작업은 기존 작업과 같은 원본 번호를 사용합니다. 이전 후보나 문서별 진행 위치를 이어 쓰지 않고 처음부터 다시 구축합니다. 중단했던 작업을 재시도할 때도 이 조건은 같습니다.

예를 들어 `r18`을 대상으로 한 `q203`이 실패한 뒤 `r19`가 보관되었더라도, `q203`의 재시도는 `r18`을 사용합니다. `r19`를 반영하려면 진행 중인 작업이 없는 때에 `r19`를 지정한 일반 갱신을 요청해야 합니다. 재시도는 같은 원본으로 작업을 다시 시작하는 기능이며, 최신 원본을 선택하는 기능은 아닙니다.[^7]

## 검토 방법과 한계

각 현재 문서는 별도의 새 컨텍스트에서 입력과 스킬만 읽고 한 번 작성했다. 생성자는 이전 출력·기대 답·평가 기준을 받지 않았다. 작성과 검토에는 같은 세션 계열 모델을 사용했으며 정확한 배포 식별자와 샘플링 설정은 노출되지 않았다.

검토자는 무작위 라벨과 순서의 v0.3.0·v0.4.0 두 문서를 원자료 및 사전에 고정한 보존 계약과 대조했습니다. 스킬이나 조건 대응표는 검토가 끝나기 전에 공개하지 않았다. 미적용 원문은 앞선 검토가 있는 참고 자료이며 이번 의미 재검토에는 포함하지 않았다. 필수 의미마다 보존·부분보존·누락·충돌과 근거를 적고, 탐색 질문에는 답의 위치와 국소 조건의 부족을 기록했습니다. 이전 점수를 재사용하거나 새 20점 합계를 만들지 않았다. 검토자가 원자료를 함께 보았으므로 실제 독자의 독해·기억 시험이 아닙니다.

새 설정배포·작업 보고 두 사례에서는 두 조건 모두 이번에 생성했다. 이 사례도 문제 유형을 고려해 설계했고 요청에 일부 구분을 명시했습니다. 실제 독자의 이해도·지연 회상·읽는 시간·피로, Claude·Gemini별 효과, 여러 번 생성했을 때의 변동은 측정하지 않았다. 모든 사례는 공개 가능한 가상 자료이며, 본문의 설치·운영 명령을 실제 서비스에서 실행한 결과가 아닙니다.
