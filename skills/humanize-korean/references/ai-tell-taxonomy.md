# 한국어 개발 문서 교정 분류

이 문서는 [기존 통합 룰북](ai-tell-rulebook.md)의 규칙 ID를 유지하면서 개발 문서에 필요한 조건을 보강합니다. 기존 `A-2`, `K-2`, `E-2`와 새 `DEV-A02` 등은 서로 다른 ID입니다. 정본 ID·정규식·용어·예제는 [development-rules.json](development-rules.json)에 기록하며, 실제 편집은 [빠른 규칙](quick-rules.md)과 [교정 절차](rewriting-playbook.md)를 함께 적용합니다.

이 분류는 개발 문서의 표현과 구조를 점검하기 위한 기준입니다. 글의 작성 주체를 판별하거나 품질을 단일 점수로 평가하는 근거로 사용하지 않습니다.

## 적용 우선순위

사용자가 지정한 범위와 보호 원칙을 먼저 적용합니다. 다음으로 명세·기록의 역할을 구분하고 개발 규칙을 적용한 뒤, 해당 문맥에 맞는 일반 교정 규칙을 보완합니다. 리듬을 바꾸려는 문체 권고 때문에 문서 세트의 어미를 섞지 않습니다.

전문 용어 보존은 실제 식별자·정의·기술 의미를 보호하는 원칙입니다. 개발 사전에 등록된 설명용 한국어 표현은 의미가 같다고 확인한 경우에만 고칠 수 있습니다. API 경로·필드명·환경변수·CLI 옵션·버전·해시·UUID를 사전의 한국어 표현으로 바꾸지 않습니다.

## DEV-A01. 문맥을 확인한 개발 용어 풀이

탐지 대상은 [빠른 규칙의 사전](quick-rules.md#dev-a01-개발-직역-조어)에 있는 14개 용어군입니다. 정본의 `translation_coinages` 항목은 각 용어군에 독립된 하위 ID를 부여하며, 모든 교정 전 표현·권장 표현·적용 조건·보존 기준을 포함합니다.

사전은 개발자가 읽는 설명문에 적용합니다. 사전 항목과 같은 문자열이 나와도 코드 식별자, API 계약의 고정 이름, 원시 출력이면 원형을 유지합니다. 전문 용어라는 이유만으로 설명문의 어색한 표현을 모두 보호하거나, 반대로 사전이 있다는 이유로 정의된 기술 의미를 바꾸지 않습니다.

확인할 핵심 차이는 다음과 같습니다.

- 자격 증명의 생성·등록과 파일·모듈 가져오기를 구분합니다.
- 암호화와 경로 접근 제어를 구분하며, 확인되지 않은 DPAPI 사용을 추가하지 않습니다.
- DB·파일·메모리·객체 저장소를 구분하고 실제 저장 대상과 기간을 보존합니다.
- 프로세스의 실행 여부와 상태 검사의 정상 판정을 구분합니다.
- 일시 차단되는 대상이 워커인지 요청인지 확인하고 실제 원인·해제 조건을 유지합니다.
- 고유 키 수와 전체 행 수를 구분합니다.
- 로그·훅·보존 정책이 다루는 단계를 확인하고, 문서의 범위를 임의로 줄이지 않습니다.

조건이 확인되지 않으면 가능한 표현 가운데 사실을 추가하지 않는 표현을 선택합니다. 그래도 의미를 결정할 수 없으면 원문과 불확실성을 기록하고 확인 요망으로 남깁니다.

## DEV-A02. 분열문과 논리 관계

초점이나 대조가 실제 정보인 경우에는 그 기능을 보존합니다. 목적을 별도 명사절로 감싼 문장은 목적과 동작을 직접 연결하고, 원인을 설명한 문장은 원인과 결과를 바로 연결합니다. 원문에 필요한 조건이 명시된 경우에만 의무나 필요조건을 나타내는 문장으로 바꿉니다.

| 교정 전 | 교정 후 | 판단 |
| --- | --- | --- |
| 재시도한 이유는 전송을 마치기 위해서입니다. | 전송을 마치도록 재시도했습니다. | 실행 목적과 시제를 유지합니다. |
| 요청을 거부하는 것은 권한이 없기 때문입니다. | 권한이 없으므로 요청을 거부합니다. | 원인과 결과를 유지합니다. |
| 요청을 보내는 데 필요한 것은 토큰을 등록하는 것입니다. | 요청을 보내려면 토큰을 등록해야 합니다. | 명시된 필요조건만 조건형으로 바꿉니다. |

앞 문장을 읽지 않고 특정 어미만 지우지 않습니다. 목적을 달성했다는 결과가 원문에 없으면 성공한 것으로 쓰지 않습니다.

## DEV-A03. 동작을 직접 설명하는 동사

명사와 보조적인 동사로 나뉜 서술을 구체적인 동사로 정리합니다. 입력은 검증하고, 스크립트는 실행하며, 설정은 저장하고, 요청은 처리합니다. 상태가 바뀌는 문장에서는 누가 상태를 바꾸는지 원문에서 확인합니다.

행위자가 없거나 상태 변화 자체가 초점이면 자연스러운 피동을 유지할 수 있습니다. 검증을 시작했다는 기록을 검증을 마쳤다는 기록으로 바꾸지 않으며, 실행 가능성·실행 중·완료·실패의 차이를 보존합니다.

## DEV-A04. 장소·수단·기준의 구분

겹친 조사와 추상적인 매개구를 찾고 문장이 실제로 표현하는 관계를 확인합니다. 장소는 위치나 실행 환경으로, 도구는 수단으로, 선택 규칙은 판단 기준으로 설명합니다. 원문에 있는 동작을 구체적인 동사로 쓰는 편이 더 분명하면 문장 구조를 조정합니다.

법령·계약·정의된 전문 용례의 고정 표현은 보존합니다. 정규식 일치만으로 실제 매개 경로나 출처 정보를 없애지 않습니다.

## DEV-C01. 문서의 역할과 증거 보존

현행 명세는 독자가 현재 구조·API 계약·운영 절차를 이해하고 따르는 문서입니다. 검증·인계 기록은 특정 실행에서 무엇을 확인했는지와 어떤 제한이 남았는지를 보존하는 문서입니다. 파일명만으로 역할을 결정하지 말고 각 절의 내용을 읽어 구분합니다.

명세에 붙은 실행별 기록은 저장소의 이력 문서나 증거 디렉터리로 옮깁니다. 날짜·경로·프로세스 번호·포트·컨테이너 값·명령·출력은 그대로 보존합니다. 원래 명세에는 현재 유효한 결론·제한과 실제 기록을 가리키는 링크를 남깁니다.

고정 서비스 포트, 기본 경로, 재현에 필요한 명령, 알려진 미검증 범위는 현재 계약의 일부일 수 있으므로 자동으로 걷어내지 않습니다. 원본 보존용 사본은 읽기 전용으로 분류하며, 편집 가능한 요약이나 색인을 별도로 작성합니다.

기록을 옮기거나 제목을 고치기 전에 기존 헤더와 명시적 앵커를 수집합니다. 기존 링크가 같은 위치나 적절한 안내에 도달하도록 호환 앵커를 유지합니다. 실제로 만들지 않은 기록 파일에 링크하지 않습니다.

## DEV-C02. 작업 세션 표현의 객관화

[빠른 규칙의 탐지 예문](quick-rules.md#dev-c02-객관적인-검증-범위)과 정본의 `patterns`를 모두 검사합니다. 제품 문서에 필요하지 않은 작업 도구의 대화 구분은 삭제하고, 검증 범위를 설명하는 정보는 검토 대상·실행 단계·실행 제약으로 정리합니다.

이 검토 범위에서 확인했다는 말은 다른 환경에서도 검증했다는 뜻이 아닙니다. 실행 정책 제한으로 거부된 작업은 실행되지 않은 상태로 남깁니다. 대체 방법으로 일부를 확인했더라도 원래 차단된 검사까지 통과했다고 쓰지 않습니다.

실제 제품 설정의 식별자와 변경 금지 출력은 원형을 유지합니다. 원시 증거를 고치지 않고 독자가 읽는 주변 설명에서 범위와 제약을 명확히 씁니다.

## DEV-E01. 문서 세트의 어미와 시제

사용자가 지정한 문서 세트를 하나의 단위로 봅니다. `docs/` 전체와 연결된 루트·테스트 안내 문서를 목록화하고, 본문과 문장형 표 셀을 모두 확인합니다. 명세의 현재형과 기록의 과거형은 각각 유지하면서 경어체를 맞춥니다.

짧은 명사구 표 셀·제목·라벨을 완결된 문장으로 늘릴 필요는 없습니다. 원시 출력·코드 주석·직접 인용은 별도로 보존합니다. 설명문이 백틱 안에 있다는 이유만으로 검사에서 제외하지 않습니다.

정본의 종결어미 정규식은 후보를 넓게 찾는 보조 수단입니다. 일치한 구간을 직접 읽어 본문인지 인용인지 분류합니다. 숫자나 단어의 일부를 잘못 잡았을 때는 문법 오류로 단정하지 않습니다. 일치하지 않더라도 해요체 등 다른 어미가 섞였는지 문서 전체를 읽어 확인합니다.

## DEV-S01. 압축 표기의 탐지와 보호

정본의 `spacing_patterns`에 등록된 네 가지 유형을 모두 검색합니다. 명사·부사와 숫자, HTTP 메서드와 상태 코드, 종료 값의 설명, 붙어 있는 수식어와 명사를 구분합니다. 모든 예제는 [빠른 규칙](quick-rules.md#dev-s01-압축-표기)에서 확인합니다.

숫자·부호·상태 코드·횟수는 그대로 두고 필요한 공백만 보완합니다. 원문에 단위가 빠져 있으면 문맥에서 확인한 경우에만 단위를 보충합니다. 확인되지 않은 수량을 건수나 사람 수로 단정하지 않습니다.

`v1`, `sha256`, `fwrun6`, `rcfield4`는 보호 예제입니다. 새로운 고유 식별자도 코드·API·설정의 실제 사용처를 기준으로 판단합니다. 영문과 숫자가 만나는 모든 곳을 자동으로 나누는 정규식은 사용하지 않습니다.

## 매핑과 확인 목록

아래 모든 ID를 처리 기록에 남깁니다. 수정이 없으면 확인한 범위와 유지한 이유를 기록합니다. 일부 파일이나 일부 ID만 확인하고 전체 점검으로 보고하지 않습니다.

- [ ] `DEV-A01`: 14개 용어군을 모두 확인하고, 기능·측정 대상·저장 방식에 맞는 표현만 선택했습니다.
- [ ] `DEV-A02`: 분열문을 직접 연결하면서 목적·원인·필요조건의 차이를 보존했습니다.
- [ ] `DEV-A03`: 동작을 명사로 감싼 문장을 구체적인 동사로 바꾸고 주체·시제·진행 상태를 유지했습니다.
- [ ] `DEV-A04`: 장소·수단·기준을 구분해 자연스러운 조사나 구체적인 동사로 연결했습니다.
- [ ] `DEV-C01`: 명세에는 현재 계약을 남기고 실행별 증거는 별도 이력 문서로 옮긴 뒤 유효한 링크를 연결했습니다.
- [ ] `DEV-C02`: 작업 도구의 대화 표현을 객관적인 범위·단계·제약으로 바꾸고 차단·미검증 상태를 유지했습니다.
- [ ] `DEV-E01`: 대상 파일을 전부 확인하고 본문과 완결된 문장형 표 셀의 어미를 경어체로 통일했습니다.
- [ ] `DEV-S01`: 모든 압축 표기 유형을 확인하고 숫자·상태 코드·식별자를 보존하며 필요한 공백만 보완했습니다.

규칙을 바꿀 때는 정본 JSON의 ID·정규식·사전·예제를 먼저 갱신한 뒤 네 진입 문서의 연결을 대조합니다. 교정 전 예문이 탐지되고 교정 후 표현과 보호 토큰이 오탐되지 않는지도 확인합니다.
