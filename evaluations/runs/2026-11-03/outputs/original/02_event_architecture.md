# Harbor Intake 이벤트 수집 서비스 아키텍처

Harbor Intake는 HTTP로 받은 이벤트를 Kafka에 발행하고, 별도 소비자인 `event-writer`가 PostgreSQL에 저장하는 비동기 이벤트 수집 서비스입니다. **`POST /v1/events`의 `202` 응답은 Kafka에 이벤트를 수락했다는 뜻이며, 데이터베이스 저장 완료를 뜻하지 않습니다.**

API 연동 시에는 같은 논리적 이벤트를 재시도할 때 같은 `event_id`를 사용해야 합니다. 전송과 소비 과정에서 중복 전달이 발생할 수 있으며, 최종 저장 단계에서 `event_id` 유일성 제약으로 중복 행 생성을 막습니다.

## 구성요소와 역할

| 구성요소 | 역할 | 처리 경계 |
| --- | --- | --- |
| `collector-api` | `POST /v1/events` 요청의 토큰과 스키마를 검사하고 Kafka에 이벤트를 발행합니다. | Kafka 발행을 확인한 뒤 `202`와 `event_id`를 반환합니다. API 자체에서는 중복 요청을 제거하지 않습니다. |
| Kafka 토픽 `telemetry.raw.v1` | API가 발행한 이벤트를 `event-writer`에 전달합니다. | 토픽에 수락된 이벤트와 데이터베이스에 저장된 이벤트는 구분해야 합니다. |
| `event-writer` | 토픽에서 이벤트를 읽어 `event_store`에 기록합니다. | 데이터베이스 트랜잭션이 성공한 뒤 Kafka offset을 커밋합니다. |
| PostgreSQL 데이터베이스 `event_store` | 이벤트를 저장합니다. | `event_id` 유일성 제약을 적용합니다. `event-writer`는 이 제약으로 확인한 중복을 이미 기록된 이벤트로 취급합니다. |

## 이벤트가 저장될 때까지의 흐름

### 1. 요청 검증

클라이언트가 `POST /v1/events`로 이벤트를 제출하면 `collector-api`가 토큰과 스키마를 확인합니다. 유효하지 않은 토큰에는 `401`, 스키마 오류에는 `400`을 반환합니다.

### 2. Kafka 발행과 수락 응답

검증을 통과한 이벤트를 `collector-api`가 `telemetry.raw.v1`에 발행합니다. Kafka 발행을 확인하면 클라이언트에 `202`와 `event_id`를 반환합니다. 발행에 실패하면 `503`을 반환합니다.

`202`를 받은 시점에 확인된 상태는 **Kafka 수락**입니다. `collector-api`는 `event-writer`의 데이터베이스 저장 완료를 기다려 응답하지 않습니다. 따라서 이 응답만으로 `event_store`에 이벤트가 있는지 판단하면 안 됩니다.

### 3. 데이터베이스 저장

`event-writer`가 `telemetry.raw.v1`에서 이벤트를 읽어 `event_store`에 기록합니다. 이미 기록된 `event_id`라면 유일성 제약으로 중복을 확인하고 추가 행을 만들지 않습니다.

### 4. Kafka offset 커밋

`event-writer`는 데이터베이스 트랜잭션이 성공한 뒤 Kafka offset을 커밋합니다. 이 순서는 저장에 실패한 이벤트를 다시 처리하기 위한 기준입니다. 데이터베이스 쓰기에 실패하면 해당 이벤트의 offset을 커밋하지 않습니다.

데이터베이스 기록과 offset 커밋은 별도 단계입니다. 기록을 마친 뒤 offset 커밋 전에 worker가 종료되면 같은 이벤트를 다시 읽을 수 있습니다.

## API 응답을 해석하는 방법

| 응답 | 의미 | 연동 시 처리 |
| --- | --- | --- |
| `202` + `event_id` | Kafka 발행을 확인했습니다. | 큐 수락으로 처리합니다. 최종 저장 완료로 표시하지 않습니다. |
| `400` | 이벤트 스키마가 올바르지 않습니다. | 요청 데이터를 스키마에 맞게 수정합니다. |
| `401` | 토큰이 유효하지 않습니다. | 인증 정보를 확인합니다. |
| `503` | Kafka 발행에 실패했습니다. | 같은 논리적 이벤트를 재시도할 때 같은 `event_id`를 사용합니다. |

현재 구현에는 **`event_id`로 최종 저장 상태를 조회하는 API가 없습니다.** 응답으로 받은 `event_id`는 저장 완료 확인 수단이 아닙니다. 연동 시스템에서 최종 저장 여부가 필요하다면, 현재 API만으로는 그 상태를 확인할 수 없다는 제약을 반영해야 합니다.

## 중복 전달과 중복 저장의 차이

Harbor Intake는 이벤트가 한 번만 전달된다고 가정하지 않습니다. 중복은 다음 경로에서 발생할 수 있습니다.

- 클라이언트가 같은 이벤트를 다시 제출합니다. `collector-api`는 중복 요청을 제거하지 않으므로 API 단계에서 재제출을 걸러 주지 않습니다.
- `event-writer`가 데이터베이스 기록 후 offset 커밋 전에 종료됩니다. 이후 같은 이벤트를 다시 읽어 처리할 수 있습니다.

중복 저장을 막는 기준은 `event_store`의 **`event_id` 유일성 제약**입니다. `event-writer`는 이 제약으로 확인된 중복을 이미 기록된 이벤트로 취급하고 추가 행을 만들지 않습니다. 중복 메시지 전달 가능성과 중복 행 방지는 서로 다른 성질입니다.

따라서 `event_id`는 다음 원칙으로 다룹니다.

- **같은 논리적 이벤트를 재시도할 때는 같은 ID를 사용합니다.** 재시도마다 ID를 바꾸면 `event_id` 유일성 제약으로 같은 이벤트인지 판별하지 못합니다.
- **서로 다른 이벤트에는 같은 ID를 재사용하지 않습니다.** 이미 저장된 ID와 충돌하면 `event-writer`가 중복 이벤트로 취급해 추가 행을 만들지 않습니다.

## 장애 시 재처리가 일어나는 위치

| 장애 상황 | 응답 또는 처리 상태 | 재처리 주체와 동작 |
| --- | --- | --- |
| `collector-api`의 Kafka 발행 실패 | 클라이언트에 `503`을 반환합니다. | 클라이언트가 같은 `event_id`로 다시 제출합니다. |
| `event-writer`의 데이터베이스 쓰기 실패 | 해당 이벤트의 offset을 커밋하지 않습니다. | 데이터베이스가 회복되면 `event-writer`가 미커밋 이벤트를 다시 처리합니다. |
| 데이터베이스 기록 후 offset 커밋 전 worker 종료 | 데이터베이스에는 기록이 있지만 offset 커밋은 끝나지 않은 상태입니다. | 같은 이벤트를 다시 읽을 수 있습니다. 이때 `event_id` 유일성 제약으로 중복 행 생성을 막습니다. |

클라이언트 재시도와 `event-writer` 재처리는 구분해야 합니다. Kafka 발행 실패는 API 연동 측에서 다루고, Kafka에서 읽은 뒤 발생한 데이터베이스 쓰기 실패는 `event-writer`가 미커밋 이벤트를 다시 처리하는 방식으로 복구합니다.

## 운영 시 확인할 경계와 미확정 항목

`202`를 받은 이벤트의 저장을 확인할 때는 API 응답만 보지 말고, `event-writer` 처리 상태와 `event_store` 기록을 확인해야 합니다. 특히 데이터베이스 기록과 Kafka offset 커밋 사이에서 worker가 종료됐는지에 따라 재처리 시 같은 이벤트를 다시 읽을 수 있습니다.

다음 운영 기준은 제공된 구현 자료에서 확정되지 않았습니다.

| 미확정 항목 | 운영에 미치는 영향 |
| --- | --- |
| Kafka 보존 기간 | 장애가 지속될 때 미처리 이벤트를 Kafka에서 언제까지 다시 읽을 수 있는지 판단할 기준이 필요합니다. |
| 공식 처리량 목표 | 유입량과 처리량이 목표를 충족하는지 판단할 기준이 필요합니다. |
| 장애 복구 시간 목표 | 장애 발생 후 어느 시점까지 복구해야 하는지 판단할 기준이 필요합니다. |

이 문서의 재처리 동작만으로 무기한 재처리나 특정 시간 안의 저장 완료를 약속하면 안 됩니다. 운영 인계 시 위 기준을 별도로 확정해야 합니다.
