# 모래결 색인 갱신기: 접수부터 검색 반영까지

모래결 색인 갱신기는 자료집의 문서를 검색할 색인을 만드는 내부 서비스입니다. 원본 업로드는 별도 시스템이 맡고, 이 서비스는 보관된 원본을 골라 색인을 갱신합니다. 검색에는 원본 대신 색인을 사용하며, 현재 검색에 사용하도록 지정된 색인 판을 **활성 판**이라고 합니다. 이 문서에 나오는 서비스와 사례는 모두 가상입니다.

갱신을 이해하려면 접수 성공, 작업 완료, 검색 결과가 각각 무엇을 뜻하는지 구분해야 합니다. 접수 성공은 작업 기록이 저장됐다는 뜻이고, 완료는 활성 판 전환이 확정됐다는 뜻입니다. 개별 검색 결과는 그 검색 요청이 시작될 때의 활성 판을 따릅니다. 먼저 구성 요소와 식별자를 살펴본 뒤, 갱신 과정과 실패·중단·재시도 시의 판단 기준을 이어서 설명합니다.

## 구성 요소와 식별자로 갱신 흐름 이해하기

갱신 요청은 접수 API에서 시작합니다. 접수 API가 요청을 기록하면 작업 조정기가 작업을 구축기에 넘깁니다. 구축기는 선택한 원본으로 아직 검색에 쓰이지 않는 후보 색인을 만들고 검증합니다. 조정기는 검증을 통과한 후보를 활성 판으로 반영하고, 조회 API는 활성 판을 사용해 검색합니다.

이 흐름에서 자료집, 원본, 작업, 색인은 서로 다른 식별자를 사용합니다.

| 식별자 | 예시 | 가리키는 대상 |
| --- | --- | --- |
| 자료집 번호 | `C17` | 갱신할 자료집 |
| 원본 번호 | `r18` | 갱신에 사용할 원본 |
| 접수 번호 | `q203` | 접수한 작업. 작업 상태를 조회할 때 사용합니다. |
| 색인 판 번호 | `i52` | 구축한 색인의 판 |

예를 들어 자료집 `C17`의 원본 `r18`을 갱신해 달라는 요청 `q203`이 색인 `i52`를 만들 수 있습니다. `r18`, `q203`, `i52`의 숫자는 각각 별도 순서이므로 서로 비교해 진행률이나 최신 여부를 판단할 수 없습니다.

## 접수할 원본을 정하고 작업 기록 저장하기

원본 번호는 내용이 고정된 한 묶음을 가리킵니다. `q203`이 `r18`로 접수됐다면 이후 `r19`가 올라와도 작업은 끝까지 `r18`을 사용합니다. 조정기나 구축기가 진행 도중 최신 원본으로 대상을 바꾸는 기능은 없습니다.

접수 API는 자료집이 존재하는지, 지정한 원본의 보관이 완료됐는지 확인합니다. 둘 중 하나라도 충족하지 않으면 이유를 돌려주고 작업 기록을 만들지 않습니다. 두 조건을 모두 충족해도 같은 자료집에 진행 중인 작업이 있으면 새 작업을 받지 않습니다. 이때는 `진행 중 작업 있음`과 진행 중인 작업의 접수 번호를 반환하며, 새 접수 번호는 만들지 않습니다. 이 제한은 같은 자료집에 적용되며 다른 자료집의 접수에는 영향을 주지 않습니다.

접수에 성공하면 작업 기록의 저장이 끝난 뒤 새 접수 번호와 `대기` 상태를 반환합니다. 이 응답으로 확인할 수 있는 것은 요청이 작업 목록에 들어갔다는 사실입니다. 구축 시작, 검증 성공, 활성 판 변경까지 보장하는 응답은 아닙니다.

접수 뒤에는 응답으로 받은 접수 번호로 작업 상태를 확인합니다. 앞의 예에서는 `q203`을 사용하며, 자료집 번호 `C17`이나 색인 판 번호 `i52`로 대신 조회할 수 없습니다.

## 작업 상태를 따라 반영 시점 확인하기

정상적인 갱신은 다음 순서로 진행합니다.

**대기 → 구축 중 → 검증 중 → 반영 대기 → 완료**

`완료`, `실패`, `중단`은 종료 상태입니다. `대기`, `구축 중`, `검증 중`, `반영 대기`는 모두 진행 중 상태이므로, 접수 뒤 이 상태들이 보인다면 아직 작업이 끝나지 않은 것입니다.

### 대기부터 검증까지: 후보 색인 준비

`대기`는 작업 기록은 있지만 구축기가 아직 시작하지 않은 상태입니다. 구축기가 선택한 원본으로 후보 색인을 만들기 시작하면 `구축 중`이 됩니다. 후보는 활성 판과 분리해 보관하므로, 일부 문서만 만들어진 후보가 검색 결과에 섞이지 않습니다.

`검증 중`에는 후보의 문서 수가 원본과 일치하는지, 원본에 지정된 두 확인용 문서가 정확한 키로 조회되는지 검사합니다. 이 조건을 모두 충족해야 다음 상태로 넘어갑니다. 검증 범위는 문서 누락과 기본 조회이며, 검증을 통과했다고 해서 검색 순위의 품질까지 평가한 것은 아닙니다.

### 반영 대기부터 완료까지: 활성 판 전환

`반영 대기`는 검증을 통과한 후보가 활성 판으로 전환되기를 기다리는 상태입니다. 조정기가 전환하기 전까지 조회 API는 기존 활성 판을 사용합니다. 따라서 검증 통과 기록이나 `반영 대기` 표시만으로 새 내용이 이미 검색된다고 안내하면 안 됩니다.

반영할 때 조정기는 자료집의 활성 색인 판 변경과 해당 작업의 완료 기록을 하나의 변경으로 함께 확정합니다. **`완료` 상태는 활성 판 전환이 확정됐음을 뜻합니다.** 접수 성공 응답은 이 확정까지 걸리는 시간을 약속하지 않습니다.

## 완료 상태와 검색 결과를 함께 읽기

작업이 완료됐는지와 개별 검색 응답이 어느 판을 사용했는지는 검색 요청의 시작 시점으로 연결됩니다. 조회 API는 검색 요청을 시작할 때 활성 판을 한 번 정하고, 응답을 마칠 때까지 그 판을 유지합니다. 같은 검색 요청 안에서 두 판의 결과를 섞지 않습니다.

기존 활성 판이 있는 자료집에서 새 판으로 전환한다면, 전환 시점을 기준으로 검색 결과를 다음과 같이 읽습니다.

| 검색 요청을 시작한 시점 | 검색에 사용하는 판 |
| --- | --- |
| 전환이 확정되기 전 | 기존 활성 판. 전환 뒤에 응답하더라도 구버전 결과일 수 있습니다. |
| 전환이 확정된 뒤 | 새 활성 판 |

앞의 예에서 `q203`이 `i52`를 반영했다면, 그 전환이 확정된 뒤 시작한 검색은 `i52`를 사용합니다. 새 판으로 검색되는지 확인하려면 작업의 `완료` 상태를 확인한 뒤 새로운 검색 요청을 시작합니다. 검색 응답이 도착한 시각만으로 사용한 판을 판단하지 않도록 주의해야 합니다.

한 번도 반영을 마치지 않은 자료집에는 기존 활성 판이 없습니다. 첫 갱신이 진행 중이거나 `실패` 또는 `중단`으로 끝났다면 조회 API는 `색인 준비 안 됨`을 반환합니다. 이는 검색 결과가 없는 정상 응답인 빈 목록과 구분해야 합니다.

## 실패와 중단이 검색에 미치는 영향

### 실패하면 오류 단계와 이유 확인하기

구축 또는 검증을 더 진행할 수 없는 오류가 나면 작업은 `실패`로 끝납니다. 상태 조회에는 오류가 발생한 단계와 이유가 남으므로 접수 번호로 이를 확인합니다. 실패한 후보는 활성 판으로 반영하지 않습니다.

기존 활성 판이 있었다면 조회 API는 그 판을 계속 사용합니다. 따라서 갱신 실패가 기존 검색의 중단을 뜻하지는 않습니다. 첫 갱신이었다면 사용할 활성 판이 없으므로 앞서 설명한 `색인 준비 안 됨` 상태가 이어집니다.

### 중단 요청을 수락한 뒤에는 실제 종료 기다리기

중단 요청은 `대기`, `구축 중`, `검증 중`에만 받습니다. `반영 대기` 또는 종료 상태인 `완료`, `실패`, `중단`에서는 거절합니다. 수락 가능 여부를 판단하는 기준은 사용자가 중단 버튼을 누른 시각이 아니라 **조정기가 요청을 확인한 시점의 작업 상태**입니다. 버튼을 누를 때 `검증 중`이었더라도 조정기가 확인할 때 이미 `반영 대기`라면 중단 요청은 거절됩니다.

중단 요청을 수락하면 먼저 중단 표시를 남깁니다. 조정기나 구축기가 그 표시를 확인해 작업을 멈춘 뒤에야 상태가 `중단`으로 바뀝니다. 그동안 상태 조회에는 직전 진행 중 상태가 보일 수 있으므로, 중단 요청의 수락과 실제 중단 완료를 구분해야 합니다.

중단 표시가 남은 후보는 검증이 끝나더라도 `반영 대기`로 넘어가거나 활성화될 수 없습니다. 기존 활성 판이 있는 자료집은 그 판으로 검색을 계속합니다.

새 갱신이나 재시도를 시작하려면 작업 상태가 실제로 `중단`으로 바뀌었는지 확인해야 합니다. 한 자료집에는 진행 중 작업을 하나만 허용하므로, 중단 요청을 수락했어도 아직 `중단` 상태가 아니면 그 작업이 자리를 차지합니다. 이때 새 갱신이나 재시도를 요청하면 `진행 중 작업 있음`과 기존 접수 번호를 반환하고 새 번호는 만들지 않습니다.

## 재시도할 원본과 새로 반영할 원본 구분하기

재시도는 `실패` 또는 `중단`으로 끝난 작업에만 요청할 수 있습니다. 수락되면 기존 작업 기록은 그대로 두고, 새 접수 번호로 `대기`부터 시작합니다. 재시도 역시 새 작업이므로 같은 자료집에 다른 진행 중 작업이 있으면 받을 수 없습니다.

재시도는 기존 작업과 같은 원본 번호를 사용합니다. 이전 후보나 문서별 진행 위치를 이어 쓰지 않고, 선택된 원본으로 처음부터 다시 구축합니다. 새 접수 번호가 생겨도 사용할 원본이 바뀌는 것은 아닙니다.

예를 들어 `r18`을 사용한 `q203`이 실패한 뒤 `r19`의 보관이 완료됐다고 가정해 보겠습니다. `q203`을 재시도하면 새 작업도 `r18`을 사용합니다. `r19`를 반영하려면 진행 중 작업이 없는 때에 `r19`를 지정한 일반 갱신을 요청해야 합니다. 같은 원본을 다시 처리할지, 다른 원본을 반영할지에 따라 요청을 선택합니다.

## 아직 정해지지 않은 동작

위에서 설명한 재시도 조건은 수동으로 재시도를 요청할 때 적용됩니다. 다음 항목은 아직 확정되지 않았습니다.

- 대기 시간의 상한
- 자동 재시도의 유무와 간격
- 실패·중단 후보의 보관 기간
- 반영 단계에서 오류가 발생했을 때의 복구 절차

접수 응답이나 작업 상태를 근거로 일정 시간 안의 완료 또는 자동 복구를 보장해서는 안 됩니다. 반영 단계의 오류 처리도 구축·검증 실패와 동일하게 동작한다고 가정할 수 없습니다.
