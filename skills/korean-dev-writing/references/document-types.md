# 문서별 구성

문서의 목적에 맞는 항목만 선택한다. 아래 소제목 흐름은 출발점이며 의무적인 목차가 아니다. 근거와 독자의 목적에 따라 필요한 항목을 선택하거나 합치고 순서를 바꾼다. 짧은 요청에는 짧게 답하고, 원자료가 없는 항목을 채우기 위해 기능이나 검증 결과를 만들지 않는다.

## README

첫 문단은 프로젝트가 무엇을 하는지 설명한다. 기술 스택은 프로젝트 이해나 실행에 필요한 위치에 둔다. 프로젝트의 현재 상태와 독자의 첫 행동을 우선하고, 자세한 설명은 실제로 존재하는 관련 문서로 연결한다.

| 프로젝트 유형 | 우선 배치할 정보 |
| --- | --- |
| 애플리케이션·서비스 | 용도, 주요 동작, 실행 조건, 첫 실행, 확인 방법 |
| CLI | 처리 대상, 설치 방법, 가장 작은 실행 예, 입출력과 옵션 |
| 라이브러리 | 해결하는 문제, 설치, 최소 사용 코드, 주요 계약과 제약 |
| 게임·엔진 프로젝트 | 프로젝트 목적, 확인된 엔진 환경, 여는 대상, 실행·조작 방법 |
| 학습·연구 프로젝트 | 탐구하는 질문, 재현 범위, 실행 자료, 확인한 결과와 한계 |

설치 명령, 패키지 관리자, 작업 경로, 실행 스크립트, 포트는 저장소 자료를 확인한다. 이미지·예시 파일·문서 링크는 존재할 때만 연결한다. 테스트한 버전과 지원한다고 명시된 범위를 구분한다. 모든 프로젝트에 개발 서버나 환경 변수 파일이 있다고 가정하지 않는다.

다음은 구조를 보여주는 템플릿이다. 대괄호 문구를 실제 정보로 바꾸고 불필요한 절은 제거한다. 확인하지 못한 명령은 생성하지 않는다.

[확인된 실행 조건과 작업 위치를 설명합니다.]

## PR 설명과 작업 보고

소제목 흐름 예: **변경 이유 → 핵심 변경 → 영향 범위 → 검증 상태와 결과**.

변경이 필요한 이유와 바뀌는 동작을 먼저 설명한다. 이어서 검토자가 판단할 수 있도록 핵심 변경, 영향 범위, 실제 검증 내용을 적는다. 사소한 변경에 같은 요약을 여러 절로 반복하지 않는다.

- 원인을 확인했으면 근거와 함께 적는다. 원인 조사용 변경이면 조사 중인 문제와 추가한 관찰 수단을 설명한다.
- 짧은 설명에서도 대상 시스템과 관측·검증의 한계를 구분한다. 원자료에 왜 현재 로그나 환경만으로 판단할 수 없는지가 있으면, 단순히 미확정이라고 줄이지 않는다.
- 호환성·설정·마이그레이션 영향은 자료에서 확인된 내용만 적는다.
- 테스트의 실행 여부, 범위, 결과를 구분한다. 실행하지 않은 테스트는 통과 체크박스로 표시하지 않는다.
- 배포 계획과 운영 반영 완료를 구분한다. 주어지지 않은 일정을 약속하지 않는다.

## 버그 리포트와 장애 기록

증상과 조건이 드러나는 제목을 붙인다. 확인된 발생 환경, 재현 순서, 기대 결과와 실제 결과, 관찰 근거를 적는다. 정확한 빈도를 모르면 횟수를 만들지 않는다.

원인을 모를 때도 기록을 완성할 수 있다. 조사 기록의 소제목 흐름 예: **관찰 → 조사한 가설 → 확인 방법과 결과 → 현재 판단 → 남은 확인**. 시도한 가설의 수나 조사 결말을 미리 정하지 않는다. 임시 완화와 근본 원인 해결을 구분한다.

## 아키텍처와 프로젝트 현황

소제목 흐름 예: **목적과 범위 → 구성 요소와 책임 → 데이터 흐름 → 의존성과 제약 → 장애 처리 경계**.

시스템의 목적과 문서가 다루는 범위를 먼저 밝힌다. 주요 구성 요소의 책임과 경계, 데이터의 이동, 외부 의존성, 중요한 제약을 설명한다. 기술 이름만 나열하는 구조 설명은 피한다.

- 구성 요소를 나열한 뒤 요청이나 데이터가 실제로 어떻게 흐르는지 연결한다.
- 설계 이유가 자료에 있으면 선택의 배경과 비용을 설명한다. 확인하지 않은 의도를 구현에서 역으로 단정하지 않는다.
- 현재 구현, 운영 설정, 제안된 변경을 구분한다. 서로 다른 시점의 정보를 하나의 현재 상태로 합치지 않는다.
- 장애·재시도·저장 책임 등 중요한 경계는 확인된 내용까지만 적는다.
- 관계를 이해하는 데 도움이 될 때만 도식을 사용한다. 도식에도 확인되지 않은 연결을 추가하지 않는다.

## ADR

소제목 흐름 예: **제안·결정의 상태와 요약 → 배경과 제약 → 검토한 선택지 → 선택 이유 → 결과·비용과 미결 사항**.

결정의 상태, 배경과 제약, 검토한 선택지, 결정과 이유, 결과와 감수하는 비용을 기록한다. 선택지가 하나만 기록돼 있으면 경쟁안을 만들지 않는다. 제안 단계의 결정을 채택 완료로 바꾸지 않는다. 선택하지 않은 대안은 자료에 있는 비교 기준으로 설명한다.

## 운영 절차

소제목 흐름 예: **적용 상황 → 준비와 조치 범위 → 단계별 실행·확인·중단 조건 → 복구 확인과 실패 시 대응**.

적용할 상황과 범위를 먼저 적고, 필요한 권한·준비 상태, 실행 순서, 확인 기준, 실패 시 중단·복구 조건을 정리한다. 독자가 필요한 정보를 찾을 수 있도록 점검과 상태 변경을 구분한다.

- 환경과 명령을 임의로 추정하지 않는다. 비밀 값 대신 자료에 있는 변수명이나 참조 위치를 사용한다.
- 각 단계에서 무엇을 확인하고 다음으로 넘어가는지 알려 준다. 성공 기준을 모르면 확인이 필요하다고 표시한다.
- 재시작·재실행·복구 절차가 제공되지 않았다면 일반적인 명령으로 채우지 않는다.
- 실제 실행한 점검과 문서상 제안하는 점검을 구분한다. 읽기 좋은 절차를 만들기 위해 운영 작업을 수행하지 않는다.

## API 안내와 튜토리얼

API 소제목 흐름 예: **사용 목적 → 인증과 입력 → 요청·응답 예 → 오류와 재시도 조건**.

API는 사용 목적, 인증·입력 계약, 요청과 응답 예, 실제 오류 동작을 연결한다. 필수·선택 필드, 기본값, 단위, 누락과 빈 값의 차이를 자료에 따라 적는다. 재시도·중복 처리·호출 제한은 확인된 계약만 설명한다.

초기 상태의 예외와 오류·거절 응답은 어떤 요청·조건에 대응하는지 함께 설명하고, 제목이나 항목명에서 그 위치를 찾을 수 있게 한다. 특정 사용 사례 안에만 일반적인 거절 기준을 남기지 않는다.

튜토리얼 소제목 흐름 예: **목표와 시작 조건 → 단계별 작업과 확인 → 최종 결과 확인**.

튜토리얼은 시작 조건부터 독자의 행동 순서로 구성한다. 코드가 들어갈 위치와 그 단계에서 확인할 결과를 알려 준다. 필요한 설명만 코드 앞뒤에 붙이고, 이미 설명한 코드를 문장으로 한 줄씩 반복하지 않는다.

## 기술 글과 회고

소제목 흐름 예: **핵심 내용 → 문제와 배경 → 주요 시도와 판단 → 결과와 한계**.

독자가 얻을 내용이나 현재 결론을 앞에서 밝힌다. 문제와 배경, 판단에 필요한 과정, 관찰 결과와 한계를 이어 쓴다. 탐색 과정을 모두 나열하기보다 결론을 이해하는 데 필요한 시도를 선택한다. 실패한 가설이나 교훈을 형식에 맞추려고 새로 만들지 않는다.
