# 의미 보존 평가 계약

v0.4.0 검증은 기존 여덟 사례의 필수 범위를 유지하면서, 한 사실 묶음 안에서 따로 빠질 수 있는 대상·조건·이유·검증 범위를 구분한다. 생성 전 마련한 전이 사례 두 개도 같은 계약으로 확인한다. 계약은 [preservation-v1.json](../evaluations/contracts/preservation-v1.json)에, 구조·무결성 검사는 [check_claims.py](../scripts/check_claims.py)에 있다.

이 계약은 과거 사례·입력·출력·리뷰·점수를 고치지 않는다. 과거 출력을 새 계약으로 다시 검토한 결과도 새 실행의 기록이다. 기존 20점 평가의 점수를 소급해서 바꾸거나 새 합계와 섞지 않는다. 계약 버전과 스킬 버전은 별개이며, 후속 스킬에서도 같은 계약을 사용할 수 있다. 기준을 바꾸면 새 계약 버전과 변경 이유를 기록한다.

## 기존 평가와의 관계

기본 여섯 사례의 `verifiable_claims`, `required`, `expected_checks.must_include`와 읽기 흐름 두 사례의 `must_preserve`, `reader_questions`가 출발점이다. 새 계약은 각 요구사항에서 원자료 ID와 이전 기준을 가리킨다. 선택 명제를 필수로 승격하지 않는다.

한 요구사항은 따로 누락되거나 약해질 수 있는 의미를 담는다. 예를 들어 관측의 대상 서비스, 기존 로그에서 발견한 순서, 그 순서만으로 실제 영향을 확정할 수 없는 이유, 환경 미비 때문에 하지 못한 검증은 서로 다른 판정 대상이다. 조건과 결과의 관계 자체를 단어별로 해체하지는 않는다.

포괄 요약이 필수 의미를 충분히 담으면 보존으로 인정한다. 원자료의 어순, 같은 단어의 반복, 항목별 열거를 강제하지 않는다. 원문에 없는 동작·수치·검증 결과를 추가하거나 조건을 뒤집는 문제는 별도로 검토한다. 기존 `forbidden_inventions`, `hard_fail_if`와 [rubric](../evaluations/rubric.json)의 치명성 정의도 원자료를 통한 검토 근거로 유지한다.

## 계약의 구성

사례 하나의 필드는 다음과 같다.

| 필드 | 의미 |
| --- | --- |
| `case_id` | 원자료와 일치하는 사례 ID |
| `source_path`, `source_sha256` | 원자료의 저장소 상대 경로와 원본 바이트의 SHA-256 |
| `input_path`, `input_sha256` | 생성자에게 전달할 입력 경로와 SHA-256 |
| `requirements` | 필수·선택 의미의 평가 목록 |
| `questions` | 답의 내용과 찾는 경로를 확인할 평가자 전용 질문 |

요구사항은 `id`, `source_refs`, `legacy_refs`, `required`, `meaning`, `literal_signals`를 갖는다. `source_refs`는 해당 사례의 실제 원자료 ID다. `legacy_refs`는 다음 표기만 사용한다.

| 표기 | 가리키는 기존 항목 |
| --- | --- |
| `verifiable_claims:PC5` | 기존 검증 명제 PC5 |
| `must_preserve:S07` | 기존 필수 보존 목록의 원자료 S07 |
| `must_include:3` | 기존 `expected_checks.must_include`의 0부터 세는 네 번째 항목 |
| `source_facts:S04` | 별도 필수 명제가 없는 선택 원자료 S04 |

이전 기준이 없는 전이 사례의 `legacy_refs`는 빈 배열이다. 검증기는 기존 필수 명제·필수 보존 ID·`must_include` 각각에 연결된 필수 요구사항이 있는지 확인한다. 연결이 있다는 사실만으로 의미의 분해가 적절하다고 판정하지는 않는다. 계약 작성 시 원자료를 읽어 그 범위를 검토해야 한다.

질문은 `id`, `question`, `requirement_refs`, `expected_answer`를 갖는다. 질문이 가리키는 모든 요구사항 ID가 실제로 존재해야 한다. 원자료에 답이 없는 정책을 정답으로 채우지 않는다. `meaning`과 `expected_answer`는 의미 대조 기준이며 출력이 그 문구를 복제해야 한다는 조건이 아니다. 특정 제목 문구, 표 개수, 문단 수를 정답으로 요구하지 않는다.

시스템의 실제 조건을 정확히 설명하고 사람의 확인 행위를 필요조건으로 추가하지 않으면 해당 구분은 보존이다. 확인 행위가 시스템의 조건이 아니라는 별도 부정문을 출력에 반드시 붙일 필요는 없다. 예를 들어 활성 판 선택이 전환 확정과 검색 요청 시작 시점으로 결정된다고 정확히 설명하면, 사람이 먼저 완료 상태를 조회해야만 새 판이 선택된다고 덧붙이지 않는 한 그 경계는 유지된다.

## 생성자와 평가자의 자료 분리

생성자에게는 독자, 목적, 사용자 요청, 원자료, 값이 있는 편집 원문과 해당 조건의 동결 스킬만 제공한다. 기존 입력을 재사용하는 사례는 원본과 동일한 바이트를 사용한다. 평가 계약, 필수 목록, 질문·정답, 이전 출력·리뷰, 사례별 개선 지시는 전달하지 않는다.

계약과 스킬을 출력 생성 전에 동결하고 해시를 기록한다. 사례·조건마다 새 컨텍스트에서 한 번 작성하며, 결과가 아쉽다는 이유로 재생성하거나 출력 후 편집하지 않는다. 출력이 아예 없는 도구 실패의 재시도는 횟수와 이유를 남긴다.

평가자는 원자료와 평가 기준, 무작위 라벨의 출력만 읽는다. 조건 대응표와 스킬 내용은 검토를 고정할 때까지 숨긴다. 질문에 대한 답과 위치를 기록한 뒤 원자료상 필요한 답과 대조한다. 같은 모델이 원자료까지 보고 수행한 검토는 실제 독자의 이해도·기억·탐색 시간 측정이 아니다.

이번 v0.4.0 실행에서는 기존 여덟 사례의 배포 v0.3.0 출력을 그대로 비교군으로 사용하고 후보 출력을 새로 만든다. 전이 사례 두 개는 두 스킬 조건에서 모두 새로 만든다. 따라서 새 출력은 12개이며 기존 사례의 조건들은 동시 생성 비교가 아니다. 단회 생성, 시점·플랫폼 차이, 같은 모델 계열의 생성·평가라는 한계를 함께 보고한다.

## 자동 검사 범위

기존 [check.py](../scripts/check.py)는 패키지·문서·기본 사례의 구조 검사 역할을 유지한다. `check_claims.py`는 다음만 자동 확인한다.

- 계약의 필수 필드, ID 중복, 원자료·기존 기준·질문의 참조 무결성.
- 원자료·생성 입력·출력의 SHA-256와 UTF-8 형식.
- 출력 목록과 여러 리뷰 파일 사이의 문서 누락·중복.
- 모든 필수 요구사항과 모든 질문에 대한 리뷰 행의 존재, 중복 및 상태값.
- 근거 인용이 해당 출력의 연속된 부분 문자열과 정확히 일치하는지.
- 계약에 지정된 문자열의 존재·부재와 원문 Unicode 문자 수.

문자열 신호의 `kind`는 `identifier`, `path`, `command`, `number`, `unit`, `service_name`, `literal` 중 하나다. 숫자·식별자·경로에는 ASCII 토큰 경계를 적용해 `1`을 `1000` 안에서 찾거나 짧은 옵션 이름을 다른 긴 옵션의 일부로 찾는 일을 피한다. 한국어 조사는 식별자의 일부로 취급하지 않는다. 그 밖의 문자열은 있는 그대로 찾는다.

표현이 동등한지, 문자열이 올바른 주체·조건·부정과 연결되는지, 단위 환산이 맞는지는 자동 판단하지 않는다. `5분` 대신 `300초`라고 쓰면 문자열 부재 신호가 나올 수 있지만 의미 판정은 별도다. 어떤 식별자가 없다는 신호만으로 선택 정보를 필수 누락으로 바꾸지 않는다. 정확한 문자열이 있어도 의미 보존이나 `hard_fail=false`를 보증하지 않는다.

문자 수는 공백·개행·Markdown 문법·마지막 개행을 포함한 Python `len(text)`다. 사용자 요청의 길이 조건을 사람이 검토할 때 쓸 보조 정보이며 자동 품질 점수가 아니다.

## CLI 사용법

CLI 상대 경로는 실행한 셸의 디렉터리와 무관하게 이 저장소 루트를 기준으로 해석한다. 계약 내부의 원자료·입력 경로와 출력 목록의 `path`도 저장소 상대 경로여야 하며 저장소 밖으로 나갈 수 없다. CLI 인수 자체에는 테스트용 외부 파일 등의 절대 경로도 사용할 수 있다.

계약만 검사할 수 있다.

```sh
python scripts/check_claims.py
python scripts/check_claims.py --contract evaluations/contracts/preservation-v1.json
```

출력 목록의 형식은 다음과 같다. `sha256`에는 실제 파일 바이트의 64자리 소문자 해시를 넣는다. `case_id`와 `label`의 쌍이 문서를 식별한다. 목록은 검토할 사례의 일부만 담을 수도 있다.

```json
{
  "documents": [
    {
      "case_id": "short_investigation_wait_log",
      "label": "doc-example",
      "path": "evaluations/runs/2026-11-03-v0.3.0-refresh/outputs/latest/08_short_log_pr.md",
      "sha256": "dd8ef1b809390a9fb72a39c30f7dfc68357926a9b430cb42ba8696ce4f2e4e6b"
    }
  ]
}
```

출력의 해시를 확인하고 문자열 신호를 기록한다. 아래 파일명은 새 실행에서 준비할 목록과 결과 경로의 예다.

```sh
python scripts/check_claims.py \
  --output-index evaluations/runs/2026-11-03-v0.4.0/output-index.json \
  --write-signals evaluations/runs/2026-11-03-v0.4.0/literal-signals.json
```

리뷰는 여러 파일을 한 번에 대조할 수 있다.

```sh
python scripts/check_claims.py \
  --output-index evaluations/runs/2026-11-03-v0.4.0/output-index.json \
  --reviews evaluations/runs/2026-11-03-v0.4.0/reviews/core.json \
            evaluations/runs/2026-11-03-v0.4.0/reviews/long.json \
            evaluations/runs/2026-11-03-v0.4.0/reviews/onboarding.json \
            evaluations/runs/2026-11-03-v0.4.0/reviews/transfer.json
```

제출한 리뷰들의 합집합이 출력 목록을 정확히 덮어야 한다. 한 문서를 여러 파일에 중복 제출하거나 항목별로 나눠 제출할 수 없다. 일부 묶음만 확인하려면 그 묶음의 문서만 담은 출력 목록을 사용한다. `--reviews`와 `--write-signals`에는 `--output-index`가 필요하다. 오류가 있으면 종료 코드 1, CLI 인수 오류는 2, 구조 검사를 통과하면 0을 반환한다. 부분보존·누락·충돌을 기록한 유효한 리뷰도 구조 검사는 통과할 수 있다.

신호 파일에는 계약·출력 목록 해시, 문서별 원문 해시와 문자 수, 요구사항별 문자열의 `present`만 기록한다. 의미 상태, 자동 점수, 자동 치명성 판정은 만들지 않는다. 검사에 오류가 있으면 신호 파일을 쓰지 않으며, 읽은 입력·출력·리뷰를 신호 파일로 덮어쓰는 경로는 거부한다.

## 의미 리뷰 JSON

최상위는 `documents` 배열이다. 각 문서는 `case_id`, `label`, `requirements`, `questions`, `hard_fail`을 갖는다.

모든 `required=true` 요구사항에 판정 행을 둔다. `required=false` 항목은 행을 생략할 수 있으며, 제출한다면 같은 네 상태로 기록한다. `omitted`라는 별도 상태는 없다. 포함된 선택 정보의 오류와 근거 없는 추가 사실은 묶음별 Markdown 리뷰에서도 확인한다. 선택 항목의 생략 자체를 필수 누락으로 처리하지 않는다.

| `status` | 의미 |
| --- | --- |
| `preserved` | 필요한 의미·조건·관계가 전달됨 |
| `partial` | 핵심 방향은 있으나 대상·이유·범위·조건 일부가 약해짐 |
| `missing` | 필요한 의미를 확인할 수 없음 |
| `conflict` | 원자료와 양립하지 않는 사실·조건·확정을 제시함 |

다음은 요구사항 행 하나의 예다. 배열 전체를 대신하는 완성 리뷰는 아니다.

```json
{
  "requirement_id": "S06.reason",
  "status": "partial",
  "evidence": ["실제 응답 유실·중복 처리 여부는 알 수 없고 빈도도 집계하지 않았습니다."],
  "reason": "실제 영향 미확정은 남았지만 로그 이름과 출력 순서라는 증거의 한계에 직접 연결하지 않는다."
}
```

`preserved`, `partial`, `conflict`에는 한 개 이상의 정확 인용이 필요하다. `missing`에는 `evidence: []`를 쓸 수 있다. 모든 행에 비어 있지 않은 `reason`을 적는다. 인용은 요약이나 말줄임표를 삽입한 재작성일 수 없으며 원문의 백틱·공백·개행도 그대로 보존한다. 여러 구절은 각각 별도 문자열로 넣는다. 검증기는 인용의 존재만 확인하며 그 인용이 판정을 뒷받침하는지는 평가자가 판단한다.

## 탐색·조건 위치·재환기 리뷰

모든 질문에 답의 내용과 위치를 기록한다. 답이 문서 전체에 있다는 판단과 특정 절에 진입한 독자가 조건을 함께 볼 수 있다는 판단은 구분한다.

```json
{
  "question_id": "SCOPE1",
  "answer_status": "sufficient",
  "entry_location": "마지막 검증 문단",
  "additional_locations": [],
  "local_condition_gap": "",
  "answer_evidence": ["로컬 합성 요청 환경이 준비되지 않아 테스트와 변경 후 로그 수집을 하지 못했습니다."],
  "reason": "미실행한 검증과 환경 미준비 이유를 같은 문단에서 확인할 수 있다."
}
```

`answer_status`는 `sufficient`, `partial`, `missing`, `incorrect` 중 하나다. `missing`을 제외하면 정확한 `answer_evidence`가 한 개 이상 필요하다. 답을 찾지 못한 경우 `entry_location`에 `찾지 못함`처럼 상황을 기록하고 인용은 빈 배열로 둘 수 있다.

`entry_location`은 첫 진입 위치이며 `additional_locations`는 답을 완성하기 위해 더 읽어야 하는 위치다. `local_condition_gap`에는 그 위치만 볼 때 빠지는 전제·예외를 적고, 없으면 빈 문자열로 둔다. 위치는 제목·문단·표 행 등을 설명하는 문자열이며 검증기가 그 탐색의 타당성을 판정하지는 않는다.

완료를 확인하는 절차가 실제 완료의 시스템 조건인 것처럼 바뀌지 않았는지, 재시도나 재개 단계에서 앞의 조건을 다시 볼 수 있는지도 필요한 질문으로 확인한다. 앞선 설명을 반복했다는 이유만으로 감점하지 않는다. 다른 판단 지점의 조건 재확인인지, 추가 정보 없는 재진술인지는 Markdown 리뷰에 근거와 함께 기록한다. 질문 수·절 이동 수·반복 횟수를 자동 점수로 만들지 않는다.

## 치명성 및 결과 보고

각 문서의 `hard_fail`은 `value` 불리언, 비어 있지 않은 `reason`, `evidence` 배열이다. `value=true`에는 최소 한 개의 정확 인용이 필요하다. false라면 빈 인용 배열을 허용하지만 판단 이유는 기록한다.

```json
{
  "value": false,
  "reason": "관측을 원인 확정이나 해결 완료로 바꾸지 않았으며 실시하지 않은 검증을 성공 근거로 내세우지 않는다.",
  "evidence": []
}
```

필수 항목의 부분보존·누락과 치명적 사실왜곡은 구분한다. 새 계약의 존재나 자동 검사 통과가 의미 보존 합격을 뜻하지 않는다. 반대로 구조 검사가 유효한 `conflict` 행을 받아들였다는 사실은 그 문서의 품질을 승인한 것이 아니다.

결과에는 필수 의미의 판정과 근거, 선택 정보·새 주장 검토, 질문별 답과 위치, 구조·문장 연결·재환기의 장단점, 치명성 판단을 함께 남긴다. 새 합계 점수를 만들지 않고 불리한 결과도 보존한다. 비교 조건은 모든 리뷰 JSON과 Markdown 보고서를 고정한 뒤 공개한다. 사람의 읽기 시간·기억·피로와 반복 생성의 안정성은 이 실행으로 측정한 것처럼 표현하지 않는다.
