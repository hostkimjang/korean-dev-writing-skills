# 장문 개발 문서 독립 검토

## 범위와 판정 기준

입력은 `packet-long.json` 하나다. 이 파일에 포함된 세 사례의 원자료, `verifiable_claims`, `expected_checks`와 익명 문서 세 편씩을 대조했다. 다른 저장소 파일, 이전 평가, 외부 자료를 사용하지 않았고 문서의 운영 명령을 실행하지 않았다. 출력 원문은 수정하지 않았다.

명제 판정은 다음 의미로 사용한다.

- **보존:** 필수 내용과 해당 조건·예외·상태가 문서 안에서 유지된다. 여러 절에 나누어 설명한 경우도 포함한다.
- **부분보존:** 핵심의 일부는 있지만 필요한 조건이나 범위가 빠져 의미가 약해진다.
- **누락:** 해당 필수 내용을 확인할 수 없다.
- **충돌:** 원자료와 양립하지 않는 내용을 말한다.

선택 명제는 별도로 확인하며 필수 명제로 승격하지 않는다. 원자료에서 도출되는 설명, 실행을 보조하는 기록 방법, 명시적으로 제안한 후속 검증 항목을 새로운 구현 사실이나 검증 결과와 구별했다. 문단 구성과 반복에 관한 평가는 실제 구절의 연결·배치에 대한 검토다. 독자의 이해도, 기억, 소요 시간이나 피로를 측정한 결과가 아니다. 길이 순위, 문서별 승자, 점수 합계는 만들지 않았다.

## 주요 발견

각 문서에서 필수 명제를 모두 확인했다. 필수 명제에 대한 부분보존·누락·충돌 판정은 없으며, 각 사례의 `hard_fail_if`에 해당하는 치명적 문제도 발견하지 못했다. 아키텍처 문서는 수락과 저장의 경계 및 재처리를, 운영 절차는 롤백·재개의 선행조건과 이관 기준을, ADR은 제안 상태와 복합 키·동일 트랜잭션·미결 사항을 유지한다.

차이는 주로 정보를 처음 제시하는 위치, 참조용 표와 본문의 역할 분담, 같은 조건을 다시 말하는 목적에 있다. 운영 명령 직전의 선행조건 반복은 그 자리에서 행동을 제한한다. 반면 이미 표로 설명한 내용을 바로 뒤 문단에서 거의 같은 범위로 다시 풀어 쓰는 부분은 추가 정보가 적기도 하다. 이런 차이를 사실 오류와 구별해 아래에 기록했다.

작은 표현상 문제로는 `doc-1b3a8d72`의 장애 표에서 이미 명시한 조건을 다시 가능성 표현으로 낮춘 문장, `doc-81666cd9`의 요청 처리 순서에서 생성과 신규·중복 분기의 관계가 압축된 부분이 있다. 문서 전체의 필수 명제를 뒤집지는 않는다.

# 1. 이벤트 수집 서비스 아키텍처

## 1.2 선택 명제와 추가 점검

AC7–AC9는 선택 명제다. 세 문서 모두 `401`/`400` 구별, Kafka 보존 기간·공식 처리량 목표·복구 시간 목표의 미확정 상태, `event_id`로 최종 저장 상태를 조회하는 API의 부재를 설명한다. 선택 명제가 없다는 이유로 결함을 부여한 경우는 없다.

세 문서 모두 `collector-api` 자체가 중복 요청을 제거하지 않는다는 A4의 범위를 보존한다. 재전달 가능성을 저장 행의 중복 방지와 구별하며, 전체 경로의 exactly-once를 주장하지 않는다. 상태 조회 API, 별도 중복 제거 서비스, dead-letter 토픽, 임의의 보존 기간·처리량·복구 시간 수치를 만들지 않았다. 서비스·구성요소·토픽·DB·경로·ID·HTTP 코드의 식별자도 유지한다.

`doc-1b3a8d72`의 “서로 다른 논리적 이벤트에 같은 ID를 재사용해서도 안 된다”는 A7의 ID 기반 판정에서 도출되는 연동 주의사항이다. 서로 다른 이벤트의 동일 ID를 식별할 별도 기능이 있다고 주장하지 않는다. `400`과 `401`에 대해 요청 내용·인증 정보를 확인하라는 응답 표도 원자료의 검증 실패 조건에 대응하는 조치 설명이다.

같은 문서의 Kafka 보존 기간 확인 이유와 무제한·정시 복구 보장을 경계하는 문단은 A8의 재처리와 A9의 미확정 값을 연결한 운영상 해석이다. 새 보존 설정이나 복구 보장을 제시하지 않는다. `doc-b5214855`의 각주는 “제공된 Harbor Intake 구현 메모 A1–A10”을 가리키며 패킷의 출처 범위와 일치한다. 각주가 없는 다른 문서를 그 이유로 사실상 열등하다고 판정하지 않는다.

**치명적 문제:** 세 문서 모두 발견하지 못했다. `202`의 의미를 뒤집거나, DB 기록 전에 offset을 커밋하도록 설명하거나, API가 모든 중복을 제거하므로 ID를 바꾸어도 된다고 안내하지 않는다.

## 1.3 문서별 연결·배치·반복 검토

### doc-6158b084

구성요소 표 다음에 정상 흐름을 두고, 그 직후 굵은 문장으로 `202`의 한계를 설명한다. 도입의 “API의 수락 응답과 데이터베이스 저장 완료 시점을 구분해야 합니다”가 실제 흐름의 응답 의미로 이어진다. 역할을 먼저 확인한 뒤 각 단계에서 누가 무엇을 하는지 대조할 수 있는 구성이다.

“중복 처리는 저장 단계에서 이루어집니다” 다음에 `event-writer`와 유일성 제약의 동작이 바로 붙는다. 이어 장애 표는 Kafka 발행 실패, DB 쓰기 실패, 기록 후 커밋 전 종료를 나눠 재처리 주체를 제시한다. 동일 ID 규칙을 본문과 Kafka 실패 행에 반복한 것은 일반적인 연동 규칙과 특정 장애 항목을 각각 참조할 수 있게 한다. 마지막 행의 “추가 행을 만들지 않습니다” 역시 장애 상황 안에서 중복 처리 결과를 확인하는 기능이 있다.

다만 HTTP 상태 코드별 독립 표는 없다. `400`·`401`은 정상 흐름 2에서, `503`은 흐름 3과 장애 표에서 찾아야 한다. 필수 내용을 빠뜨린 것은 아니며, 코드별로 찾아보는 용도에서는 문서의 흐름 절을 거쳐야 하는 배치상의 차이다. 최종 저장 상태 조회 API 부재도 별도 제목 없이 흐름 뒤 문단에 있다.

장애 표 뒤의 “데이터베이스 쓰기 실패 후의 재처리는 `event-writer`가 맡습니다”는 표를 재진술하지만, 바로 다음 문장에서 이 실패를 이미 반환한 `202`로 알 수 없다는 연결을 덧붙인다. 따라서 해당 문단 전체를 불필요한 반복으로 볼 근거는 약하다. 운영 전 확인 항목은 미확정 목록만 제시하므로, 각 값이 복구 판단에 어떤 영향을 주는지까지 찾으려면 본문의 재처리 설명과 연결해야 한다. 설명의 상세도 차이이지 미확정 사실의 누락은 아니다.

### doc-1b3a8d72

도입에서 수락·저장 경계와 조회 API 부재를 먼저 제시한다. 특히 “응답을 받은 시점에 이미 저장되었을 수도 있지만”이라는 구절은 저장 완료를 보증하지 않는다는 말이 곧 반드시 미저장 상태라는 뜻은 아님을 구분한다. 이 설명은 단계별 목록이 실제 응답 수신과 writer 실행을 엄격히 직렬화한 것처럼 읽힐 여지를 줄이는 문장이다.

요청 검증·Kafka 발행·DB 기록·offset 커밋을 각각 제목으로 나누고, “이 순서는 데이터베이스에 기록하지 못한 이벤트를 다시 처리할 수 있게 한다”에서 “다만 … 중단될 수 있는 구간”으로 이어진다. 순서의 이유와 그 순서만으로 중복 전달이 사라지지 않는 이유를 한 묶음으로 설명한다. 별도의 API 응답 표는 코드별 해석과 동일 ID 재시도를 찾는 참조 지점이다.

추가된 문단 중 “재시도마다 새 ID를 사용하면 … 이 중복 방지 장치가 적용되지 않는다”는 규칙을 다시 쓰는 데 그치지 않고 유일성 제약과의 인과관계를 설명한다. 끝의 운영 기준 표도 미확정 항목별 확인 목적을 새로 제공한다. 이런 추가 설명은 문서 길이만을 이유로 중복이라고 처리할 수 없다.

반면 `202` 해석은 도입, 구성요소의 처리 경계, 발행 절, API 표, 표 뒤 문단, 운영 시 경계 절에 걸쳐 반복된다. 응답 표와 운영 절의 독립 참조 기능은 있지만, “`event_id`를 반환받았다는 사실만으로 저장 완료를 확인할 수는 없다”와 이어지는 조회 API 부재 설명은 도입·발행 절과 겹치는 범위가 크다. 운영 절에서 새로 더하는 Kafka 발행·DB 기록·offset 커밋 확인 항목과 이 재진술 부분은 구별할 수 있다.

작은 정밀도 문제는 장애 표의 “데이터베이스 기록 후 offset 커밋 전에 worker 종료” 행에 있다. 이 조건 아래에서 상태를 “Kafka offset은 커밋되지 않았을 수 있다”라고 표현하여, 행 제목이 이미 규정한 미커밋 상태를 다시 가능성으로 낮춘다. 앞의 커밋 절은 순서와 중간 종료를 명확히 설명하므로 AC4를 부분보존으로 낮출 정도는 아니다.

### doc-b5214855

도입에서 `202`의 경계를 밝힌 뒤 역할 표와 세 단계 흐름을 제시한다. 흐름 3은 DB 기록과 offset 커밋을 함께 묶되 “저장과 offset 커밋은 이 순서로 진행됩니다”라고 순서를 보존한다. 단계 수가 적다는 이유로 순서가 생략됐다고 볼 수 없다.

API 응답 표와 재시도 규칙 다음에 실패 단계별 주체를 설명한다. 장애 표 직후의 “마지막 경우처럼 저장에 성공한 이벤트도 다시 소비될 수 있습니다”는 표의 특정 행을 가리켜 “offset이 커밋되지 않았다는 사실만으로 데이터베이스에도 이벤트가 없다고 판단할 수는 없습니다”라는 결론으로 이어진다. 이 문장은 표의 재전달 사실을 운영 해석과 연결하는 실질적인 추가 설명이다.

중복 처리 절 앞의 “저장 중복은 뒤에서 설명하는 … 처리로 막습니다”는 의도적인 예고다. 다만 예고와 상세 설명 사이에 장애 절이 있어, 저장 중복의 구체적인 처리만 찾는 경우에는 다음 절까지 이동해야 한다. 해당 이동이 필요한 구조라는 점과 정보 자체의 보존은 구별된다.

`202`는 도입, 흐름, 흐름 뒤 문단, 응답 표에 다시 나온다. 흐름 뒤 문단에는 조회 API 부재라는 추가 정보가 있고 응답 표는 코드별 참조 기능이 있으므로 모든 반복이 같은 역할은 아니다. 다만 흐름 2의 “이 시점에 확인된 것은 큐의 수락입니다”는 도입과 응답 표의 핵심 문장과 내용이 겹친다. 두 정보를 구분하라는 강조의 역할은 있으나 새로운 동작을 설명하는 문장은 아니다. 각주는 출처 범위를 표시하지만 개별 주장별 대응까지 제공하지는 않는다. 개별 각주를 요구하는 원자료 조건은 없으므로 결함으로 계산하지 않는다.

## 2.2 조건·명령·새 사실 점검

세 문서 모두 알람만으로 배포를 확정 원인으로 보지 않는다. `stable`을 미리 지정된 복구 대상 배포라고 설명하며 임의 버전이나 새 복구 대상을 만들지 않는다. 롤백 명령은 모두 `opsctl deploy rollback river-worker --to stable`이다. 조회·pause·resume 명령과 서비스·큐·알람·출력 필드도 원자료와 일치한다. `bash`와 `sh` 코드 블록 표시는 명령 내용의 변경이 아니다.

`doc-3b424e2a`의 표에 있는 `queue inspect`, `worker status`는 바로 위 전체 명령을 가리키는 축약 표제다. 실제 실행용 코드 블록에는 대상까지 포함한 전체 명령이 보존되어 있다. 이를 명령 훼손으로 판정하지 않았다.

5분은 pause 요청 시점, 10분은 소비 재개 시점을 기준으로 한다. 성공한 롤백 뒤에만 재개하며, 롤백 실패 시 정지 상태를 유지하는 예외가 빠지지 않았다. 큐 삭제·offset 초기화·강제 종료·자동 재시작을 새 복구 명령으로 추가하지 않았다.

pause 요청·재개 시각 기록, 큐 조회값 비교, 미확인 시각을 미확인으로 표시하는 방법은 주어진 시간 조건과 관찰 결과 이관을 구체화한 운영 보조 절차다. `doc-23696af5`가 이관 목록에 `changed_at`, 조회 필드, 진행 시각 등을 추가한 것도 실제 조회·행동으로 확보하는 정보의 기록 안내다. 새로운 시스템 기능이나 원자료에 없는 권한·책임자를 사실로 추가한 것은 아니다. “알람 발생 시각만으로 이를 대신 판단하지 않는다” 역시 배포와 적체 시작의 관계를 확인해야 한다는 O4에 부합한다.

**치명적 문제:** 세 문서 모두 발견하지 못했다. 정지 조건 중 하나만으로 롤백하거나, 실패한 롤백 뒤 resume하거나, 파괴적인 조치를 실행하거나, 배포와 적체의 관계를 확인하지 않고 무조건 롤백하라고 안내하지 않는다.

## 2.3 문서별 연결·배치·반복 검토

### doc-adee7cc9

도입에서 적용 대상, 원인 미확정, 수행하지 않는 조치를 모두 제시한다. 1단계는 조회와 롤백 판단을 함께 묶고, “다음 두 조건을 모두 확인한 경우에만 2단계로 진행합니다”로 분기를 끝낸다. 2단계의 “1단계의 롤백 조건을 충족했다면”은 앞선 판단을 다음 명령에 연결한다.

pause 블록 뒤에 접수 의미를 설명하고, 상태 조회 블록 뒤에 두 정지 조건과 5분 제한을 둔다. 3단계에서 `state=paused`·`inflight=0`을 다시 말하는 것은 이미 등장한 내용을 반복하지만, 롤백 명령을 실행하는 자리의 선행조건을 다시 규정한다. 같은 정보를 줄이라는 이유로 삭제할 근거는 없다.

롤백 실패 시 정지 유지·이관·재개 금지를 설명한 다음 “롤백 명령이 성공한 경우에만”과 resume 블록을 붙인다. 성공 분기의 조건과 실제 명령이 인접해 있다. 복구 단계도 “이후에도 명령을 다시 실행해 … 변화를 비교합니다”를 명시하므로 감소가 단일 조회값의 속성이 아니라 비교 결과라는 점을 설명한다.

이관은 마지막 한 목록으로 모으고 초기 분기에서 “5단계를 참고합니다”라고 연결한다. 반면 이관 사유 전체를 모은 별도 표는 없어서, 특정 중단 조건을 찾는 경우에는 관련 단계로 돌아가야 한다. 정보 누락은 아니며, 행동 순서로 읽는 구조와 중단 사유로 찾아보는 구조의 차이다. 1단계에 조회·출력·시각 비교·분기가 함께 있어, 제목 하나 아래에서 여러 역할을 수행한다는 점도 확인할 수 있다.

### doc-23696af5

조회, 롤백 판단, pause, 롤백·재개, 복구 판단, 이관을 독립 단계로 분리한다. 초기 표의 “복구 확인에 사용할 기준값을 남긴다”가 5단계의 “앞선 조회값과 비교한다”로 이어져 관찰의 용도가 연결된다. “두 조건 중 하나라도 충족하지 않았고 … 5분이 지나지 않았다”라는 상태 표는 대기와 이관을 구별하는 명시적인 분기다.

6단계의 이관 사유 표는 앞 단계의 실패 분기를 한곳에서 참조하게 한다. 다만 첫 행의 “롤백 조건을 충족하지 못했다”는 두 번째 행의 “`current`와 `stable`이 같다”를 이미 포함한다. 특정 경우를 따로 찾게 하는 효과와 별개로 두 행은 조건 범위가 겹친다. 새로운 이관 규칙이 늘어난 것으로 볼 수는 없다.

4단계의 성공·실패 목록은 의미상 정확하다. 그러나 성공 항목이 “아래 명령”을 가리킨 뒤 실패 항목이 나오고, 그 뒤에 resume 코드 블록이 놓인다. 코드 블록과 성공 조건 사이에 실패 분기가 끼는 배치이므로 두 분기 중 어느 쪽에 속하는지 문장을 따라 확인해야 한다. 실패 항목의 “소비를 재개하지 않는다”와 제목의 성공 조건이 명확하므로 잘못된 재개 지시나 OC5의 부분보존으로 판정하지는 않는다.

금지 조치는 문서 마지막 독립 절에 모여 있다. 세 조치를 빠뜨리지 않았지만 `doc-adee7cc9`·`doc-3b424e2a`처럼 처음부터 제약을 제시하는 배치와는 다르다. 이것을 형식 취향만으로 오류라고 할 수는 없다. 마지막 이관 목록은 원자료의 필수 네 종류를 포함하면서 진행 시각·마지막 상태까지 구체화하여, 단순 재진술과 실제 기록 범위의 확장이 함께 있다.

### doc-3b424e2a

초기에 금지 조치를 제시하고, 큐·worker 조회와 배포 조회를 별도 단계에 둔다. 1단계의 `oldest_age_seconds` 설명은 뒤의 복구 판단을 예고하며, 2단계가 `changed_at`과 적체 시작 시각의 비교를 롤백 조건에 연결한다. 조회 명령을 용도별로 분리하면서도 판단에 필요한 원자료 필드를 유지한다.

정지 조건은 3단계에 코드 형태로 명시하고 4단계 앞에서 “일시정지 상태와 처리 중인 작업이 없음을 모두 확인했다면”이라고 의미를 다시 말한다. 식별자를 반복하지 않은 문장도 앞 단계의 두 조건을 가리키며, 하나의 조건으로 축소한 것은 아니다. 실패 시 정지 유지·이관 뒤에 성공한 경우에만 재개한다는 문장과 코드가 바로 이어진다.

작은 실행 안내 차이는 반복 관찰이다. 3단계는 상태를 “다시 확인”하고, 5단계는 큐 상태를 “관찰하며” 감소를 확인하라고 한다. `doc-adee7cc9`·`doc-23696af5`처럼 반복 조회와 이전 값 비교를 별도 문장으로 풀지는 않는다. 필요한 두 조건과 5분·10분 기준은 명확하므로 정지 또는 복구 조건 누락은 아니지만, 관찰을 반복하는 구체적인 동작은 상대적으로 덜 명시적이다. 원자료에 없는 폴링 간격을 요구하는 평가는 아니다.

마지막 이관 절은 필수 정보와 이관 사유 예시를 함께 모은다. 각 단계의 이관 문장에 절 번호 참조는 없지만 “플랫폼 온콜 이관 시 전달할 내용”이라는 제목이 같은 행동을 명시한다. 끝의 이관 사유 나열은 앞 단계의 조건을 반복하되 무엇을 전달할지 설명하는 역할을 한다. 모든 이관 사유를 다시 자세한 절차로 쓰지는 않는다.

# 3. 이벤트 중복 판정 저장소 ADR

대조 원자료는 D1–D9, 필수 명제는 DC1–DC6이다. 문서는 `doc-81666cd9`, `doc-2cdba188`, `doc-17330007`다.

## 3.2 선택 명제·제안 상태·보장 범위 점검

선택 명제 DC7은 세 문서 모두 보존한다. DB 작업 실패 시 `503`을 반환하고 같은 `tenant_id`와 `event_id`로 재시도한다. 선택 명제를 의무화하여 다른 평가 항목을 늘리지 않았다.

`expected_checks.must_include`의 운영 책임 주체도 세 문서 모두 “승인 전에 결정할 사항”에 미결 항목으로 둔다. 담당자를 임의로 확정하지 않는다. `ADR-007`, `2026-10-15`, `event_receipts`, 필드 이름, 복합 키 표기, PostgreSQL·Redis·TTL·503 식별자도 보존한다.

어느 문서도 Redis가 언제나 데이터를 잃는다거나 중복 판정에 사용할 수 없다고 일반화하지 않는다. 키의 TTL 만료·유실 뒤 과거 이벤트가 들어오는 경우와 PostgreSQL 업무 이벤트 생성과의 원자성 문제를 비교한다. 과거 이벤트 대상 요구사항을 유지하면서 보존 기간이 미정임을 구분하며, PostgreSQL 역시 기록 보존과 정리 정책이 필요하다고 한다.

성능 우위, 지연 수치, 비용 절감 수치, 보존 기간 수치는 새로 만들지 않는다. `doc-81666cd9`의 “일반 요청, 동일 키 재시도, 과거 이벤트 재반입, 기록 정리 작업”과 측정 항목은 원자료보다 구체적이지만 “포함하는 방안을 제안한다”, “확정된 성능 목표나 검증 결과는 아니다”라고 명시한다. 검증 계획을 위한 제안이지 이미 수행한 측정이나 승인된 목표로 바뀐 것이 아니다.

같은 문서의 “함께 커밋되거나 함께 롤백”은 D4의 동일 트랜잭션에서 도출한 설명이고, 기록 삭제 후 `event_receipts`만으로 과거 처리 여부를 알 수 없다는 문장은 보존되는 판정 키의 범위에 관한 해석이다. 이를 외부 부수효과까지 포함하는 exactly-once 보장으로 확대하지 않는다. “이번 제안에서는 Redis와 TTL 방식을 채택하지 않는다” 역시 제안 내부에서 선택하지 않는 대안을 말하며, 상단·본문·말미의 미승인 상태와 양립한다.

**치명적 문제:** 세 문서 모두 발견하지 못했다. 승인 완료로 상태를 변경하거나, tenant를 제거한 전역 ID 유일성을 채택하거나, 독립 저장 작업 두 개에 동일 트랜잭션의 원자성을 부여하지 않는다.

## 3.3 문서별 연결·배치·반복 검토

### doc-81666cd9

상단 상태 표 뒤에 tenant 범위와 과거 이벤트 요구사항을 먼저 설명하고 제안을 제시한다. 제안 직후 “함께 커밋되거나 함께 롤백”이라는 문장을 두어 두 기록을 같은 트랜잭션으로 묶는 이유를 설명한다. 이어 제안 이유, 대안 비교, 보장 범위·비용, 승인 전 결정 사항으로 이어진다.

“별도 Redis 운영을 추가하지 않아도 된다” 다음에 “운영 부담이 없어지는 것은 아니다”와 기존 PostgreSQL에 추가되는 부담을 둔 것은 이점과 비용을 바로 연결한다. 대안 표에서도 PostgreSQL의 보존·정리 정책 필요성을 함께 적어, TTL이 있다는 사실만으로 Redis 전체를 부정하거나 PostgreSQL에 무기한 중복 판정이 자동으로 생기는 듯한 설명을 피한다.

요청 처리 목록에는 작은 분기 모호함이 있다. 1번 “중복 판정 기록을 생성한다” 뒤에 2번 “새 키라면”, 3번 “이미 존재하는 키라면”이 나온다. 이 목록만 보면 기록 생성 시도와 신규·중복 판정의 관계가 압축되어 있고, 분기별 행동이 연속 단계처럼 제시되어 있다. 다만 바로 위 문장에 동일 트랜잭션이 있고, 3번은 중복 키에 업무 이벤트를 만들지 않는다고 명확히 말한다. 중복 기록을 실제로 중복 생성한다거나 두 독립 트랜잭션을 쓰겠다는 충돌은 아니다. 충돌 처리 SQL이나 중복 응답 코드는 원자료에도 없으므로 이를 보충하지 않았다는 이유로 결함을 부여하지 않았다.

중복 방지 범위를 기록 보존에 연결하는 설명은 배경, 제안 이유, 대안 표, 보장 범위, 승인 전 표에 반복된다. 보장 범위 절의 “기록을 삭제하면 … 이전 처리 여부를 확인할 수 없다”는 조건의 결과를 새로 설명하고, 승인 전 표는 이를 결정 사항으로 바꾼다. 이 반복에는 서로 다른 기능이 있다. 반면 “데이터베이스 실패 시 재시도가 필요하다” 소절의 `503`·동일 ID 설명은 제안 목록 4번과 거의 같은 처리 규칙을 별도 참조 위치에 다시 둔다. 추가 계약을 설명하는 부분은 아니다.

마지막 성능 검증 계획은 기존 미결 사항을 실행 가능한 리뷰 항목으로 구체화한다. 무엇을 측정할지 제안한 문장과 아직 측정하지 않았다는 문장이 분리되어 있어 제안과 결과를 구별할 수 있다. 다만 같은 트랜잭션과 별도 Redis 운영 불필요라는 이유는 제안·선택 이유·대안 표 등 여러 위치에서 다시 등장한다. 각 절의 독립 참조 용도와 순서대로 읽을 때의 내용 중첩이 함께 있다.

### doc-2cdba188

메타데이터 바로 뒤에 저장소, 복합 키, 동일 트랜잭션, 주된 이유를 요약한다. 배경을 읽기 전에 검토 대상 제안을 확인할 수 있고, 배경에서는 서로 다른 tenant의 같은 ID 허용과 과거 이벤트 요구사항으로 그 제안의 범위를 설명한다.

처리 방식은 “새 키”, “중복 키”, “데이터베이스 작업 실패”를 병렬 원칙으로 제시한다. 이를 모두 순서대로 실행해야 하는 단계로 적지 않아 분기 범위를 문장 자체에서 구별할 수 있다. 대안 표 뒤에는 요구사항을 다시 가져와 원자성과 과거 이벤트 재수집이 왜 선택 근거인지 설명한다. 표의 항목 나열을 판단 근거에 연결하는 기능이다.

“다만 이 방식도 보존 정책이 정해져야 중복 판정의 시간적 범위를 확정할 수 있다”가 바로 다음 비용·검증 한계 절의 기록 정리 부담으로 이어진다. 보존 문제를 Redis에만 부과하지 않는다. 마지막 표는 보존 정책, 성능 검증 계획, 운영 책임 주체를 각각 리뷰의 결정 사항으로 제시한다.

찾아보기 관점에서 보장 범위는 독립 제목으로 분리되기보다 배경·대안 뒤 문단·비용 절에 나누어 있다. 내용은 모두 보존되지만 시간적 범위만 확인하려면 “보존 정책” 설명들을 연결해서 읽어야 한다. 별도의 보장 범위 절이 반드시 있어야 한다는 요구는 없다.

재수집과 보존 정책의 관계는 배경, 대안 표, 표 뒤 해석, 비용 절, 마지막 표에서 거듭 등장한다. 마지막 표는 결정할 행동을 지정하므로 앞 설명과 역할이 다르지만, 대안 표의 만료 조건을 뒤 문단에서 다시 풀어 쓰는 부분에는 겹치는 내용이 있다. 도입 요약과 제안 절의 복합 키·같은 트랜잭션 반복도 요약과 상세의 관계로 이해할 수 있으며, 문서 길이만으로 낭비라고 판정하지 않는다.

### doc-17330007

도입 요약은 저장소와 선택 이유를 제시하고, 정확한 복합 키는 배경의 tenant 구분과 설계 절에서 제시한다. `doc-2cdba188`처럼 요약부터 복합 키를 모두 적지는 않지만 문서 전체에 요구 범위가 명확하다. 배경에서 보존 기간 미정임을 알린 뒤 비용과 보장 범위 절에서 그 의미를 설명하는 연결이 있다.

대안 표는 원자적 처리, 과거 이벤트 재수집, 운영 영향을 같은 기준으로 비교한다. 뒤의 “이 API는 업무 이벤트를 이미 PostgreSQL에 저장하고 있으므로”가 기존 저장소와 선택 이유를 연결한다. 비용·검증 상태·기록 보존에 따른 보장 범위를 한 절에 모아, 도입 부담과 미확정 보장을 인접해서 확인하게 한다.

작은 국소적 한계는 대안 표 뒤의 “Redis 방식은 과거 이벤트 재수집 시 중복을 놓칠 수 있고”라는 요약이다. 이 문장 자체에는 TTL 만료·키 유실 조건이 반복되어 있지 않다. 앞 표의 “TTL 만료 또는 키 유실 뒤”가 조건을 정확히 제공하므로 문서 전체에서 DC4가 훼손된 것은 아니다. 다만 요약 문장만 따로 인용하면 원자료보다 조건이 덜 드러난다.

같은 트랜잭션과 별도 Redis 운영 불필요라는 근거는 요약, 설계, 대안 표, 표 뒤 문단에서 반복된다. 설계 절은 구현 범위를, 표는 비교를 제공하지만 표 뒤의 동일 트랜잭션 설명에는 이미 나온 선택 이유와 중첩되는 부분이 있다. 반대로 보존 미정이라는 배경 문장은 뒤의 “어느 기간까지 … 보장할지 확정하지 않는다”에서 결과로 이어지므로 단순한 동일 문장의 반복은 아니다.

승인 전 사항은 굵은 항목명으로 구별한 목록이다. 다른 두 문서의 표와 형식은 다르지만 보존·성능 검증·운영 책임의 세 미결 영역이 모두 드러난다. 구체적인 검증 시나리오나 담당자 이름을 확정하지 않은 것은 원자료의 미결 상태에 맞으며, 더 자세한 제안이 없다는 이유로 필수 누락으로 처리하지 않았다.

# 4. 사례 간 관찰과 해석의 한계

아키텍처에서는 동일한 사실이 정상 흐름, 응답 코드, 장애 상황이라는 서로 다른 진입점에서 쓰인다. 예를 들어 `202`와 동일 ID 재시도를 응답 표에서 다시 말하면 해당 응답만 찾아보는 참조 지점이 생긴다. 그와 별개로 같은 제목 아래에서 결론을 여러 번 재진술하는 문장은 새로운 판단 근거를 더하지 않을 수 있다. 이 둘을 반복 횟수만으로 합치지 않았다.

운영 절차에서는 상태 조건이 명령 실행 가능 여부를 결정한다. pause 뒤와 rollback 직전에 두 정지 조건을 다시 제시하거나, 실패 뒤 resume 금지를 명시하는 반복은 행동 경계를 유지한다. 중단 조건을 마지막에 모은 표는 별도의 참조 목적을 갖지만, 포괄 조건과 그 하위 사례를 별도 행으로 적으면 범위가 겹칠 수 있다. 이 차이는 내용의 진위와 별도로 볼 필요가 있다.

ADR에서는 제안 요약, 비교 근거, 감수할 비용, 미결 결정을 각각 찾아볼 수 있어야 한다. 같은 보존 정책이 배경에서는 요구 범위, 비교에서는 대안의 조건, 승인 전 목록에서는 결정 항목으로 작동한다. 구체적인 검증 항목이 늘어났더라도 제안이라고 표시하면 측정 결과를 지어낸 것과 다르다. 반대로 요약에서 조건을 생략한 문장은 본문에서 조건을 보존하더라도 단독 인용 시 덜 정확할 수 있다.

이 검토로 확인한 것은 제공된 원자료와 문서 사이의 의미 보존 및 표현 구조다. 실제 시스템의 구현, 명령 실행 결과, 실제 독자의 수행 속도·이해·기억·피로는 확인하지 않았다. 발견한 작은 표현상 모호함과 정보 배치의 제약은 위에 구체적으로 기록했으며, 이를 근거로 새 점수를 만들거나 특정 문서를 우승시키지 않았다.
