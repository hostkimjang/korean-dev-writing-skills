## 배경

관련 이슈: #184

운영 로그에서 같은 `job_id`가 두 번 발송된 사례를 확인했습니다. 로컬에서는 아직 안정적인 재현 방법을 찾지 못해, 운영에서 발생하는 중복 사례를 대조할 수 있도록 진단 로그를 추가합니다.

발송 작업이 길어져 lock TTL이 먼저 만료되는 상황을 원인 후보로 보고 있습니다. 다만 실제 원인인지는 아직 확인하지 못했습니다.

## 변경 내용

`src/workers/deliver.ts`에 `delivery_retry_probe` 진단 로그를 추가합니다.

- 기록 필드: `job_id`, `attempt`, `lock_owner`
- 활성화 조건: `DELIVERY_DIAG_ENABLED=true`일 때만 출력하며, 기본값은 `false`입니다.
- 수신자 주소와 메시지 본문은 기록하지 않습니다.

이번 PR의 범위는 원인 조사를 위한 로깅입니다. 발송 순서, 재시도 횟수, lock TTL 값, 중복 방지 동작은 그대로 유지하며, 중복 발송을 해결하는 수정은 포함하지 않습니다.

## 검증

`tests/workers/deliver-log.test.ts`에서 진단 로그의 조건부 출력과 기록 필드를 검증했습니다. 아래 명령을 로컬에서 실행했고 통과했습니다.

```sh
pnpm exec vitest run tests/workers/deliver-log.test.ts
```

스테이징의 실제 발송 경로는 아직 검증하지 않았습니다. 진단 로그를 활성화했을 때의 처리량과 지연 변화도 측정하지 않았습니다.

## 리뷰 요청

- `job_id`, `attempt`, `lock_owner`가 중복 사례를 구분하는 데 충분한지 확인 부탁드립니다.
- 수신자 주소나 메시지 본문이 로그에 섞일 여지가 없는지 확인 부탁드립니다.

## 배포 후 확인

배포 후 `DELIVERY_DIAG_ENABLED=true`로 진단 로그를 활성화해 중복 사례의 `job_id`, `attempt`, `lock_owner`를 대조할 예정입니다. 조사 결과를 #184에 정리한 뒤 수정 방향을 결정하겠습니다.
