## 배경과 목적

운영 로그에서 같은 `job_id`가 두 번 발송된 사례를 확인했습니다(#184). 로컬에서는 아직 안정적인 재현 방법을 찾지 못해, 이번 PR에서 발송 worker에 진단 로그를 추가해 원인 조사에 필요한 정보를 수집하려 합니다.

발송 작업이 길어져 lock TTL이 먼저 만료되는 경우를 원인 후보로 보고 있지만, 실제 원인인지는 확인하지 못했습니다.

## 변경 범위

`src/workers/deliver.ts`에 다음 진단 로그를 추가합니다.

- 로그 이름은 `delivery_retry_probe`이며, `job_id`, `attempt`, `lock_owner`를 기록합니다.
- `DELIVERY_DIAG_ENABLED=true`일 때만 진단 로그를 출력합니다. 이 설정의 기본값은 `false`입니다.
- 수신자 주소와 메시지 본문은 기록하지 않습니다.

발송 순서, 재시도 횟수, lock TTL 값, 중복 방지 동작은 변경하지 않습니다. 중복 발송을 해결하는 수정도 포함하지 않습니다.

## 검증 결과

`tests/workers/deliver-log.test.ts`에서 진단 로그의 조건부 출력과 기록 필드를 검증했습니다. 아래 명령을 로컬에서 실행해 통과했습니다.

```sh
pnpm exec vitest run tests/workers/deliver-log.test.ts
```

스테이징에서 실제 발송 경로는 검증하지 않았습니다. 진단 로그를 켰을 때 처리량과 지연이 어떻게 달라지는지도 아직 측정하지 않았습니다.

## 배포 후 확인 계획

배포 후 진단 로그를 켜서 중복 사례의 `job_id`, `attempt`, `lock_owner`를 대조할 예정입니다. 결과를 이슈 #184에 정리한 뒤 수정 방향을 결정하려 합니다.

## 리뷰 요청

- 수신자 주소나 메시지 본문이 로그에 섞일 여지가 없는지 확인해 주세요.
