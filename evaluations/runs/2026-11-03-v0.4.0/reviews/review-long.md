# long 익명 문서 정성 검토

## 범위와 판정 기준

검토 근거는 지정된 long.json 패킷의 원자료, 요청, 사전 의미 기준, 독자 질문, 익명 문서 A/B뿐이다. 다른 자료나 조건 대응표를 사용하지 않았다. 사례마다 두 문서를 원자료와 각각 대조했으며 라벨이 어떤 작성 조건인지 추정하지 않았다.

세 사례의 A/B 모두 필수 의미를 보존한다. 문서에 포함된 선택 항목에서도 원자료와 충돌하는 내용을 찾지 못했다. 수락과 저장의 경계, 롤백 전 복합 조건, 제안의 승인 상태처럼 사용·운영·검증 판단을 뒤집는 변화가 없어 hard_fail은 모두 false다. 전체 문서에 사실이 있는지와 특정 절에서 그 사실을 바로 찾을 수 있는지는 별도로 기록했다.

JSON의 요구사항 판정은 문서 전체의 의미 보존을 다룬다. 질문의 partial은 요청한 독립 진입 위치에서 답이 일부만 보이는 경우로 제한했다. 운영 절차 NAV1은 롤백 명령 절에 대기 한계가 없어 partial이지만, 앞 정지 단계에는 그 조건이 있어 요구사항 누락이나 hard_fail로 확대하지 않았다. 다른 질문은 표시한 추가 위치를 통해 답이 완성되는지를 설명하고, 국소 전제가 흩어진 경우 local_condition_gap에 적었다.

## 길이 기준

세 user_prompt 모두 한국어 Markdown이나 명령 코드 블록 등 형식을 요청하지만 글자 수 상한·하한을 요구하지 않는다. 패킷의 length_guidance는 공백 포함 600–1000자를 suggested 범위로 두고 scoring=false로 표시한다. 따라서 아래 분량은 참고 범위를 넘지만 사용자 길이 요구 위반으로 판정하지 않는다.

## event_architecture — 이벤트 수집 아키텍처

### 문서 A

**의미 보존과 설명 연결.** 수락과 저장을 먼저 구별하고, 요청 검증과 큐 수락 다음에 DB 기록과 offset 커밋을 배치한다. 실제 저장 주체와 처리 순서가 분명하다.

> Kafka에 발행된 이벤트는 API 응답과 별개로 `event-writer`가 소비합니다. `event-writer`는 이벤트를 `event_store`에 기록하고, **데이터베이스 트랜잭션이 성공한 뒤 Kafka offset을 커밋합니다.**

이 구절은 응답 확인과 DB 쓰기를 별도 단계로 이해하게 하는 충분한 근거다. 독자가 응답을 확인해야 저장된다는 필요조건을 더하지 않으므로, 확인 행위가 저장을 완료시키지 않는다는 부정문을 따로 요구하지 않았다. 이어지는 커밋 전 종료 설명이 왜 다시 읽힐 수 있는지를 연결한다.

**찾아보기.** 「저장 장애와 중복 처리」는 식별자 유지 이유를 먼저 적고 같은 절의 표에서 DB 기록 후 재전달을 다룬다.

> 중복 여부를 판단하는 기준이 `event_id`이므로, 클라이언트 재시도에서도 같은 식별자를 유지해야 합니다.

> | 데이터베이스 기록 후, offset 커밋 전에 작업자 종료 | 기록은 완료되었지만 offset은 커밋되지 않은 상태입니다. | `event-writer`가 같은 이벤트를 다시 읽을 수 있습니다. 이미 저장된 `event_id`는 중복으로 처리해 추가 행을 만들지 않습니다. |

따라서 이 절로 진입하면 같은 ID와 재전달·추가 행 방지의 관계를 함께 찾는다. 503이라는 API 응답 코드는 앞의 「API 오류 응답과 클라이언트 재시도」에서 확인해야 한다. 반대로 API 오류 절부터 읽으면 DB 기록 후 커밋 전 종료의 경우는 저장 장애 절로 이동한다. 실패 종류별 배치의 차이며 사실의 전역 누락은 아니다.

**자연스러움과 반복.** 「기록이 성공했더라도」라는 양보 조건 뒤에 「같은 이벤트를 다시 읽을 수 있습니다」가 이어져 예외 흐름이 자연스럽다. 앞 흐름 설명과 뒤 장애 표가 DB 기록·offset 커밋을 반복하지만, 뒤 표는 장애 상황을 독립적으로 찾는 용도가 있다. 도입부의 202 경계와 큐 수락 절의 재확인도 서로 다른 진입 지점을 제공한다. 이 반복들을 배경 설명의 단순 재진술과 같은 것으로 보지 않았다.

### 문서 B

**의미 보존과 설명 연결.** 구성요소 표, 단계별 흐름, 응답 표, 재처리 표, 중복 처리 절로 내용을 나눈다. 핵심 보장 범위는 A와 같다. 실패 표에서 클라이언트 재시도의 식별자와 writer의 재전달 조건을 함께 찾을 수 있다.

> | Kafka 발행 실패 | `collector-api`가 `503`을 반환합니다. 클라이언트가 같은 논리적 이벤트를 재시도할 때는 같은 `event_id`를 사용해야 합니다. |

> | 데이터베이스 기록 후, offset 커밋 전에 `event-writer` 종료 | 데이터베이스에는 이벤트가 기록되어 있어도 같은 이벤트를 다시 읽을 수 있습니다. 재처리 중 확인된 중복은 이미 기록된 이벤트로 취급합니다. |

**찾아보기.** 표 안에는 중복을 이미 기록된 것으로 취급한다는 설명이 있고, event_id 유일성 제약으로 추가 행을 막는 구체적 범위는 바로 다음 「중복 전달과 저장 중복 처리」에 있다. 따라서 RECALL1의 답은 충분하지만 실패 표 단독 조회에는 그 범위의 재확인이 남는다. A는 유일성 제약 설명과 장애 표를 한 절에 두고, B는 재처리 표 다음 절에 둔다는 구조 차이가 있다.

**자연스러움과 반복.** 역할·흐름·응답처럼 제목의 분류가 명확하고 문장 자체는 이해 가능하다. 다만 같은 절에서 새로운 조건을 더하지 않는 재진술이 있다.

> 요청 수락은 `collector-api`가, 데이터베이스 기록은 `event-writer`가 담당합니다. 두 구성요소 사이에서 이벤트를 전달하는 경계가 `telemetry.raw.v1`입니다.

> 저장과 offset 커밋은 이 순서로 진행됩니다.

첫 구절은 바로 앞 구성요소 표의 역할 관계를 다시 설명하고, 두 번째는 바로 앞 문장의 DB 성공 후 커밋 순서를 재진술한다. 축약을 검토할 수 있는 부분이다. 반면 장애 표에서 같은 event_id 조건을 다시 붙이면 재시도하려는 독자가 같은 위치에서 식별자 조건을 확인할 수 있다. 이 기능을 실제 독자 피로가 개선됐다는 실험 결과로 해석하지 않는다. 202의 경계가 여러 진입 위치에 반복되는 것도 저장 완료로 오해하지 않도록 하는 전제 재확인으로 구분했다.

### 두 문서의 중요한 차이

의미 보존의 충돌이나 누락 차이는 없다. A는 저장 장애와 중복 처리의 설명을 한 절로 묶고, B는 재처리 표와 저장 중복의 기제를 나눈다. B는 202까지 포함한 전체 응답 표를 제공하고 A는 오류 코드 표와 별도의 수락 설명을 제공한다. 이런 배치 차이를 사실 보존의 우열로 환산하지 않았다.

## incident_runbook — 배포 후 worker 적체 대응

### 문서 A

**의미 보존과 설명 연결.** 초기 큐·worker 점검과 배포 정보 점검을 두 단계로 나누고, 알람 발생 시각과 적체 시작 시각을 구분해 기록한다. 배포 관련 두 조건이 충족돼야 일시정지로 진행하며, pause 접수와 실제 정지 완료를 구별한다. 다음 문장은 바로 앞 상태 조회와 다음 롤백 단계를 연결한다.

> **`state=paused`와 `inflight=0`을 모두 확인한 다음에만 4단계로 진행합니다.**

> 일시정지 요청 후 **5분이 지나도 두 조건을 모두 만족하지 못하면 롤백하지 않고 플랫폼 온콜에 이관합니다.**

**찾아보기와 국소 한계.** 실제 롤백 명령이 있는 4단계는 정지 상태 두 조건을 다시 보여 준다.

> `state=paused`와 `inflight=0`을 모두 확인했다면 다음 명령으로 롤백합니다.

하지만 이 위치에 5분 한계는 반복되지 않는다. 롤백 명령만 찾아온 독자는 앞 3단계에서 pause 반환의 의미와 요청 기준의 대기 한계를 추가 확인해야 한다. 이 때문에 NAV1은 국소적으로 partial이다. 앞 단계는 5분 초과 시 이관하도록 명시하고 있어 문서 전체의 실행 조건이 빠지거나 뒤집힌 것은 아니다.

**반복의 역할과 자연스러움.** 명령 직전에 paused와 inflight=0을 모두 다시 쓰는 것은 실행 조건의 재확인이다. 마지막 「중단 및 플랫폼 온콜 이관」은 여러 중단 사유를 한 문장에 모은다.

> 롤백 조건을 확인하지 못했거나, 일시정지 요청 후 5분이 지나도 `state=paused`와 `inflight=0`을 모두 만족하지 못했거나, 롤백에 실패했거나, 재개 후 10분 동안 개선되지 않으면 해당 단계에서 조치를 중단하고 플랫폼 온콜에 이관합니다.

이 문장은 「거나」가 이어져 목록보다 조건을 분리해 읽어야 한다. 그럼에도 마지막 절만 조회하는 온콜에게 중단 기준을 다시 제공하므로 단순한 배경 반복으로 처리하지 않았다. 이관 정보에 관찰 값과 pause·resume 시각을 더 기록하도록 한 내용은 이미 제시된 명령 출력과 시간 기준을 전달하는 보조 지시다. 원자료의 이관 항목을 지우거나 다른 복구 조치를 만들지 않는다.

### 문서 B

**의미 보존과 설명 연결.** 큐·worker·배포의 세 조회를 한 코드 블록과 한 출력 표로 모으고, 판단에서 일시정지·롤백·재개·복구 확인으로 진행한다. 제시된 실행 조건과 5분·10분 기준은 A와 같다. 제목 자체에 재개 조건을 담는다.

> ## 3. stable로 롤백하고 성공한 경우에만 소비를 재개합니다

> **롤백 명령이 성공한 경우에만** 다음 명령으로 소비를 재개하고, 재개 시각을 기록합니다.

제목과 본문이 같은 조건을 반복하지만 제목 검색 후 명령을 실행하는 지점에서 성공 조건을 재확인하는 기능이 있다. 바로 다음 복구 단계에는 running과 대기 시간 감소의 두 조건 및 재개 후 10분 이관이 함께 있다.

**찾아보기와 국소 한계.** 롤백 명령 직전에는 paused와 inflight=0이 다시 나오며 5분 한계는 바로 앞 2단계에 있다. 따라서 A와 같은 이유로 NAV1을 partial로 판정했다. 복구 확인 절로 직접 들어오면 성공한 롤백 뒤에만 소비를 재개한다는 전제는 앞 3단계로 가야 한다. 이는 JSON의 RECALL1에 위치를 명시했으며 복구 조건의 전역 누락은 아니다.

마지막 이관 절은 전달할 정보에 집중한다.

> 앞 단계에서 이관 조건에 해당하면 다음 정보를 전달합니다.

여기에는 각 단계의 중단 조건을 다시 나열하지 않는다. 마지막 절에 바로 진입한 독자가 이관 여부까지 판단하려면 앞 단계가 필요하고, 이미 이관을 결정한 독자는 전달 목록을 바로 사용할 수 있다. A의 마지막 절은 중단 조건을 재집합하고 B는 조건이 있는 앞 단계와 전달 목록의 역할을 나누는 구조다.

### 두 문서의 중요한 차이

두 문서 모두 원자료의 명령·조건·기한·이관 대상을 보존한다. A는 초기 점검과 배포 판단을 나누고 이관 절에 조건 요약을 더하며, B는 초기 조회를 모으고 단계 제목에 행동과 조건을 길게 담는다. 명령 직전의 복합 조건 반복은 두 문서 모두 유지한다. 5분 한계의 국소 탐색 문제도 공통이며, 복구 실패 시 반복 롤백하거나 소비를 재개하라는 잘못된 지시는 없다.

## storage_adr — 이벤트 중복 판정 저장소 ADR

### 문서 A

**의미 보존과 설명 연결.** 상태·작성일·미완료 검토를 먼저 제시하고, tenant별 복합 키, 같은 트랜잭션의 범위, Redis 대안, 비용과 미결 사항을 연결한다. 대안 표는 중복 누락의 조건을 충분히 한정한다.

> | 과거 이벤트의 중복 판정 | 중복 판정 기록의 보존 기간과 정리 정책을 정해야 한다. | TTL 만료 또는 키 유실 뒤 과거 이벤트가 다시 들어오면 중복을 놓칠 수 있다. |

같은 표에서 PostgreSQL 업무 이벤트 생성과의 원자적 처리에 추가 설계가 필요하다고 적어, Redis 자체가 항상 중복을 놓친다는 일반화가 생기지 않는다. 보존 정책의 이유도 비용 설명에 연결한다.

> 기록 정리는 과거 이벤트의 중복 판정에 영향을 주므로, 보존 기간과 함께 결정해야 한다.

「영향을 주므로」가 정리 정책과 보존 기간을 함께 정해야 하는 이유를 설명한다. 단순한 미결 항목 나열보다 정책의 관련성을 문장에 드러낸다.

**찾아보기와 반복.** 마지막 승인 전 절은 보존·성능·책임을 표로 모으고 현재 상태를 다시 적는다.

> 리뷰에서 위 사항을 정한 뒤 제안의 승인 여부를 결정한다. 데이터 및 운영 담당자의 검토가 완료되기 전까지 이 문서의 상태는 제안이다.

앞머리에 있던 제안 상태의 반복이지만, 승인 전 사항만 찾아온 독자가 검토 완료로 오해하지 않게 하는 독립 조회의 전제다. 반면 추가 비용이 아직 미측정이고 공식 지연·처리량 보장이 없다는 구체적 한계는 바로 앞 절에 있다. 마지막 표는 측정 계획을 정하라고 하므로 검증의 미완료 상태를 암시하지만, 미측정 사실의 직접 근거는 앞 절에서 찾아야 한다. 이 분산은 RECALL1에 기록했다.

**같은 절 안의 재진술.** 대안 비교 직후의 제안 이유는 비교 표의 원자성과 운영 이점을 다시 설명한다. 그 중 다음 문장은 표와 정보가 겹친다.

> PostgreSQL 제안은 기존 데이터베이스의 트랜잭션으로 두 기록을 함께 처리할 수 있다는 점에서 적합하다고 판단한다.

앞 문장들이 과거 이벤트 재수집 요구와 원자성 과제를 연결하고 있어 설명 전체가 무의미한 반복은 아니다. 표에 이미 있는 내용을 그대로 다시 나열하는 부분과 선택 근거를 잇는 문장을 구분해 볼 수 있다. 「적합하다고 판단한다」는 제안 이유이며 머리말과 마지막 문단의 미승인 상태와 충돌하지 않는다.

### 문서 B

**의미 보존과 설명 연결.** 신규 키·기존 키·DB 작업 실패를 조건별 표로 제시한다. 업무 이벤트 생성을 생략해야 하는 경우와 같은 식별자로 재시도할 경우가 각각 명확하다. 대안 표에도 TTL 만료·키 유실 뒤 과거 이벤트가 다시 들어오는 조건과 PostgreSQL 업무 이벤트 생성의 원자성 범위가 모두 있어 NAV1은 충분하다.

**찾아보기와 상태 표현.** 마지막 절에서는 검토와 세 미결 결정을 끝낸 뒤 승인 여부를 결정한다고 설명한다.

> 데이터와 운영 담당자의 검토를 마치고 보존 정책, 성능 검증 계획, 운영 시 책임 주체를 정한 뒤 제안의 승인 여부를 결정한다.

이 문장 자체가 승인 이전의 절차임을 나타낸다. A처럼 「상태는 제안」을 같은 자리에서 그대로 되풀이하지 않아도 제안 상태의 의미는 보존된다. B도 미측정 비용과 공식 지연·처리량 미보장은 바로 앞 「도입 시 감수할 비용과 검증 한계」에 두므로, 마지막 승인 조건 표만 읽는 경우 성능 한계를 더 확인해야 한다.

**자연스러움과 반복.** 비교 표 뒤에 PostgreSQL을 제안하는 이유와 Redis 대안에서 해결할 과제를 이어 적는다.

> PostgreSQL을 제안하는 이유는 기존 데이터베이스의 트랜잭션을 활용해 중복 판정 기록과 업무 이벤트 생성을 함께 처리할 수 있기 때문이다. 별도 Redis 운영을 추가하지 않는다는 이점도 있다.

문장은 원인과 선택을 연결하지만 바로 앞 표의 원자성·운영 구성 두 행과 정보가 겹친다. 이 부분의 길이를 줄이는 편집 여지는 있다. 반면 보관 중인 기록을 기준으로 중복 판정한다는 설명과 승인 조건에서 보존 정책을 재확인하는 부분은 과거 이벤트 재수집의 보장 범위를 한정하므로 단순 배경 반복과 다르다. B의 「다시 가져오는 작업」과 「재반입」, A의 「다시 가져오는 작업」과 「재수집」은 각각 문맥상 같은 요구를 가리키며 기술 의미를 바꾸지 않는다.

### 두 문서의 중요한 차이

두 문서의 필수 의미와 제안 상태는 같다. A는 처리 규칙을 글머리표로, B는 조건별 표로 제공한다. A는 마지막 절에 제안 상태를 명시적으로 재확인하고 B는 승인 여부를 아직 결정해야 한다는 절차로 나타낸다. 두 표현 모두 충분하므로 동일 문구의 복제를 요구하지 않았다. 양쪽 모두 성능 미측정의 직접 설명은 승인 전 표의 바로 앞 절에 둔다.

## 검증 기록과 해석의 한계
