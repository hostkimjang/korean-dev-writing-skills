trace-slice

trace-slice는 로컬 JSON Lines 로그 파일에서 지정한 최소 심각도 이상의 항목을 골라 내는 CLI입니다. 오류 로그만 터미널에서 확인하거나, 경고 이상의 로그를 파일로 저장할 때 사용할 수 있습니다. 로그를 네트워크로 전송하지 않습니다.

이 문서는 0.4.2 버전을 기준으로 합니다.

설치

Python 3.10 이상이 필요합니다. 설치와 기본 동작을 확인한 환경은 Ubuntu 22.04 / Python 3.11이며, 다른 운영체제에서의 검증 기록은 없습니다.

다음 명령으로 0.4.2 버전을 설치합니다.

python -m pip install trace-slice==0.4.2

설치 후 도움말을 확인합니다.

trace-slice --help

첫 실행: 오류 로그 확인

확인할 로컬 JSON Lines 파일을 준비합니다. 각 정상 로그 행에는 level 필드가 있어야 합니다.

아래 예제는 로그 파일이 ./logs/api.jsonl에 있다고 가정합니다. 실제 파일이 다른 위치에 있다면 경로를 바꿔 실행하세요.

trace-slice ./logs/api.jsonl --level error

error 항목이 표준 출력으로 나옵니다. 터미널에서 실행하면 결과를 바로 확인할 수 있습니다.

사용 형식과 주요 옵션

trace-slice INPUT [--level LEVEL] [--output PATH]
인수·옵션 설명 생략 시 동작
INPUT 읽을 로컬 JSON Lines 파일의 경로 필수 위치 인수이므로 생략할 수 없습니다.
--level LEVEL 출력할 최소 심각도. debug, info, warn, error 중 하나를 지정합니다. info
--output PATH 결과를 저장할 파일 경로 표준 출력으로 내보냅니다.

심각도는 debug → info → warn → error 순으로 높아집니다. 지정한 값과 그보다 높은 심각도의 항목이 모두 출력됩니다.

--level 값 출력 대상
debug debug, info, warn, error
info info, warn, error
warn warn, error
error error

기본 심각도로 확인

--level을 생략하면 info 이상의 항목을 출력합니다.

trace-slice ./logs/api.jsonl

경고 이상의 로그를 파일로 저장

출력 파일이 이미 있으면 덮어씁니다. 보관해야 할 파일과 경로가 겹치지 않는지 확인한 뒤 실행하세요.

trace-slice ./logs/api.jsonl --level warn --output ./warnings.jsonl

warn과 error 항목이 ./warnings.jsonl에 저장됩니다.

Harbor Intake 이벤트 수집 서비스 아키텍처

Harbor Intake는 HTTP로 제출된 이벤트를 Kafka에 수락한 뒤 PostgreSQL에 비동기로 저장하는 서비스다. API 요청을 처리하는 collector-api와 데이터베이스에 기록하는 event-writer가 분리되어 있다.

연동할 때 가장 먼저 구분해야 할 것은 이벤트 수락과 저장 완료다. POST /v1/events의 202 응답은 Kafka 발행이 확인되었다는 뜻이다. 이 시점에 event_store 저장까지 완료되었다고 판단해서는 안 된다. 현재는 event_id로 최종 저장 상태를 조회하는 API도 없다.

구성요소

구성요소 역할 처리 경계
collector-api POST /v1/events 요청의 토큰과 스키마를 검증하고 이벤트를 Kafka에 발행한다. Kafka 발행 확인 후 202와 event_id를 반환한다. 자체적으로 중복 요청을 제거하지 않는다.
Kafka 토픽 telemetry.raw.v1 API가 수락한 이벤트를 event-writer에 전달한다. 이벤트가 토픽에 발행되었다는 사실과 데이터베이스에 저장되었다는 사실은 구분된다.
event-writer Kafka에서 이벤트를 읽어 데이터베이스에 기록한다. 데이터베이스 트랜잭션이 성공한 뒤 Kafka offset을 커밋한다.

이벤트가 저장되는 흐름

1. 요청 검증

클라이언트는 POST /v1/events에 이벤트를 제출한다. collector-api는 토큰과 스키마를 확인한다.

  • 토큰이 유효하지 않으면 401을 반환한다.
  • 스키마에 오류가 있으면 400을 반환한다.
  • 검증을 통과하면 telemetry.raw.v1에 이벤트를 발행한다.

2. Kafka 발행과 수락 응답

collector-api는 Kafka 발행이 확인된 뒤 202와 event_id를 반환한다. Kafka 발행에 실패하면 503을 반환한다.

202는 API의 수락 단계가 끝났음을 알리는 응답이다. 이후 저장은 event-writer가 처리한다. 따라서 클라이언트가 202를 받았어도 데이터베이스 장애 등으로 저장이 지연될 수 있다. 반대로 응답을 받은 시점에 이미 저장되었을 수도 있지만, 응답만으로 그 여부를 구분할 수는 없다.

3. 데이터베이스 기록

event-writer는 telemetry.raw.v1에서 이벤트를 읽고 event_store에 기록한다. 이때 event_id의 유일성 제약으로 중복을 확인한다. 이미 기록된 이벤트라면 추가 행을 만들지 않는다.

4. Kafka offset 커밋

event-writer는 데이터베이스 트랜잭션이 성공한 뒤 Kafka offset을 커밋한다. 이 순서는 데이터베이스에 기록하지 못한 이벤트를 다시 처리할 수 있게 한다.

다만 데이터베이스 기록과 offset 커밋 사이에는 중단될 수 있는 구간이 있다. 기록은 성공했지만 offset을 커밋하기 전에 worker가 종료되면 같은 이벤트를 다시 읽을 수 있다. 이 재처리에서 추가 행이 생기지 않도록 하는 장치가 event_id 유일성 제약이다.

API 응답 해석

응답 의미 연동 시 처리
400 이벤트 스키마에 오류가 있다. 요청 내용을 수정해야 한다. 동일한 잘못된 요청을 반복해도 스키마 오류는 해소되지 않는다.
401 토큰이 유효하지 않다. 인증 정보를 확인하고 수정해야 한다.
503 Kafka 발행에 실패했다. 같은 논리적 이벤트를 재시도할 때 같은 event_id를 사용해야 한다.
202 + event_id Kafka 발행이 확인되어 이벤트가 큐에 수락되었다. 수락된 것으로 처리하되, 최종 저장 완료로 해석하지 않는다.

event_id를 반환받았다는 사실만으로 저장 완료를 확인할 수는 없다. 현재 구현에는 해당 ID로 저장 상태를 조회하는 API가 없으므로, 연동 코드에서 조회 API를 통한 완료 확인을 전제로 삼아서는 안 된다.

중복 전달과 event_id

Harbor Intake의 전송 및 소비 과정에서는 같은 이벤트가 여러 번 전달될 수 있다. collector-api가 중복 요청을 제거하지 않기 때문에 클라이언트의 재시도 요청이 Kafka에 다시 발행될 수 있고, event-writer도 미커밋 이벤트를 다시 읽을 수 있다.

중복 처리는 저장 단계에서 이루어진다. event_store의 event_id 유일성 제약으로 중복임이 확인되면, event-writer는 이를 이미 기록된 이벤트로 취급하고 추가 행을 만들지 않는다. 따라서 같은 논리적 이벤트를 재시도할 때 같은 event_id를 유지해야 한다.

재시도마다 새 ID를 사용하면 기존 이벤트와 같은 ID라는 조건이 성립하지 않아 이 중복 방지 장치가 적용되지 않는다. 또한 유일성 제약은 ID를 기준으로 하므로, 서로 다른 논리적 이벤트에 같은 ID를 재사용해서도 안 된다.

river-worker 적체 장애 대응 절차

WorkerQueueAgeHigh 알람이 발생하면 이 절차를 시작한다. 대상 worker는 river-worker, 작업 큐는 river-events다. 알람만으로 배포가 원인이라고 확정하지 말고, 적체 시작 시점과 배포 정보를 확인한 뒤 롤백 여부를 판단한다.

1. 현재 상태와 배포 정보를 확인한다

다음 명령을 실행하고 결과를 기록한다.

opsctl queue inspect river-events
opsctl worker status river-worker
opsctl deploy show river-worker
조회 대상 기록할 항목 확인 목적
river-events pending, oldest_age_seconds, consumer_state 현재 적체와 소비 상태를 파악하고, 복구 확인에 사용할 기준값을 남긴다.
river-worker state, inflight worker 상태와 처리 중인 작업을 확인한다.
배포 current, stable, changed_at 현재 배포와 복구 대상 배포, 배포 변경 시각을 확인한다.

stable은 온콜이 복구 대상으로 사용할 수 있도록 미리 지정된 배포다.

알람 발생 시각과 적체 시작 시각도 기록한다. 적체 시작 시각을 changed_at과 비교해 현재 배포 직후부터 적체가 시작됐는지 확인한다. 적체 시작 시각을 확인할 수 없다면 알람 발생 시각만으로 이를 대신 판단하지 않는다.

2. 롤백 조건을 판단한다

이 절차에서는 다음 두 조건을 모두 확인한 경우에만 롤백을 진행한다.

  1. 현재 배포 직후부터 적체가 시작됐다.
  2. current와 stable이 다르다.

두 조건을 모두 확인했으면 3단계로 진행한다. 배포와 적체 시작 시점의 관계를 확인할 수 없거나, 롤백 조건이 충족되지 않으면 롤백하지 않고 플랫폼 온콜에 이관한다. 이관할 내용은 6단계를 따른다.

3. worker를 일시정지하고 처리 중인 작업이 끝났는지 확인한다

롤백 전에 다음 명령을 실행하고, 일시정지 요청 시각을 기록한다.

opsctl worker pause river-worker

명령이 반환됐다는 것은 일시정지 요청을 접수했다는 뜻이다. 이미 처리 중인 작업은 계속 진행될 수 있으므로, 명령 반환만으로 롤백을 시작하지 않는다.

4. stable로 롤백하고, 성공한 경우에만 소비를 재개한다

2단계의 롤백 조건을 충족했고, 3단계에서 state=paused와 inflight=0을 모두 확인한 다음 실행한다.

배경과 요구사항

기존 이벤트 API는 PostgreSQL에 업무 이벤트를 저장한다. 같은 tenant_id에서 같은 event_id가 다시 제출되어도 업무 이벤트가 중복 생성되지 않아야 한다. 서로 다른 tenant_id에서는 같은 event_id를 사용할 수 있으므로, 중복 판정의 기준은 (tenant_id, event_id) 쌍이다.

중복 판정은 일반적인 요청 재시도뿐 아니라 과거 이벤트를 다시 가져오는 작업에도 적용된다. 따라서 중복 판정 기록의 보존 범위가 과거 이벤트에 대한 중복 방지 범위를 결정한다. 기록을 얼마나 오래 보관할지는 아직 정하지 않았다.

제안

PostgreSQL에 event_receipts 테이블을 만들고 (tenant_id, event_id)에 유일성 제약을 설정한다. 중복 판정 기록의 생성과 업무 이벤트의 생성은 같은 데이터베이스 트랜잭션에서 처리한다.

요청 처리 방식은 다음과 같다.

  1. 요청의 (tenant_id, event_id)를 기준으로 중복 판정 기록을 생성한다.
  2. 새 키라면 같은 트랜잭션에서 업무 이벤트를 생성하고 커밋한다.
  3. 이미 존재하는 키라면 업무 이벤트를 새로 만들지 않는다.
  4. 데이터베이스 작업이 실패하면 요청에 503을 반환한다. 클라이언트는 같은 tenant_id와 event_id로 재시도한다.

유일성 제약은 같은 키로 들어온 요청이 중복 판정 기록을 각각 생성하지 못하도록 한다. 같은 트랜잭션을 사용하면 중복 판정 기록과 업무 이벤트가 함께 커밋되거나 함께 롤백되므로, 두 기록의 정합성을 기존 데이터베이스 안에서 관리할 수 있다.

이 방식은 리뷰를 위한 제안이며, 아직 승인된 결정이 아니다.

이 선택을 제안하는 이유

핵심 요구사항은 중복 여부를 빠르게 조회하는 데 그치지 않고, 중복 판정 결과에 따라 업무 이벤트가 한 번만 생성되도록 하는 것이다. 업무 이벤트를 이미 PostgreSQL에 저장하고 있으므로, 중복 판정 기록도 같은 데이터베이스에 두면 기존 트랜잭션으로 두 작업을 묶을 수 있다.

또한 별도 Redis 운영을 추가하지 않아도 된다. 다만 운영 부담이 없어지는 것은 아니다. 중복 판정 기록을 저장하고 유지하는 부담이 기존 PostgreSQL에 추가된다.

과거 이벤트의 재반입도 중복 판정 대상이고 보존 기간이 미정인 상황에서는, TTL 만료에 따라 판정 기록이 사라지는 방식을 채택하기 전에 보장 범위를 먼저 정해야 한다. PostgreSQL 제안 역시 보존 정책이 필요하지만, 저장소 간 원자성을 위한 추가 설계 없이 현재의 업무 이벤트 저장 경로와 통합할 수 있다는 점을 우선한다.

이벤트 API의 중복 판정 기록을 PostgreSQL의 event_receipts 테이블에 저장할 것을 제안한다. (tenant_id, event_id)에 유일성 제약을 두고, 중복 판정 기록과 업무 이벤트 생성을 같은 데이터베이스 트랜잭션에서 처리한다. 기존 PostgreSQL의 트랜잭션을 활용하고 별도 Redis 운영을 추가하지 않는 것이 제안의 주요 근거다.

배경과 요구사항

기존 이벤트 API는 PostgreSQL에 업무 이벤트를 저장한다. 같은 tenant_id에서 같은 event_id가 다시 제출되면 업무 이벤트가 중복 생성되지 않아야 한다. 서로 다른 tenant_id에서는 같은 event_id를 사용할 수 있으므로, 중복 판정 기준은 두 값의 조합이다.

과거 이벤트를 다시 가져오는 작업도 중복 판정 대상이다. 다만 중복 판정 기록을 얼마나 오래 보관할지는 아직 정하지 않았다. 보존 정책을 정할 때는 과거 이벤트의 재수집을 포함해 중복 방지가 필요한 범위를 함께 검토해야 한다.

제안하는 처리 방식

PostgreSQL에 event_receipts 테이블을 만들고 (tenant_id, event_id)에 유일성 제약을 설정한다. 요청은 다음 원칙에 따라 처리한다.

  • 새 키에 대한 중복 판정 기록과 업무 이벤트 생성은 같은 데이터베이스 트랜잭션에서 처리한다.
  • 중복 키가 이미 있으면 업무 이벤트를 새로 만들지 않는다.
  • 데이터베이스 작업이 실패하면 요청에 503을 반환한다. 클라이언트는 같은 tenant_id와 event_id로 재시도한다.

  • 현재본은 대기/구축, 검증, 반영/완료를 소제목으로 나누고 각 단계에서 무엇이 확인되는지 설명합니다. 상태 이름만 나열하지 않고 후보와 활성 판의 관계를 이어 줍니다.

  • 현재본은 기존 판을 계속 사용한다는 설명의 전제가 이미 활성 판이 있는 자료집임을 다시 밝힙니다. 첫 갱신에는 「색인 준비 안 됨」이 반환되며 빈 목록과 다르다는 조건을 유지합니다.

  • 「다음 작업은 종료 상태를 확인한 뒤 요청한다」에서 중단 요청 수락, 실제 중단, 새 접수 가능 시점을 연결합니다. 미적용·v0.2.1에도 이 관계가 있었으며 현재본에서는 실패·중단 절 안의 독립 소제목으로 찾습니다.

검토에 기록된 한계

  • 첫 갱신 예외는 「완료 상태와 실제 검색 결과를 함께 읽기」 안에 있습니다. v0.2.1의 「실패하거나 첫 갱신이 끝나지 않았을 때」처럼 제목에서 해당 예외가 바로 보이지는 않습니다.

  • 접수 절에는 진행 중 작업이 있으면 새 작업을 받지 않는다고 적지만, 「진행 중 작업 있음」·현재 접수 번호·새 번호 미생성이라는 응답 세부는 중단 절에 있습니다. 일반 접수의 거절 응답을 찾으려면 뒤를 읽어야 합니다.

  • 현재본의 반영 대기 설명에도 기존 활성 판을 사용하는 문장이 있고, 기존 판이 있는 자료집이라는 일반 전제는 다음 절에서 다시 밝힙니다. 모든 조건을 각 문장에 붙인 결과는 아닙니다.

  • 「완료를 확인한 뒤 검색 요청을 시작」하라는 안내는 새 판을 확인하는 절차입니다. 사람이 완료를 조회하는 행위가 판 선택의 필수조건인 것은 아니며, 실제 기준은 전환 확정과 검색 시작의 선후입니다.

5. 완료 뒤에도 이전 판의 검색 응답이 올 수 있다

작업 완료와 검색 응답을 함께 읽으려면 검색 요청이 언제 시작했는지를 봐야 한다. 조회 API는 요청을 시작할 때 활성 판을 한 번 정하고, 응답을 마칠 때까지 그 판을 유지한다. 한 검색 요청 안에서 두 판의 결과를 섞지는 않는다.

검색 요청이 시작된 시점 사용하는 색인 판 응답을 해석하는 방법
활성 판 전환 전 기존 활성 판 전환 뒤에 응답이 도착하더라도 이전 판의 결과일 수 있다.
활성 판 전환 확정 후 새 활성 판 새로 반영된 판으로 검색한다.

예를 들어 q203이 반영 대기인 동안 시작한 검색은 기존 활성 판을 선택한다. 그 검색이 끝나기 전에 q203이 완료되어 i52가 활성화되더라도, 이미 시작한 검색은 끝까지 기존 판을 사용한다. 반대로 전환이 확정된 뒤 시작한 검색은 i52를 사용한다.

따라서 완료를 확인한 뒤 이전 내용의 응답을 받았다는 사실만으로 전환 실패라고 판단할 수는 없다. 그 응답이 전환 전에 시작한 검색의 결과인지 함께 살펴야 한다. 새 판의 검색 결과를 확인하려면 전환 확정 뒤 시작한 검색을 기준으로 읽는다.

현재 적용 · v0.3.0

이 때문에 작업이 완료된 뒤 도착한 검색 응답에도 구판의 결과가 담길 수 있습니다. 그 검색이 전환 전에 시작됐다면, 전환 후에 응답을 마치더라도 처음 선택한 판을 계속 사용하기 때문입니다. 전환이 확정된 뒤 시작한 검색은 새 판을 사용합니다. 새 내용의 반영 여부를 확인하려면 작업의 완료를 확인한 뒤 검색 요청을 시작해야 합니다.

두 원문 모두 검색 요청의 시작 시점이 판을 결정한다고 설명합니다. 현재본은 요청 시작→구판 응답이 늦게 도착하는 이유→확인할 다음 행동을 두 문단으로 묶습니다. 새로운 보장을 추가한 것이 아니라 같은 규칙의 연결 방식이 달라진 결과입니다.

모래결 색인 갱신기: 요청 접수부터 검색 반영까지

모래결 색인 갱신기는 자료집의 문서를 검색할 색인을 만드는 내부 서비스다. 새로 합류한 개발자가 먼저 구분해야 할 것은 갱신 요청의 접수, 작업의 진행 상태, 검색에 쓰이는 활성 색인이다. 접수가 성공하면 작업 기록이 생기지만, 검색 결과가 곧바로 바뀌지는 않는다. 작업이 후보 색인을 만들고 검증한 뒤 활성 판으로 전환되어야 새 내용을 검색할 수 있다.

이 문서는 가상의 자료집 C17, 원본 r18, 접수 q203, 색인 판 i52를 예로 들어 그 과정을 설명한다.

1. 원본에서 검색 결과까지, 구성 요소가 맡는 일

원본을 올리는 기능은 별도 시스템에 있다. 모래결 색인 갱신기는 이미 보관된 원본을 선택해 색인을 갱신한다. 조회 API가 검색하는 대상은 원본 자체가 아니라 활성 색인이다. 따라서 새 원본의 보관이 끝났다는 사실만으로 검색에 새 내용이 반영되었다고 판단할 수는 없다.

갱신과 검색은 다음 네 구성 요소가 나누어 맡는다.

구성 요소 역할
접수 API 갱신 요청을 확인하고 작업 기록을 저장한다.
작업 조정기 작업을 구축기에 넘기고, 검증을 통과한 후보를 활성 색인으로 반영한다.
구축기 선택된 원본으로 후보 색인을 만들고 검증한다.
조회 API 자료집의 활성 색인을 사용해 검색한다.

접수 API가 요청을 기록하면 조정기가 작업을 구축기에 넘긴다. 구축기는 검색에 사용할 새 색인을 후보로 만든다. 이 후보는 기존 활성 색인과 분리되어 보관된다. 구축 도중 일부 문서만 만들어져 있어도 그 내용이 기존 검색 결과에 섞이지 않는 이유다.

후보가 검증을 통과하면 조정기가 활성 판으로 전환한다. 조회 API는 이 전환이 확정되기 전까지 기존 활성 판을 사용한다. 후보를 만드는 과정과 실제 검색에 사용하는 판을 바꾸는 과정은 이렇게 구분된다.

2. 네 식별자를 구분하고, 작업이 선택한 원본을 확인한다

하나의 갱신을 살펴볼 때는 다음 식별자를 함께 보게 된다.

식별자 가리키는 대상 예시
자료집 번호 색인을 갱신하고 검색할 자료집 C17
원본 번호 내용이 고정된 원본 한 묶음 r18
접수 번호 접수된 작업 기록 q203
색인 판 번호 만들어진 색인의 판 i52

예를 들어 “자료집 C17의 원본 r18로 색인을 갱신한다”는 요청이 q203으로 접수되고, 그 작업이 색인 i52를 만들 수 있다. 이때 r18, q203, i52의 숫자는 각각 별도 순서다. 숫자 크기를 서로 비교해 진행률이나 최신 여부를 판단해서는 안 된다.

작업 상태를 조회할 때 사용하는 식별자는 접수 번호다. q203의 상태를 알고 싶다면 q203으로 조회해야 한다. 자료집 번호 C17이나 색인 판 번호 i52로 대신 조회할 수 없다.

원본 번호는 작업이 어떤 내용을 사용해야 하는지도 고정한다. q203이 r18로 접수되었다면 이후 r19가 보관되어도 작업은 끝까지 r18을 사용한다. 조정기나 구축기가 진행 도중 최신 원본으로 대상을 바꾸는 기능은 없다. 따라서 새 원본이 올라왔는지와 현재 작업이 어느 원본을 처리하는지는 별도로 확인해야 한다.

3. 접수 성공은 어디까지 보장하는가

접수 API는 먼저 자료집이 존재하는지, 지정한 원본의 보관이 완료되었는지 확인한다. 둘 중 하나라도 충족하지 않으면 이유를 반환하고 작업 기록을 만들지 않는다.

두 조건을 모두 충족해도 접수가 거절될 수 있다. 한 자료집에는 진행 중인 작업을 하나만 허용하기 때문이다. 같은 자료집에 진행 중 작업이 있으면 새 갱신이나 재시도 요청에 대해 진행 중 작업 있음과 그 작업의 접수 번호를 반환하며, 새 접수 번호는 만들지 않는다. 이 제한은 자료집별로 적용되므로 다른 자료집의 접수에는 영향을 주지 않는다.

접수에 성공하면 작업 기록을 저장한 뒤 새 접수 번호와 대기 상태를 반환한다. 이 응답으로 확인할 수 있는 것은 요청이 작업 목록에 들어갔다는 사실이다. 다음 사항까지 보장하는 응답은 아니다.

  • 구축기가 작업을 시작했다는 것
  • 후보 색인이 검증을 통과했다는 것
  • 자료집의 활성 색인이 바뀌었다는 것

접수 뒤에는 응답으로 받은 접수 번호로 작업 상태를 확인한다. 검색에 새 내용이 반영되었는지를 판단하려면 이후의 상태 전이, 특히 완료 여부를 봐야 한다. 접수 응답은 그 확정까지 걸리는 시간도 약속하지 않는다.

4. 정상 경로에서 각 상태가 뜻하는 것

정상적인 갱신은 대기 → 구축 중 → 검증 중 → 반영 대기 → 완료 순서로 진행한다. 이 중 완료는 종료 상태다. 정상 경로 밖의 종료 상태로는 실패와 중단이 있으며, 이 세 상태를 제외한 나머지는 모두 진행 중 상태다.

상태 작업에서 일어나는 일 다음에 기다리는 일
대기 작업 기록은 있지만 구축기가 아직 시작하지 않았다. 구축 시작
구축 중 접수할 때 선택한 원본으로 후보 색인을 만든다. 후보 구축을 마치고 검증 진행
검증 중 후보의 문서 수와 확인용 문서의 조회를 검사한다. 모든 검증 항목 통과

검증 통과가 뜻하는 범위

검증 중에는 두 가지를 확인한다. 후보의 문서 수가 원본과 일치해야 하고, 원본에 지정된 두 확인용 문서가 정확한 키로 조회되어야 한다. 모두 통과해야 반영 대기로 넘어간다.

이 검증은 문서 누락과 기본 조회를 확인하는 범위다. 검색 순위의 품질을 평가한 결과는 아니다. 따라서 검증 통과 기록을 근거로 검색 순위가 좋아졌다고 설명할 수는 없다.

검증 통과와 검색 반영도 구분해야 한다. 반영 대기는 후보가 검증을 마쳤다는 뜻이지만, 아직 활성 판 전환을 기다리는 상태다. 이때 조회 API는 기존 활성 판을 사용한다. 검증 통과 기록이나 반영 대기 표시만 보고 새 내용이 이미 검색된다고 안내해서는 안 된다.

완료가 뜻하는 확정 시점

반영할 때 조정기는 자료집의 활성 색인 판 변경과 해당 작업의 완료 기록을 하나의 변경으로 함께 확정한다. 따라서 완료 상태는 활성 판 전환이 확정되었다는 뜻이다.

q203이 만든 i52가 반영되는 경우라면, q203의 완료는 자료집 C17의 활성 판이 i52로 전환되었음을 뜻한다. 접수 성공과 달리 실제 검색에 사용할 판의 변경까지 확인할 수 있는 상태다.

5. 완료 뒤에도 이전 판의 검색 응답이 올 수 있다

작업 완료와 검색 응답을 함께 읽으려면 검색 요청이 언제 시작했는지를 봐야 한다. 조회 API는 요청을 시작할 때 활성 판을 한 번 정하고, 응답을 마칠 때까지 그 판을 유지한다. 한 검색 요청 안에서 두 판의 결과를 섞지는 않는다.

검색 요청이 시작된 시점 사용하는 색인 판 응답을 해석하는 방법
활성 판 전환 전 기존 활성 판 전환 뒤에 응답이 도착하더라도 이전 판의 결과일 수 있다.
활성 판 전환 확정 후 새 활성 판 새로 반영된 판으로 검색한다.

예를 들어 q203이 반영 대기인 동안 시작한 검색은 기존 활성 판을 선택한다. 그 검색이 끝나기 전에 q203이 완료되어 i52가 활성화되더라도, 이미 시작한 검색은 끝까지 기존 판을 사용한다. 반대로 전환이 확정된 뒤 시작한 검색은 i52를 사용한다.

따라서 완료를 확인한 뒤 이전 내용의 응답을 받았다는 사실만으로 전환 실패라고 판단할 수는 없다. 그 응답이 전환 전에 시작한 검색의 결과인지 함께 살펴야 한다. 새 판의 검색 결과를 확인하려면 전환 확정 뒤 시작한 검색을 기준으로 읽는다.

6. 실패했을 때 기존 검색은 어떻게 되는가

구축이나 검증을 더 진행할 수 없는 오류가 나면 작업은 실패로 끝난다. 상태 조회에는 오류가 발생한 단계와 이유가 남는다. 실패한 후보는 활성 판으로 반영하지 않는다.

이미 활성 판이 있는 자료집은 그 판을 계속 사용한다. 새 갱신의 실패가 기존 검색의 중단을 뜻하지 않는 이유다. 갱신 상태에 실패가 표시되어도 조회 API는 이전에 반영된 색인으로 검색할 수 있다.

다만 첫 갱신이라면 상황이 다르다. 한 번도 반영을 마치지 않은 자료집에는 기존 활성 판이 없다. 첫 갱신이 진행 중이거나 실패 또는 중단으로 끝났다면 조회 API는 색인 준비 안 됨을 반환한다.

이 응답은 검색 결과가 없는 정상 응답인 빈 목록과 구분해야 한다. 빈 목록은 검색 결과가 없다는 뜻이고, 색인 준비 안 됨은 검색에 사용할 활성 판이 아직 없다는 뜻이다. 작업 상태만 보지 말고 해당 자료집에 이전에 반영된 활성 판이 있었는지도 함께 보아야 한다.

7. 중단 수락과 작업의 중단 완료는 다른 시점이다

중단 요청은 모든 상태에서 받을 수 있는 것이 아니다.

조정기가 중단 요청을 확인한 시점의 상태 수락 여부
대기·구축 중·검증 중 수락 가능
반영 대기 거절
완료·실패·중단 거절

판단 기준은 사용자가 중단 버튼을 누른 시각이 아니라 조정기가 요청을 확인한 시점의 작업 상태다. 사용자가 검증 중이라고 보고 중단을 요청했더라도, 조정기가 확인할 때 이미 반영 대기라면 요청은 거절된다.

중단을 수락하면 먼저 중단 표시를 남긴다. 이후 조정기나 구축기가 그 표시를 확인하고 작업을 멈춘 뒤에야 상태를 중단으로 바꾼다. 따라서 중단 수락 뒤에도 잠시 직전의 진행 중 상태가 보일 수 있다. 수락 응답을 곧바로 중단 완료로 읽어서는 안 된다.

그동안에도 중단 표시의 효력은 있다. 표시가 남은 후보는 검증을 마치더라도 반영 대기로 넘어가거나 활성화될 수 없다. 중단으로 새 후보가 활성 판을 대체하지 않으므로, 기존 활성 판이 있었다면 기존 검색을 계속 사용한다. 활성 판이 없는 첫 갱신이었다면 앞서 설명한 대로 색인 준비 안 됨 상태가 이어진다.

새 작업은 중단 상태가 된 뒤 접수한다

중단 요청이 수락되었더라도 아직 상태가 중단이 아니라면 그 작업은 자료집의 진행 중 작업 자리를 차지한다. 이때 새 갱신이나 재시도를 요청하면 진행 중 작업 있음과 기존 접수 번호가 반환되며 새 번호는 생기지 않는다.

따라서 중단 후 다른 작업을 시작하려면 기존 접수 번호로 상태를 확인하면서 실제로 중단에 도달하기를 기다려야 한다. 중단을 요청했다는 사실, 중단이 수락되었다는 사실, 작업이 중단 상태로 끝났다는 사실을 구분해야 다음 접수 시점을 판단할 수 있다.

8. 재시도는 같은 원본으로 새 작업을 시작한다

재시도는 실패 또는 중단으로 끝난 작업에만 요청할 수 있다. 수락되면 기존 기록을 그대로 두고 새 접수 번호를 만든다. 새 작업은 대기부터 시작하며, 이전 작업과 같은 원본 번호를 사용한다.

이때 이전 후보를 재사용하거나 문서별 진행 위치에서 이어서 처리하지 않는다. 선택된 원본으로 처음부터 다시 구축한다. 재시도 후 상태를 확인할 때도 기존 작업의 접수 번호가 아니라 새로 받은 접수 번호를 사용해야 한다.

원본 선택이 달라지는 것도 아니다. r18을 사용한 q203이 실패한 뒤 r19의 보관이 끝났다고 하자. 이 상황에서 선택할 요청은 반영하려는 원본에 따라 달라진다.

모래결 색인 갱신기: 요청 접수부터 검색 반영까지

모래결 색인 갱신기는 자료집의 문서를 검색할 색인을 만드는 내부 서비스다. 원본 업로드는 별도 시스템이 담당하며, 이 서비스는 보관이 끝난 원본을 선택해 색인을 갱신한다. 조회 API가 검색에 사용하는 대상은 원본이 아니라 활성 색인이다.

갱신을 요청한 뒤에는 접수 응답, 작업 상태, 검색 결과를 함께 읽어야 한다. 접수 성공은 작업 기록이 저장되었다는 뜻이고, 완료는 새 색인으로의 전환이 확정되었다는 뜻이다. 검색 결과를 해석할 때는 해당 검색이 전환 전후 어느 시점에 시작했는지도 살펴야 한다. 이 문서의 서비스명과 사례는 모두 가상이다.

구성 요소와 원본이 검색에 반영되는 경로

갱신은 접수 API에서 시작한다. 접수 API가 요청을 확인해 작업 기록을 남기면, 작업 조정기가 그 작업을 구축기에 넘긴다. 구축기는 선택된 원본으로 후보 색인을 만들고 검증한다. 검증을 통과한 후보를 활성 색인으로 반영하는 주체는 조정기다.

조회 API는 이 과정에서 활성 색인으로 검색한다. 구축 중인 후보는 활성 색인과 분리되어 보관되므로, 후보에 일부 문서만 만들어진 상태가 검색 결과에 섞이지 않는다. 기존 활성 색인이 있는 자료집이라면 새 후보를 만드는 동안에도 그 기존 판으로 검색한다. 처음 색인을 만드는 자료집처럼 활성 판이 아직 없는 경우의 응답은 뒤에서 따로 설명한다.

자료집, 원본, 요청, 색인을 구분하는 식별자

갱신 과정을 따라가려면 무엇을 가리키는 번호인지 먼저 구분해야 한다. 예를 들어 자료집 C17의 원본 r18을 갱신해 달라는 요청 q203이 색인 i52를 만들 수 있다.

r18, q203, i52의 숫자는 각각 별도 순서다. 숫자끼리 비교해 진행률이나 최신 여부를 판단할 수 없다. 작업 상태를 조회할 때도 접수 번호인 q203을 사용해야 하며, 자료집 번호나 색인 판 번호로 대신 조회할 수 없다.

원본 번호는 작업이 사용할 내용을 고정한다. q203이 r18로 접수되었다면 작업 도중 r19가 올라와도 끝까지 r18을 사용한다. 조정기와 구축기는 진행 중에 최신 원본으로 대상을 바꾸지 않는다. 따라서 갱신 완료 여부를 확인할 때는 어떤 원본을 대상으로 접수했는지도 함께 확인해야 한다.

접수 성공으로 알 수 있는 것

접수 API는 자료집이 존재하는지, 지정한 원본의 보관이 끝났는지 확인한다. 둘 중 하나라도 충족하지 않으면 이유를 반환하고 작업 기록을 만들지 않는다. 이 확인을 통과하더라도 같은 자료집에 진행 중인 작업이 있으면 새 작업을 받지 않는다. 한 자료집에는 진행 중 작업을 하나만 허용하기 때문이다.

요청을 받으면 작업 기록의 저장을 마친 뒤 새 접수 번호와 대기 상태를 반환한다. 이 응답으로 확인할 수 있는 것은 요청이 작업 목록에 들어갔다는 사실이다. 구축기가 이미 작업을 시작했는지, 검증을 통과했는지, 활성 색인이 바뀌었는지는 접수 성공만으로 알 수 없다. 접수 응답은 활성 색인 전환까지 걸리는 시간도 약속하지 않는다.

접수 번호를 받았다면 이후에는 그 번호로 작업 상태를 조회한다. 기존 활성 색인이 있는 자료집에서 접수 직후 예전 내용이 검색되더라도, 그것만으로 갱신이 실패했다고 판단할 수는 없다. 새 후보가 활성 판으로 전환되기 전까지는 기존 판을 사용하기 때문이다.

정상적인 갱신은 대기 → 구축 중 → 검증 중 → 반영 대기 → 완료 순서로 진행한다.

대기 작업 기록은 저장되었지만 구축기가 아직 시작하지 않았다. 접수는 끝났고 구축 시작을 기다리는 상태다.
구축 중 선택한 원본으로 후보 색인을 만든다. 후보는 활성 색인과 분리되어 있어 검색에 섞이지 않는다.
검증 중 후보의 문서 수와 확인용 문서 조회를 검사한다. 모든 검사를 통과해야 다음 상태로 간다.
반영 대기 검증을 통과한 후보가 활성 판으로 전환되기를 기다린다. 아직 전환 전이며, 기존 활성 판이 있다면 조회 API는 그 판을 사용한다.
완료 활성 색인 판 변경과 작업 완료 기록이 함께 확정되었다. 새 판으로의 전환이 확정된 상태다.

검증에서는 후보의 문서 수가 원본과 일치하는지 확인한다. 또한 원본에 지정된 두 확인용 문서가 정확한 키로 조회되는지 검사한다. 이 검사를 모두 통과해야 반영 대기로 이동한다. 검증이 확인하는 범위는 문서 누락과 기본 조회이며, 검색 순위의 품질을 평가한 결과는 아니다.

반영 대기는 검증을 마쳤지만 검색에 사용할 판은 아직 바뀌지 않은 상태다. 조정기가 반영할 때 자료집의 활성 색인 판 변경과 해당 작업의 완료 기록을 하나의 변경으로 함께 확정한다. 따라서 검증 통과 기록이나 반영 대기 표시만 보고 새 내용이 이미 검색된다고 안내해서는 안 된다. 전환이 확정되었는지는 완료 상태로 판단한다.

작업의 종료 상태는 완료, 실패, 중단이다. 대기, 구축 중, 검증 중, 반영 대기는 모두 진행 중 상태이므로, 이 중 어느 상태에 있든 같은 자료집의 진행 중 작업 자리를 차지한다.

완료 상태와 실제 검색 결과를 함께 읽기

조회 API는 검색 요청을 시작할 때 활성 판을 한 번 정하고, 응답을 마칠 때까지 그 판을 유지한다. 검색 도중 활성 판이 바뀌어도 같은 요청 안에서 두 판의 결과를 섞지 않는다.

예를 들어 기존 활성 판으로 검색 요청을 시작한 뒤 q203의 반영이 확정되었다고 하자. 이 검색은 q203이 완료된 뒤 응답하더라도 기존 판의 결과를 반환할 수 있다. 반영이 확정된 뒤 시작한 검색은 새 판인 i52를 사용한다.

따라서 완료 상태를 확인한 시각과 검색 응답을 받은 시각만 비교해서는 부족하다. 완료 뒤 도착한 응답이 예전 내용이라면 검색이 전환 전에 시작했는지 살펴야 한다. 새 판의 결과를 확인하려면 전환이 확정된 뒤 시작한 검색의 결과를 읽어야 한다.

실패하거나 첫 갱신이 끝나지 않았을 때

구축 또는 검증을 더 진행할 수 없는 오류가 나면 작업은 실패로 끝난다. 상태 조회에는 오류가 발생한 단계와 이유가 남으며, 해당 후보는 활성 판으로 반영하지 않는다. 기존 활성 판이 있었다면 계속 사용하므로 갱신 실패가 기존 검색의 중단을 뜻하지는 않는다.

한 번도 반영을 마치지 않은 자료집에는 유지할 기존 활성 판이 없다. 첫 갱신이 진행 중이거나 실패 또는 중단으로 끝났다면 조회 API는 색인 준비 안 됨을 반환한다. 이는 검색을 정상적으로 수행했지만 결과가 없어 빈 목록을 반환하는 경우와 구분해야 한다.

중단 요청이 수락되어도 기다려야 하는 이유

중단 요청은 대기, 구축 중, 검증 중에만 받는다. 반영 대기와 종료 상태인 완료, 실패, 중단에서는 거절한다. 수락 가능 여부는 사용자가 중단 버튼을 누른 시각이 아니라 조정기가 요청을 확인한 시점의 작업 상태로 판단한다. 버튼을 누를 때 검증 중이었더라도 조정기가 확인할 때 반영 대기라면 중단 요청은 거절된다.

중단 요청을 수락하면 먼저 중단 표시를 남긴다. 이후 조정기나 구축기가 그 표시를 확인하고 실제로 작업을 멈춘 뒤에야 상태를 중단으로 바꾼다. 그동안 상태 조회에는 직전의 진행 중 상태가 보일 수 있다. 중단 요청 수락과 작업의 중단 완료를 구분해야 하는 이유다.
