# 문서별 구성

문서의 목적에 맞는 항목만 선택합니다. 아래 소제목 흐름은 출발점이며 의무적인 목차가 아닙니다. 근거와 독자의 목적에 따라 필요한 항목을 선택하거나 합치고 순서를 바꿉니다. 짧은 요청에는 짧게 답하고, 원자료가 없는 항목을 채우기 위해 기능이나 검증 결과를 만들지 않습니다.

문서 세트를 고칠 때는 [현행 명세와 검증 이력](#현행-명세와-검증-이력)을 먼저 구분합니다. 같은 저장소의 안내·명세와 검증 보고서는 본문과 완결된 문장형 표 셀을 경어체로 맞춥니다. 명사구 표 셀, 코드·출력 원문, 명시적인 원문 인용은 구분하며, 문서 종류를 바꾸려고 검증 상태나 시제를 바꾸지 않습니다.

## README

첫 문단은 프로젝트가 무엇을 하는지 설명합니다. 기술 스택은 프로젝트 이해나 실행에 필요한 위치에 둡니다. 프로젝트의 현재 상태와 독자의 첫 행동을 우선하고, 자세한 설명은 실제로 존재하는 관련 문서로 연결합니다.

| 프로젝트 유형 | 우선 배치할 정보 |
| --- | --- |
| 애플리케이션·서비스 | 용도, 주요 동작, 실행 조건, 첫 실행, 확인 방법 |
| CLI | 처리 대상, 설치 방법, 가장 작은 실행 예, 입출력과 옵션 |
| 라이브러리 | 해결하는 문제, 설치, 최소 사용 코드, 주요 계약과 제약 |
| 게임·엔진 프로젝트 | 프로젝트 목적, 확인된 엔진 환경, 여는 대상, 실행·조작 방법 |
| 학습·연구 프로젝트 | 탐구하는 질문, 재현 범위, 실행 자료, 확인한 결과와 한계 |

설치 명령, 패키지 관리자, 작업 경로, 실행 스크립트, 포트는 저장소 자료를 확인합니다. 이미지·예시 파일·문서 링크는 존재할 때만 연결합니다. 테스트한 버전과 지원한다고 명시된 범위를 구분합니다. 모든 프로젝트에 개발 서버나 환경 변수 파일이 있다고 가정하지 않습니다.

파일 저장·변경처럼 사용 결과가 달라지는 대표 동작은 확인된 명령 형식으로 예시를 만들고, 덮어쓰기·권한·출력 위치 등 필요한 조건을 예시 바로 옆에 둡니다. 같은 기본값과 옵션 목록을 표와 설명에서 거듭 나열하지 않습니다.

다음은 구조를 보여주는 템플릿입니다. 대괄호 문구를 실제 정보로 바꾸고 불필요한 절은 제거합니다. 확인하지 못한 명령은 생성하지 않습니다.

## PR 설명과 작업 보고

소제목 흐름 예: **변경 이유 → 핵심 변경 → 영향 범위 → 검증 상태와 결과**.

변경이 필요한 이유와 바뀌는 동작을 먼저 설명합니다. 이어서 검토자가 판단할 수 있도록 핵심 변경, 영향 범위, 실제 검증 내용을 적습니다. 사소한 변경에 같은 요약을 여러 절로 반복하지 않습니다.

- 원인을 확인했으면 근거와 함께 적습니다. 원인 조사용 변경이면 조사 중인 문제와 추가한 관찰 수단을 설명합니다.
- 짧은 설명에서도 대상 시스템과 관측·검증의 한계를 구분합니다. 원자료에 왜 현재 로그나 환경만으로 판단할 수 없는지가 있으면, 단순히 미확정이라고 줄이지 않습니다.
- 관측을 보강하는 변경은 무엇을 대조하려는지와 어떤 필드를 기록하는지 연결합니다. 필요한 필드 목록은 한 번 모아 쓰고, 반복되는 도입·범위 설명을 먼저 줄여 길이를 맞춥니다. 가설과 그 판단 한계는 가까이 둡니다.
- 호환성·설정·마이그레이션 영향은 자료에서 확인된 내용만 적습니다.
- 테스트의 실행 여부, 범위, 결과를 구분합니다. 실행하지 않은 테스트는 통과 체크박스로 표시하지 않습니다.
- 배포 계획과 운영 반영 완료를 구분합니다. 주어지지 않은 일정을 약속하지 않습니다.

## 버그 리포트와 장애 기록

증상과 조건이 드러나는 제목을 붙입니다. 확인된 발생 환경, 재현 순서, 기대 결과와 실제 결과, 관찰 근거를 적습니다. 정확한 빈도를 모르면 횟수를 만들지 않습니다.

원인을 모를 때도 기록을 완성할 수 있습니다. 조사 기록의 소제목 흐름 예: **관찰 → 조사한 가설 → 확인 방법과 결과 → 현재 판단 → 남은 확인**. 시도한 가설의 수나 조사 결말을 미리 정하지 않습니다. 임시 완화와 근본 원인 해결을 구분합니다.

## 기술 조사와 검토 보고서

소제목 흐름 예: **핵심 결론 → 발견별 번호형 요약 → 조사 범위와 자료 → 상세 근거 → 권고와 확인할 항목**.

독립된 발견이 여러 개면 요약도 발견별로 나눕니다. 제목에는 대상과 결론을 쓰되 원인 미확정·조건부 동작·제안 상태를 유지합니다. 운영 관측, 별도 환경의 실험, 성능 측정, 도입 권고가 서로 다른 질문에 답하면 문단을 나눕니다.

- 표본의 출처·환경·시점·평가 방법을 결과와 연결합니다. 같은 자료를 다시 적용한 재현과 독립 평가를 구별하고, 단독 지연 측정을 전체 시스템 성능으로 합치지 않습니다.
- 수치가 여러 개면 대상·조건·지표·결과를 같은 표에서 대응시킵니다. 비교에 필요한 분모와 측정 횟수를 생략하거나 서로 다른 집단의 결과를 한 성과로 합치지 않습니다.
- 공통 조사 범위는 한 번 설명합니다. 개별 결론의 신뢰도에 영향을 주는 미열람·미대조 사실은 해당 결론 가까이에 남깁니다. 수집 경로나 검토 규칙을 지켰다는 설명을 매 문단 끝에 붙이지 않습니다.
- 근거 경로·행 범위는 주장별로 연결하고, 여러 저장소의 긴 목록은 본문과 분리합니다. 파일이 존재한다는 관측과 그 내용을 확인했다는 관측을 구분합니다.

다음은 여러 발견이 있는 보고서의 구조 예시입니다. 항목 수는 실제 자료에 맞추고, 기존 제목 단계에 맞춰 사용합니다.

```markdown
## 핵심 요약

### 1. [첫 발견의 대상과 결론]

[같은 환경·시점의 핵심 관측과 의미를 설명한다.]

### 2. [별도 실험의 조건과 결과]

[표본·평가 방법과 결과를 연결하고 필요한 수치는 표로 대응시킨다.]

### 3. [권고안과 적용 조건]

[왜 권장하는지와 확인할 조건을 적는다.]

## 조사 범위

[전체에 공통인 자료·시점·방법을 적는다.]

## 상세 근거

[주장별 설명 바로 아래에 정확한 확인 근거를 연결한다.]
```

## 아키텍처와 프로젝트 현황

소제목 흐름 예: **목적과 범위 → 구성 요소와 책임 → 데이터 흐름 → 의존성과 제약 → 장애 처리 경계**.

시스템의 목적과 문서가 다루는 범위를 먼저 밝힙니다. 주요 구성 요소의 책임과 경계, 데이터의 이동, 외부 의존성, 중요한 제약을 설명합니다. 기술 이름만 나열하는 구조 설명은 피합니다.

- 구성 요소를 나열한 뒤 요청이나 데이터가 실제로 어떻게 흐르는지 연결합니다.
- 설계 이유가 자료에 있으면 선택의 배경과 비용을 설명합니다. 확인하지 않은 의도를 구현에서 역으로 단정하지 않습니다.
- 현재 구현, 운영 설정, 제안된 변경을 구분합니다. 서로 다른 시점의 정보를 하나의 현재 상태로 합치지 않습니다.
- 과거 실행의 임시 경로·일회성 프로세스 정보·수정 일지는 별도 검증 이력으로 연결합니다. 현재 구성에 필요한 값과 실패 조건은 본문에 유지합니다.
- 장애·재시도·저장 책임 등 중요한 경계는 확인된 내용까지만 적습니다.
- 응답을 찾아보는 절에서는 수락·성공과 오류의 범위를 함께 확인하게 합니다. 요청 흐름에서 이미 설명한 역할을 표 뒤에 다시 풀기보다 저장·재시도 경계 등 새 관계만 연결합니다.
- 관계를 이해하는 데 도움이 될 때만 도식을 사용합니다. 도식에도 확인되지 않은 연결을 추가하지 않습니다.

## ADR

소제목 흐름 예: **제안·결정의 상태와 요약 → 배경과 제약 → 검토한 선택지 → 선택 이유 → 결과·비용과 미결 사항**.

결정의 상태, 배경과 제약, 검토한 선택지, 결정과 이유, 결과와 감수하는 비용을 기록합니다. 선택지가 하나만 기록돼 있으면 경쟁안을 만들지 않습니다. 제안 단계의 결정을 채택 완료로 바꾸지 않습니다. 선택하지 않은 대안은 자료에 있는 비교 기준으로 설명합니다.

대안 표에서 선택 이유까지 충분히 설명했다면 뒤에서 같은 장점을 다시 나열하지 않습니다. 승인 전 검토 항목에는 결정에 필요한 현재 근거 상태도 붙입니다. 측정되지 않은 비용이나 정하지 않은 보장 범위를 먼 절에서만 확인하게 하지 않습니다.

## 운영 절차

소제목 흐름 예: **적용 상황 → 준비와 조치 범위 → 단계별 실행·확인·중단 조건 → 복구 확인과 실패 시 대응**.

적용할 상황과 범위를 먼저 적고, 필요한 권한·준비 상태, 실행 순서, 확인 기준, 실패 시 중단·복구 조건을 정리합니다. 독자가 필요한 정보를 찾을 수 있도록 점검과 상태 변경을 구분합니다.

- 환경과 명령을 임의로 추정하지 않습니다. 비밀 값 대신 자료에 있는 변수명이나 참조 위치를 사용합니다.
- 각 실행 단계를 **선행조건 → 명령 → 확인할 결과 → 실패·중단 대응**으로 연결합니다. 명령을 바로 찾는 독자에게 필요한 복합 조건과 대기 한계를 같은 절에 둡니다. 시간 한계는 어느 사건부터 세는지 함께 적고, 접수 응답과 실제 완료를 구분합니다. 자료에 없는 성공 기준은 만들지 않습니다.
- 마지막 이관 절에 중단 기준을 모을 때는 긴 조건문 하나로 합치지 않습니다. 공통 조치와 전달할 정보를 구분하고, 각 조건은 목록이나 표에서 따로 읽게 합니다.
- 재시작·재실행·복구 절차가 제공되지 않았다면 일반적인 명령으로 채우지 않습니다.
- 실제 실행한 점검과 문서상 제안하는 점검을 구분합니다. 읽기 좋은 절차를 만들기 위해 운영 작업을 실행하지 않습니다.
- 반복해서 사용할 운영 절차와 특정 날짜에 실행한 기록을 분리합니다. 현재 절차에는 준비·명령·확인·중단 기준을 남기고, 실제 실행 값과 로그는 이력 문서에 보존합니다.

## API 안내와 튜토리얼

API 소제목 흐름 예: **사용 목적 → 인증과 입력 → 요청·응답 예 → 오류와 재시도 조건**.

API는 사용 목적, 인증·입력 계약, 요청과 응답 예, 실제 오류 동작을 연결합니다. 필수·선택 필드, 기본값, 단위, 누락과 빈 값의 차이를 자료에 따라 적습니다. 재시도·중복 처리·호출 제한은 확인된 계약만 설명합니다.

API 명세의 경로·메서드·필드·상태 코드와 예시 명령은 원형을 보존합니다. 설명의 직역 표현이나 공백을 고치면서 식별자를 번역하지 않습니다. 특정 실행의 요청·응답 로그는 원문 기록으로 분리하되, 미검증인 동작을 확인된 계약으로 바꾸지 않습니다.

초기 상태의 예외와 오류·거절 응답은 어떤 요청·조건에 대응하는지 함께 설명하고, 제목이나 항목명에서 그 위치를 찾을 수 있게 합니다. 재요청할 수 있는 시점이나 상태 변화가 자료에 있으면 해당 응답 옆에 둡니다. 준비 절만 읽어도 필요한 입력 이름을 알 수 있게 하며, 특정 사용 사례 안에만 일반적인 거절 기준을 남기지 않습니다.

튜토리얼 소제목 흐름 예: **목표와 시작 조건 → 단계별 작업과 확인 → 최종 결과 확인**.

튜토리얼은 시작 조건부터 독자의 행동 순서로 구성합니다. 코드가 들어갈 위치와 그 단계에서 확인할 결과를 알려 줍니다. 필요한 설명만 코드 앞뒤에 붙이고, 이미 설명한 코드를 문장으로 한 줄씩 반복하지 않습니다.

## 기술 글과 회고

소제목 흐름 예: **핵심 내용 → 문제와 배경 → 주요 시도와 판단 → 결과와 한계**.

독자가 얻을 내용이나 현재 결론을 앞에서 밝힙니다. 문제와 배경, 판단에 필요한 과정, 관찰 결과와 한계를 이어 씁니다. 탐색 과정을 모두 나열하기보다 결론을 이해하는 데 필요한 시도를 선택합니다. 실패한 가설이나 교훈을 형식에 맞추려고 새로 만들지 않습니다.

## 현행 명세와 검증 이력

문서의 역할을 먼저 정하면 현재 계약과 과거 관찰이 섞이는 일을 줄일 수 있습니다. 별도 이력 문서로 옮길 때도 사실을 삭제하지 않으며, 기존 문서·절을 참조하는 링크는 유지합니다.

| 구분 | 본문에 남길 내용 | 별도 문서로 보존할 내용 |
| --- | --- | --- |
| 현행 아키텍처·운영·API 명세 | 현재 구성·계약·실행 조건·예외·미검증 범위 | 특정 실행의 임시 폴더, 일회성 PID·포트·컨테이너 ID, 단계별 시험 로그 |
| 검증·인계 이력 | 날짜·대상·방법·실행 여부·관측 결과·제한 | 원시 명령·출력·오류의 정확한 사본과 관련 파일 |
| 원본 보존용 사본 | 원본의 출처와 검증 가능한 보존 정보 | 원문은 그대로 두고 설명 교정이 필요하면 별도 문서에 작성합니다. |

현행 명세의 말미에 실행 기록을 계속 덧붙이지 않습니다. 저장소에 이미 있는 `work_history.md`나 `docs/evidence/` 등의 체계를 확인하고 실제 존재하는 파일로 연결합니다. 파일 이름은 예시이며 모든 프로젝트에 같은 경로를 강요하지 않습니다. 현재 운영에 필요한 고정 포트나 실패 시 중단 기준은 실행 기록으로 오인해 옮기지 않습니다.

이력 문서는 검증 범위·서버 확인 단계·실행 정책 제한처럼 객관적인 조건으로 설명합니다. 에이전트 대화방이나 내부 작업자 이름을 제품 구성 요소로 쓰지 않습니다. 정확한 오류 문자열과 설정을 인용해야 하면 원문 사본을 남기며, 차단·미실행·미확인 상태를 성공으로 바꾸지 않습니다.

제목을 다듬으면 기존 자동 생성 앵커를 확인하고 제목 위에 같은 `id`의 HTML 앵커를 추가합니다. 문서 밖에서 들어오는 링크도 보존할 수 있도록 현재 저장소에 링크가 없다는 이유만으로 기존 앵커를 없애지 않습니다. 전체 Markdown의 로컬 링크와 문서 간 앵커를 마지막에 다시 검사합니다.
