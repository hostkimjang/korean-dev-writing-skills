# Harbor Intake 이벤트 수집 서비스 아키텍처

Harbor Intake는 HTTP로 제출된 이벤트를 Kafka를 거쳐 PostgreSQL에 저장하는 서비스입니다. 이벤트 수집 API와 연동하거나 운영을 인계받을 때는 **큐 수락과 최종 저장 완료를 구분해야 합니다.** `202` 응답은 Kafka에 이벤트가 수락되었다는 뜻이며, 데이터베이스 저장 완료를 뜻하지 않습니다.

## 구성 요소와 책임

| 구성 요소 | 역할 |
| --- | --- |
| `collector-api` | `POST /v1/events` 요청의 토큰과 스키마를 확인하고, 유효한 이벤트를 Kafka에 발행합니다. |
| Kafka 토픽 `telemetry.raw.v1` | `collector-api`가 발행한 이벤트를 `event-writer`가 읽는 토픽입니다. |
| `event-writer` | 토픽에서 이벤트를 읽어 데이터베이스에 기록하고 Kafka offset을 커밋합니다. |
| PostgreSQL 데이터베이스 `event_store` | 이벤트를 저장합니다. `event_id`의 유일성 제약으로 중복 이벤트를 식별하는 기준을 제공합니다. |

## 이벤트 제출부터 저장까지

### 요청 검증과 큐 수락

클라이언트는 `POST /v1/events`에 이벤트를 제출합니다. `collector-api`는 토큰과 스키마를 확인한 뒤 `telemetry.raw.v1`에 이벤트를 발행합니다. Kafka 발행이 확인되면 클라이언트에 `202`와 `event_id`를 반환합니다.

이 응답만으로는 `event_store` 저장 완료 여부를 판단할 수 없습니다. 현재 구현에는 `event_id`로 최종 저장 상태를 조회하는 API도 없습니다.

### 데이터베이스 기록과 offset 커밋

Kafka에 발행된 이벤트는 API 응답과 별개로 `event-writer`가 소비합니다. `event-writer`는 이벤트를 `event_store`에 기록하고, **데이터베이스 트랜잭션이 성공한 뒤 Kafka offset을 커밋합니다.**

데이터베이스 기록과 offset 커밋은 구분되는 단계입니다. 기록이 성공했더라도 offset을 커밋하기 전에 작업자가 종료되면 같은 이벤트를 다시 읽을 수 있습니다. 이때 추가 행이 생기지 않도록 처리하는 방식은 아래의 ‘저장 장애와 중복 처리’에서 설명합니다.

## API 오류 응답과 클라이언트 재시도

`collector-api`의 오류 응답은 다음과 같습니다.

| 응답 코드 | 발생 조건 |
| --- | --- |
| `401` | 유효하지 않은 토큰으로 요청했습니다. |
| `400` | 요청에 스키마 오류가 있습니다. |
| `503` | Kafka 발행에 실패했습니다. |

클라이언트는 `503` 이후 재시도하는 경우를 포함해, **같은 논리적 이벤트를 다시 제출할 때 같은 `event_id`를 사용해야 합니다.** `collector-api` 자체에서는 중복 요청을 제거하지 않으므로, 같은 이벤트를 재시도하면 Kafka에 중복으로 전달될 수 있습니다. 중복 이벤트의 저장 처리는 `event-writer`와 `event_store`가 담당합니다.

## 저장 장애와 중복 처리

Harbor Intake의 전송 및 소비 과정에서는 이벤트가 중복으로 전달될 수 있습니다. `event_store`에는 `event_id`의 유일성 제약이 있으며, `event-writer`는 이 제약으로 확인된 중복 이벤트를 이미 기록된 이벤트로 취급해 추가 행을 만들지 않습니다. 중복 여부를 판단하는 기준이 `event_id`이므로, 클라이언트 재시도에서도 같은 식별자를 유지해야 합니다.

저장 과정에서 장애가 발생하면 데이터베이스 기록과 offset 커밋 중 어디까지 완료되었는지에 따라 재처리 동작이 달라집니다.

| 장애 상황 | offset 처리 | 재처리 동작 |
| --- | --- | --- |
| 데이터베이스 쓰기 실패 | 해당 이벤트의 offset을 커밋하지 않습니다. | 데이터베이스가 회복되면 `event-writer`가 미커밋 이벤트를 다시 처리합니다. |
| 데이터베이스 기록 후, offset 커밋 전에 작업자 종료 | 기록은 완료되었지만 offset은 커밋되지 않은 상태입니다. | `event-writer`가 같은 이벤트를 다시 읽을 수 있습니다. 이미 저장된 `event_id`는 중복으로 처리해 추가 행을 만들지 않습니다. |

따라서 Kafka 발행 실패에 대한 클라이언트의 재제출과, 저장 단계에서 `event-writer`가 수행하는 재처리는 구분해야 합니다. `202`를 받은 뒤 데이터베이스 쓰기에 실패한 경우에는 해당 offset을 커밋하지 않고, 데이터베이스 회복 후 `event-writer`가 다시 처리합니다.

## 운영 인계 시 확인할 항목

다음 항목은 제공된 구현 메모에서 확정되지 않았습니다.

- Kafka 보존 기간
- 공식 처리량 목표
- 장애 복구 시간 목표

운영 계획을 세울 때는 이 값을 별도로 확인해야 합니다. 이 문서에 설명된 재처리 동작만으로 이벤트가 무기한 보존되거나 일정 시간 안에 복구된다고 판단해서는 안 됩니다.
