# 한국어 개발 문서 작성 비교 실험 프로토콜

## 목적과 범위

같은 개발 문서 요청에 대해 스킬 미적용, 기존 스킬 적용, 개선 스킬 적용이라는 세 조건의 결과를 비교한다. 실제 업무에 가까운 합성 사례 여섯 개를 한 번씩 생성해 총 18개 출력으로 평가한다. 이 실험은 작은 탐색 실험이다. 관찰된 차이를 이 사례·이 실행의 결과로 보고하며, 모든 문서 유형이나 모든 실행에서 개선이 보장된다고 일반화하지 않는다.

사례에 등장하는 프로젝트, 서비스, API, 저장소, 명령, 로그, 이슈, 운영 절차와 데이터는 모두 이 실험을 위해 만든 가상 자료다. 공개해도 되는 자료이며 실제 고객 정보나 운영 비밀을 포함하지 않는다. 명령의 존재와 동작은 사례의 원자료에 근거해 검증한다. 가상 패키지를 실제로 설치하거나 가상의 운영 명령을 실행할 필요가 없다.

사례와 평가기준은 작성 스킬의 내용을 보지 않는 별도 작성자가 마련한다. 기존 스킬과 개선 스킬을 동결한 뒤 비교하며, 결과를 보고 사례·기준·스킬을 고쳐 동일 실행의 성공 사례로 다시 보고하지 않는다. 부득이한 수정이 생기면 변경 이유와 시점을 기록하고 별도 실행으로 다룬다.

## 파일과 역할

| 파일 | 용도 |
| --- | --- |
| `cases/01_cli_readme.json` | 로컬 로그 CLI의 README 신규 작성 |
| `cases/02_event_architecture.json` | 내부 이벤트 수집 서비스 아키텍처 문서 |
| `cases/03_investigation_pr.json` | 조사 중인 중복 발송 문제의 진단 PR 설명 |
| `cases/04_incident_runbook.json` | 배포 후 적체에 대응하는 운영 절차 |
| `cases/05_storage_adr.json` | 중복 판정 저장소에 관한 ADR 초안 |
| `cases/06_paragraph_edit.json` | 어색한 한국어 기술 문단 편집 |
| `rubric.json` | 다섯 평가 차원의 0~4점 앵커와 hard_fail 기준 |

사례 JSON의 `user_prompt`는 세 조건에 공통으로 사용할 자연스러운 요청이다. `source_facts`와 `source_draft`는 생성자가 사용할 원자료이고, `audience`와 `document_purpose`는 동일한 작업 맥락이다. `source_facts.certainty`는 `confirmed`, `hypothesis`, `unknown` 중 하나다. 가설과 미확인 사항을 확인된 사실로 승격하지 않아야 한다. `source_draft`는 편집 사례에서만 문자열이며 다른 사례에서는 `null`이다.

`verifiable_claims`와 `expected_checks`는 평가자 전용이다. 생성자에게는 보내지 않는다. 평가자는 각 명제의 `source_refs`를 통해 사실을 원자료와 대조한다. `required=true`와 `must_include`는 핵심 범위이며, 선택 명제를 전부 포함할 필요는 없다. `preserve_identifiers`는 해당 항목을 사용할 때 보존할 식별자를 뜻한다. 목록에 있다는 이유만으로 모든 식별자를 본문에 넣으라는 뜻은 아니다.

`length_guidance`는 실제 사용 예시의 규모를 짐작하기 위한 메타데이터다. README·아키텍처·운영 절차·ADR은 600~1000자, PR은 400~700자, 문단 편집은 300~500자를 참고 범위로 둔다. 이번 실행에서는 생성자에게 별도의 글자 수 조건을 부과하지 않는다. 출력 길이는 평가의 합격 조건이나 점수가 아니며, 단순한 길이 차이를 품질 차이로 해석하지 않는다.

## 생성 조건 고정

실행 관리자는 다음 사항을 출력 생성 전에 고정하고 기록한다.

1. 기존 스킬과 개선 스킬의 정확한 버전 또는 파일 해시를 기록한다. 미적용 조건에는 두 작성 스킬 중 어느 것도 제공하지 않는다.
2. 여섯 사례, `rubric.json`, 이 프로토콜의 버전 또는 해시를 기록한다. 평가 전에 기준을 동결한다.
3. 모든 생성 작업에 같은 상속 모델과 같은 공통 실행 설정을 사용한다. 모델을 조건별로 바꾸지 않는다. 설정을 직접 제어할 수 없다면 제어 가능한 항목과 플랫폼 기본값 사용 여부를 실행 기록에 남긴다.
4. 각 `case × condition`을 새롭고 독립된 컨텍스트에서 실행한다. 총 18개의 개별 작업으로 만들고, 이전 출력·다른 조건의 스킬·평가 결과·개선 이력을 전달하지 않는다.
5. 각 생성자에게 같은 사례의 `audience`, `document_purpose`, `user_prompt`, `source_facts`, 그리고 값이 있는 `source_draft`를 동일하게 전달한다. 해당 조건의 작성 스킬 유무 및 버전만 달라진다. 평가용 필드는 제외한다.
6. 상속되는 공통 시스템·개발자 지침, 파일 접근 및 도구 접근은 가능한 범위에서 일치시킨다. 미적용은 공통 지침이 전혀 없는 모델이라는 뜻이 아니라, 비교 대상 작성 스킬을 추가하지 않은 조건이다.
7. 파일을 직접 읽을 수 있는 생성자에게도 다른 조건의 스킬·출력·평가기준을 읽지 않도록 작업 범위를 제한한다. 전달한 자료와 스킬 경로를 실행 기록에 남긴다.

각 조건은 한 번만 생성한다. 결과가 마음에 들지 않는다는 이유로 재생성하거나 생성 후 사람이 편집하지 않는다. 도구 오류나 연결 실패로 사용 가능한 출력이 아예 없을 때만 같은 입력으로 다시 시도하고 사유와 횟수를 기록한다. 결과물에 실제 잘림이나 형식 오류가 있으면 이를 숨기지 않는다. 출력 예산 때문에 조건 하나만 불리해진 것이 확인되면 같은 실행의 일부만 교체하지 않고 제한 사항을 보고한다.

## 무작위 라벨과 블라인드 평가

생성 단계에서는 작성자가 자신에게 주어진 스킬을 알 수 있지만, 평가자는 적용 조건을 알 수 없게 한다.

실행 관리자는 18개 출력에 조건명을 포함하지 않는 무작위 라벨을 부여한다. 라벨과 조건의 대응표 및 무작위화에 쓴 시드는 평가자에게 전달하지 않는다. 같은 조건에 같은 접두사를 반복해서 써서 조건을 추정할 수 있게 하지 않는다. 사례별 세 출력의 표시 순서도 무작위로 섞는다. 파일 이름, 디렉터리명, 전달 메시지에 조건이 드러나지 않도록 한다.

평가자는 원자료, 사례의 평가용 필드, 동결한 rubric, 무작위 라벨의 출력만 받는다. 스킬 내용과 조건별 가설은 제공하지 않는다. 평가자가 문체를 보고 조건을 추정할 수 있다는 한계는 남지만, 스스로 추정한 조건을 채점 근거로 사용하지 않는다. 출력 본문에 스킬이나 조건이 직접 언급돼 있다면 원문을 고치지 않고 블라인드 훼손 사실을 기록한다.

평가자는 먼저 각 출력을 절대 기준으로 채점한다. 사례별 세 출력의 비교 소감은 절대 채점을 마친 뒤 적는다. 점수, 근거, hard_fail 판단을 저장하고 동결한 다음에만 대응표를 열어 조건을 해제한다. 평가자 수, 평가에 사용한 모델 또는 사람의 역할, 원자료 확인을 위한 재검토 여부를 실행 기록에 남긴다. 의견이 다른 판단을 합의로 바꿀 때는 최초 판단과 조정 이유도 남긴다.

## 사실 보존과 자연스러움의 균형

평가는 다섯 차원에 같은 비중을 둔다. 사실 정확성, 정보 완결성, 독자·목적·구조, 한국어 문장·문단 자연스러움, 실행 가능성·형식에 각각 0~4점을 주므로 총점은 20점이다. 치명적 사실왜곡은 별도 `hard_fail`로 표시한다.

원문 보존은 표현을 복제했는지가 아니라 의미를 지켰는지로 평가한다. 코드 식별자, 경로, 옵션, 기본값, 버전, 상태, 조건과 동작의 관계는 정확히 대조한다. 의미가 같은 요약, 제목 변경, 문장 분리와 결합, 문단 순서 변경, 자연스러운 동의어는 허용한다. 편집 사례는 원문에 담긴 사실 묶음을 모두 보존해야 하지만 원문의 어순이나 어미를 유지할 필요는 없다.

자연스러움은 특정 단어의 존재 여부나 명사형 문장의 수로 자동 판정하지 않는다. 문장 호응, 독자가 행위 주체와 조건을 파악할 수 있는지, 문단 사이의 정보 연결, 반복과 군더더기가 이해를 방해하는지를 실제로 읽고 판단한다. 전문 용어, 영어 식별자, 필요한 수동 표현이나 명사형 제목의 사용 자체는 오류가 아니다.

명령과 절차가 없는 문서에 명령 예제나 확인 단계를 억지로 요구하지 않는다. 아키텍처 문서는 책임과 보장 경계, PR은 변경·증거·리뷰 범위, ADR은 제안·대안·결과·미결 사항, 편집은 원뜻과 게시 가능성을 중심으로 실행 가능성·형식을 판단한다.

각 점수에는 근거가 있어야 한다. 사실 오류라면 출력 구절과 원자료 ID를 함께 제시하고, 자연스러움 문제라면 어떤 문장이 왜 이해를 늦추는지 설명한다. `hard_fail`은 일반적인 문체 불호나 가벼운 누락의 다른 이름이 아니다. 사례의 `hard_fail_if`와 rubric의 정의에 비춰 실제로 판단을 뒤집는 왜곡인지 확인한다. 같은 출력에서 자연스러움 점수가 높아도 hard_fail이 사라지지 않는다.

## 결과 보고

블라인드 평가를 동결한 뒤 조건을 해제하고 다음 내용을 함께 보고한다.

- 사례별 세 조건의 다섯 차원 점수, 총점, hard_fail 여부
- 조건별 차원 평균과 총점 평균, hard_fail 건수
- 사례별 개선 조건과 기존 조건, 미적용 조건의 점수 차이
- 차이를 설명하는 구체적인 문장 또는 문단 예와 원자료 근거
- 각 출력의 길이 등 해석에 필요한 보조 정보. 길이에 대한 별도 가감점은 하지 않는다.
- 효과가 불분명하거나 나빠진 사례, 블라인드 훼손, 생성 실패 등 불리한 관찰도 포함한 제한 사항

hard_fail이 있는 결과를 총점만으로 우수하다고 결론내리지 않는다. 반대로 hard_fail 결과를 임의의 총점 0으로 바꾸어 원래의 차원별 판단을 숨기지 않는다. 명백한 산술 오류를 수정하는 경우를 제외하면 조건을 안 뒤 점수를 재조정하지 않는다.

총 18개 출력은 독립적인 대규모 표본이 아니라 여섯 개 합성 요청의 조건별 짝 비교다. 한 모델의 한 번 생성과 제한된 문서 유형만 보며, 생성의 확률적 변동, 평가자의 취향, 합성 자료와 실제 업무의 차이를 분리할 수 없다. 유의미한 일반화나 통계적 유의성 주장을 하지 않는다. 후속 검증은 새로운 사례, 여러 번 생성, 외부 독자 평가 등을 별도 실행으로 계획할 수 있다.
