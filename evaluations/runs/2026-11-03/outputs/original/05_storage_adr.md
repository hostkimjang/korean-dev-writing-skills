# ADR-007: 이벤트 중복 판정 저장소

이벤트 중복 판정 기록을 PostgreSQL의 `event_receipts` 테이블에 저장하고, 업무 이벤트 생성과 같은 트랜잭션에서 처리하는 방식을 제안합니다.

- **작성일**: 2026-10-15
- **상태**: 제안
- **검토 상태**: 데이터·운영 담당자 검토 미완료

## 배경과 요구사항

기존 이벤트 API는 PostgreSQL에 업무 이벤트를 저장합니다. 같은 테넌트에서 같은 이벤트를 다시 제출하더라도 업무 이벤트를 중복 생성하면 안 됩니다. 중복 판정 기준은 다음과 같습니다.

- 같은 `tenant_id`에서 같은 `event_id`를 제출하면 중복으로 판정합니다.
- 서로 다른 `tenant_id`에서는 같은 `event_id`를 허용합니다.
- 과거 이벤트를 다시 가져오는 작업에도 같은 중복 판정 기준을 적용합니다.

중복 판정 기록의 보존 기간은 아직 정하지 않았습니다. 과거 이벤트 재수집도 판정 대상이므로, 보존 정책이 요구사항을 충족하는지 검토해야 합니다.

## 제안하는 저장 방식과 처리 흐름

PostgreSQL에 `event_receipts` 테이블을 추가하고, `(tenant_id, event_id)`에 유일성 제약을 설정합니다. 중복 판정 기록 저장과 업무 이벤트 생성을 하나의 데이터베이스 트랜잭션으로 묶습니다.

| 조건 | 제안하는 처리 |
| --- | --- |
| 중복 판정 키가 없음 | 중복 판정 기록과 업무 이벤트를 같은 트랜잭션에서 생성합니다. |
| 같은 `(tenant_id, event_id)` 키가 이미 있음 | 업무 이벤트를 새로 만들지 않습니다. |
| 데이터베이스 작업 실패 | 요청에 `503`을 반환합니다. 클라이언트는 같은 `tenant_id`와 `event_id`로 재시도합니다. |

두 기록을 같은 트랜잭션에서 처리하면 중복 판정 기록만 남거나 업무 이벤트만 생성되는 상태를 방지합니다. 재시도에도 같은 식별자를 사용해야 기존 처리 여부를 같은 키로 판정합니다.

## 이 방식을 제안하는 이유

업무 이벤트를 저장하는 PostgreSQL에서 중복 여부도 판정하면 기존 데이터베이스 트랜잭션을 그대로 사용합니다. 중복 판정 기록과 업무 이벤트를 함께 저장하기 위해 저장소 간 처리 절차를 추가로 설계할 필요가 없습니다.

별도 Redis 운영을 추가하지 않는다는 이점도 있습니다. 다만 PostgreSQL을 사용한다고 해서 추가 비용이 없어지는 것은 아닙니다. 중복 판정 기록을 쓰고 인덱스를 유지하는 부하는 기존 데이터베이스가 부담합니다.

## 검토한 대안: Redis 키와 TTL

대안은 Redis에 중복 판정 키를 저장하고 TTL을 설정하는 방식입니다. 다음 이유로 PostgreSQL 방식을 우선 제안합니다.

| 비교 항목 | PostgreSQL `event_receipts` | Redis 키와 TTL |
| --- | --- | --- |
| 업무 이벤트 생성과 함께 처리 | 기존 PostgreSQL 트랜잭션으로 처리합니다. | PostgreSQL의 업무 이벤트 생성과 원자적으로 처리하려면 추가 설계가 필요합니다. |
| 과거 이벤트 재수집 | 판정 기록이 남아 있는 동안 같은 키를 중복으로 판정합니다. 보존·정리 정책은 미정입니다. | TTL 만료 또는 키 유실 뒤 과거 이벤트가 다시 들어오면 중복을 놓칠 수 있습니다. |
| 운영 부담 | 별도 Redis 운영을 추가하지 않습니다. 기록 정리 정책이 필요합니다. | 중복 판정에 사용하는 Redis 운영을 추가해야 합니다. |
| 성능과 부하 | 기존 데이터베이스의 쓰기·인덱스 부하가 늘어납니다. 추가 비용은 아직 측정하지 않았습니다. | 이번 자료에는 성능 측정 결과가 없어 성능 우위를 판단하지 않습니다. |

과거 이벤트 재수집을 중복 판정 대상에 포함하면서 TTL이나 키 유실 뒤 중복을 놓치는 문제를 해결해야 한다는 점, 두 저장소의 기록을 함께 처리하는 설계가 필요하다는 점이 Redis 대안의 주요 부담입니다.

## 도입 시 감수할 점과 보장 범위

`event_receipts`를 추가하면 이벤트 처리에 필요한 쓰기와 인덱스 부하가 늘어납니다. 기록이 쌓이므로 보존 기간과 정리 정책도 마련해야 합니다. 현재 부하에서 추가 비용을 측정한 결과는 없습니다. 이 제안이 지연 시간이나 처리량에 미치는 영향은 성능 검증으로 확인해야 합니다.

유일성 제약을 통한 중복 판정은 해당 키의 기록이 남아 있다는 전제에 의존합니다. 기록을 삭제한 뒤 같은 과거 이벤트가 다시 들어오면 이 설계만으로 중복 생성을 막는다고 보장하지 못합니다. 따라서 보존 기간을 정하기 전에는 과거 이벤트 중복 판정의 시간 범위를 확정할 수 없습니다.

이 ADR은 공식 지연 목표나 처리량 보장을 정하지 않습니다. PostgreSQL 선택은 트랜잭션 처리와 운영 구성에 근거한 제안이며, 성능 측정으로 우위를 확인한 결론은 아닙니다.
