# Gemini 협업 리뷰 대조와 v0.4.0 반영

검토일: 2026-11-03 (Asia/Seoul). 사용자가 전달한 Gemini 협업 리뷰를 [검토 당시 v0.3.0 저장소](https://github.com/hostkimjang/korean-dev-writing-skills/tree/6202f14aa08cbc9ddda6bd0ffd62bbbf022033ac)와 대조했다. 외부 리뷰의 제안을 모두 사실로 전제하지 않고, 실제 출력에서 확인된 문제와 원인에 대한 추정을 구분했다.

**탐색할 위치, 시스템 조건과 확인 절차, 짧은 글의 판단 근거 보존은 보완했다. 재환기의 한 문장 상한은 채택하지 않았다.** 기존 지침을 구체화한 변경이며, 새 지침의 효과는 [현재 비교 보고서](evaluation.md)에서 실제 생성 결과와 함께 확인한다.

## 관찰과 원인 추정을 구분하기

리뷰는 v0.3.0의 남은 문제가 생성 편차가 아니라 지침 충돌에서 비롯됐다고 단정했다. 그러나 기존 실행은 현재 조건만 한 번씩 새로 생성하고 과거 조건의 원문을 재사용했다. 지침별 영향을 나눠 비교하거나 반복 생성한 실험이 아니므로 둘 중 어느 쪽이 원인인지 확정할 수 없다. [v0.3.0 실행 프로토콜](../evaluations/runs/2026-11-03-v0.3.0-refresh/protocol.md)

기존 지침에도 이해하기·실행하기·찾아보기를 구분하고, 중요한 조건은 실행 직전이나 독립적으로 읽는 절에 다시 남기라는 원칙이 있었다. 따라서 반복 축소와 필요한 조건 반복을 양립 불가능한 지시로 보기는 어렵다. 이번 보완은 원칙의 적용 대상을 더 구체적으로 쓰는 데 초점을 둔다. [이전 읽기 흐름 지침](../evaluations/runs/2026-11-03-v0.4.0/snapshots/v0.3.0/references/reading-flow.md)

v0.2.0을 전반적인 과잉 압축으로 판정하는 것도 근거를 넘어선다. 앞선 익명 검토에서는 아키텍처·ADR·운영 절차의 세 조건 모두 필수 명제를 보존했다. v0.2.0 ADR처럼 비용과 보장 범위를 같은 절에서 찾기 좋은 구성도 있었다. 설명의 친절함과 국소적인 조건 배치의 차이는 비교할 수 있지만, 길이가 늘었다는 사실만으로 잃었던 필수 내용이 복원됐다고 설명하지 않는다. [장문 검토](../evaluations/runs/2026-11-03-v0.3.0-refresh/reviews/review-long.md)

### 온보딩의 표현을 어느 정도 문제로 보는가

v0.3.0 온보딩은 “전환이 확정된 뒤 시작한 검색은 새 판을 사용합니다”라고 먼저 설명한다. 이어 “완료를 확인한 뒤 검색 요청을 시작해야 합니다”라고 안내한다. 앞은 시스템의 판 선택 기준, 뒤는 새 결과를 확인할 수 있는 절차다. 사람이 조회해야만 전환된다는 규칙을 새로 쓴 것은 아니다. 다만 확인 절차와 시스템의 필요조건이 섞여 읽힐 여지가 있어 표현을 정밀하게 하는 지침을 보완했다. [당시 원문](../evaluations/runs/2026-11-03-v0.3.0-refresh/outputs/latest/07_index_onboarding.md)

### 짧은 PR에서 남은 것과 줄어든 것

v0.3.0 당시 비교의 이전 짧은 PR은 v0.2.1이며 v0.2.0이 아니다. v0.3.0 원문은 원인 미확정, 실제 영향 미확인, 빈도 미집계, 테스트 미실시, 변경 후 로그 미수집을 유지했다. 서비스명, 특정 관측 수단만으로 판단할 수 없는 이유, 다음 관측의 구체적 비교 목적은 압축됐다. 이 손실을 불확실성 전체가 사라진 치명적 왜곡으로 확대하지 않는다. [당시 원문](../evaluations/runs/2026-11-03-v0.3.0-refresh/outputs/latest/08_short_log_pr.md)

## 필수 보존 기준은 새로 도입한 것인가

기본 여섯 사례에는 이미 검증 명제 45개 중 필수 명제 39개와 `must_include`가 있었다. 읽기 흐름 두 사례에는 `must_preserve`와 독자 질문이 있었다. v0.3.0 검토도 보존·부분보존·누락·충돌을 구분했다. 이번에는 이 기준을 별도 계약과 구조화된 검토 결과로 묶었다. [기존 프로토콜](../evaluations/protocol.md), [짧은 PR 원자료](../evaluations/runs/2026-11-03-reading-flow/source/short-pr.json)

복합 사실 묶음에서는 대상명, 관측 시점, 판단 한계의 이유가 각각 빠질 수 있다. 이를 따로 판정하되, 조건과 결과의 관계를 단어 목록으로 해체하지 않는다. 예를 들어 처리 동작이 바뀌지 않는다는 포괄 요약이 원자료의 범위를 충분히 포함하면 개별 항목을 모두 다시 열거할 필요는 없다.

정확 문자열 검사는 경로·식별자 등의 존재·부재를 알려 주는 신호다. 문자열이 모두 있어도 조건이나 부정의 관계가 틀릴 수 있고, 동의어로 의미를 보존해도 특정 문자열은 없을 수 있다. 의미 판정과 치명성 판단은 원자료·문맥·근거 구절을 대조한 별도 기록으로 남긴다. [평가 계약 안내](evaluation-contract.md)

## 검증 범위

기존 여덟 사례의 공통 입력과 과거 원문은 유지한다. v0.4.0 출력 여덟 개를 다시 만들고, 별도 작성자가 준비한 새 설정배포 안내와 짧은 작업 보고에서는 v0.3.0·v0.4.0을 각각 생성한다. 후보 스킬·사례·계약을 생성 전에 고정하고, 생성자는 평가 기준과 기대 답을 받지 않는다. [이번 실행 프로토콜](../evaluations/runs/2026-11-03-v0.4.0/protocol.md)

새 사례도 문제 유형을 고려해 설계했으며 요청에 일부 구분을 명시했다. 단회 생성과 같은 모델 계열의 검토이므로 일반적인 성능, 사람의 피로·기억·탐색 시간, 다른 모델의 결과를 입증하지 않는다. 결과가 아쉬운 문서를 후편집하거나 재생성해 같은 실행의 개선 사례로 대체하지 않는다.
